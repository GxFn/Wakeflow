# 1.4 开发计划：削减 Controller 的回合，让证据由 Wakeflow 自己核实，让做完的事读得到（2026-11-17）

> 性质：1.4 的现行开发计划（用户 2026-11-17 确认）；阶段边界与完成定义以本文为准，运行时行为仍以代码为准。
> 出发点：[1.4 的方向](./2026-11-16-1.4-direction.md)（第 9 节为调研之后的修正）与本机忽略目录里的调研报告。
> 用户（2026-11-17）："同意你的调研结果，你来设计安排开发计划吧"；看过建议稿之后："可以先统一完成再部署，正式
> 工作区计划等待这版需求做完后使用，其余按照你的建议记录和执行"。
> 登记：`docs/references/open-items.md` 的 I22、H13、K9、H7、D12、X15、X33。

## 1. 一句话的目标与三个度量

**目标**：保留"需求 → 任务包 → 投递 → 独立评审 → 归档"这副骨架和它的四条保证（写明的要求、落地证明、结果绑定到
提交、一个接受的决定），把 Controller 为记账而走的回合拿掉，把提交类证据交给 Wakeflow 自己核实，把做完的事变成
不问 Controller 也读得到的页面。

每一段收口时都量这三个数，现场一轮里再量一次；它们同时显示在每个 Demand 的页面上（第 3 段之后）。

| 度量 | 基线（1.3.1，用 `wf metrics` 量出） | 1.4 的目标 |
| --- | --- | --- |
| 单目标 Demand 里 Controller 一侧的 Wakeflow 调用数 | 一次返工的 Demand 是 42 次（全部工具调用 54 次）；去掉返工那一圈估计约 27 次 | 无返工的普通路径不超过 12 次；快速 Demand 不超过 7 次 |
| Controller 为每个目标手写的字节数（任务包加评审决定） | 每个 Demand 的每目标值，中位数 6,684 字节（5,437 到 11,132） | 不超过 3,500 字节 |
| 评审阶段（结果导入到决定）的秒数 | 每次决定的中位数 276 秒（167 到 1,538） | 不超过 140 秒 |

基线取自一次性测试工作区里 7 个已归档的 Demand（9 个目标、10 次决定、36 条证据、102 个事件）与 1.3.1 tmux 一轮里
那条带返工的 Demand 的 Controller 会话；任务刻意做小，样本很窄。手写字节数的口径只含归档里原样存着的任务包与
评审决定，投递文本与证据选择不计（见 `docs/references/maintainer-tools.md` 第 28 节）。

目标数是设计值，不是承诺：普通路径 12 次的算法是 status 1、认领 1、规划 1、准备 1、结局 1、检查 1、决定 1、
完成 2，加上余量；能不能到，由第 6 段的现场说了算。

## 2. 不做什么

- 不做任务队列，不改"一个仓库同一时刻一份未完成的任务包"；不把并发粒度降到窗口；不重做 pod。三件事只出设计
  结论（第 7 节）。
- 不把机械工作放进 hook 或后台进程去推进流程；不把工具面从 MCP 换成 CLI；不做事后补记。
- 不加按改动大小的阈值，不加新的需求类型（快速 Demand 的载体在第 4 段先出设计）。
- 不为桌面与 tmux 之外增加传输；Codex 维持 preview。

## 3. 分段

每一段是"若干批、一道完整门、一次提交（源码与文档、再制品）"。段内只跑影响报告要求的那一级。涉及助手、启动
指令、观察或投递文本的段，两种传输同批落地，或者把差距登记进 X / Y 两节。

### 第 0 段：合同与基线（只有文档与维护者工具）

- 三份决定记录：
  - **只读 git**：允许的固定命令清单（存在性、父提交、改动路径、补丁摘要、祖先判断）、不触发仓库钩子与外部
    diff 驱动的启动方式、超时与大小上限、归档里存什么（始终存补丁摘要与改动文件清单；补丁正文在上限内也存）。
    写明它扩展的是 `src/foundation/git/` 里已有的封闭能力，并逐条改掉其他 ADR 里"不读 git"的措辞。
  - **调用形状与确认点**：内部追加一次调用（对齐 ADR-0012 D2）；完成不是确认点（对齐 ADR-0011 D4），有东西
    要留给使用者时才停；快速 Demand 接受即归档。
  - **事件形状的一次升级**：结果报告加"每条验收锚点的结论"（通过、失败、受阻、未运行）与"任务包之外收到的
    指示"；写明这是升级器机制的第一次真实使用，用不上就在第 5 段删掉那套脚手架。
- 防御的留存标准写成一条规则：留下的理由只能是"现场记录里它拦对过"或"它便宜且外部有先例"。
- 文本拆分方案：三份顶格的参考与 Controller 技能各拆到哪里，之后每一段对有上限的文件净增行数不大于零。
- 维护者工具里加一个度量命令：从归档算手写字节数与评审阶段秒数，从会话记录算调用数；把基线记进门日志。
- 门：第 1 级。

### 第 1 段：只读 git 与自动证据

- `src/foundation/git/` 的只读读取器，带它自己的测试（真实的临时仓库）。
- 目标导入结果的那一次调用里，Wakeflow 当场核对上报的提交：存在、属于这个仓库、在任务基线之后、改了哪些
  文件；并把这些事实记成提交证据。Controller 被回调唤醒时证据已经在，不必再手工导出 diff、预览、应用。
- `commitExpectation` 改为对照 git 而不是目标自己的申报；新增的拒绝原因进拒绝参考。
- 已接受的结果是否已合并，改用真实的祖先判断。
- 完成时的 `required-evidence` 认自动记下的证据；`diff` 类证据保留给 git 里没有的材料。
- 两个宿主同批（读取器与宿主无关）。
- 风险：启动 git 的安全面。读取器只接受清单里的参数，测试里放一个带恶意钩子与 diff 驱动配置的仓库钉住它。
- 门：第 2 级（动了 `src/foundation`）。
- 执行记录（§13.261）：读取器、导入时核实、自动证据与评审单元里的核实情况已做；"在任务基线之后"、`leave-uncommitted` 对照 git、祖先判断与补丁正文进归档没有做，登记为 K10，前三项要先有任务基线，建议并进第 3 段。

### 第 2 段：调用路径变便宜（含调用路径上的第一批减法）

- 评审与证据解耦：追加证据不再让已检查的评审摘要失效；或者让决定这一次调用带上要记的证据，一次提交多个事件。
  两种做法在本段开头各写半页，选一种。
- 认领一次调用；引用类证据一次调用，只有内容审查有发现时才保留预览。
- 投递结局按文件引用交回：tmux 助手的 `deliver` 与桌面助手的 `landing` 把结局落盘，结局工具接受引用（窗口登记
  已经这样做）。
- 实现任务的窗口由仓库推出，`assignment.windowId` 不再要调用方填。
- 变更结果里的 `next` 带上后续调用需要的标识；命令与技能文本改为"回合开始、被唤醒、手里没有标识时才读
  status"；`inspect` 对已经读过的任务包只回摘要与引用。
- 拒绝文本可操作：`invalid-request` 说出期望的形状，不再只给路径。
- 完成不再是停点（文本）；删掉或修好在一项上恒通过的那道门。
- 按角色的工具子集：产品、Design、Test 窗口的工具目录只含各自用得到的工具。
- 门：第 2 级。
- 执行记录（§13.262、§13.263）：文本拆分与清单里的各项已做；"恒通过的那道门"查明是 Demand 级的 `append-candidates-clear`，按 ADR-0031 放进第 5 段的删除清单，没有在这一段动；余项登记为 K11。

### 第 3 段：事件形状升级与阅读面

- 事件升级：结果报告的两个新字段、升级器、黄金重放语料的补充；目标技能写明逐条锚点怎么答、任务包之外的指示
  怎么申报；Controller 的评审决定因此可以更短（独立检查只记与锚点结论不一致的部分）。
- 一份任务包承载同一窗口的多个工作项：锚点本来就可以多条，这里补的是逐条结论与规划文本，不改谱系规则。
- 阅读面：
  - 历史索引（账本根）与每个 Demand 一页（归档修订目录的旁边），由事件流与归档确定地渲染，可重算；页面带
    四样固定内容——要求了什么、改了什么、验证了什么、还剩什么——和第 1 节的三个度量。
  - 活动页加一栏"正在等使用者的事项"。
  - 本地的会话链接另起一份投影，不进账本。
  - 看板索引跟随工作区语言。
- X15：投递文本里的桌面会话号不再进归档（做法在本段开头定；改不动就把它列为已知例外并在页面渲染时抹掉）。
- 门：第 2 级（动了合同与持久形状）。

### 第 4 段：越级留痕、便宜的续接、快速 Demand

- 评审单元列出投递落地到结果导入之间、目标会话里不属于 Wakeflow 的 prompt 的条数与时间；`nudge` 的文本摘要
  落盘以便归类；Codex 上没有起点记录时报未观察。
- "接受上一份并续接下一份"压成一步。
- 快速 Demand：一个新工具加一条命令，服务端按顺序执行发布、认领、规划、准备；限制是结构性的（一个仓库、
  一个实现目标、没有测试目标、不开 pod）；接受即归档。需求的载体先写设计：倾向由工具从一句话生成两份最小
  文档，不加新类型。
- 门：第 2 级。新增公共工具，所以 1.4 是一次小版本。

### 第 5 段：底层的减法（每一类单独成段、单独过门）

每一类开工前先给用户一份清单：要删的文件与测试、因此不再有的保证、现场记录。用户点头之后才动。

| 顺序 | 类别 | 做法 | 前提 |
| --- | --- | --- | --- |
| 5a | 事务、日志与恢复 | 收敛为一种协议加幂等重放；自己造成过死路的恢复入口先删 | 第 2 段稳定 |
| 5b | 摘要与陈旧拒绝 | 只留真有并发含义的那几处 | 第 2 段的解耦已落地 |
| 5c | 隐私扫描 | 只留凭据类 | 无 |
| 5d | verify 门与观察 | 合并没有因真实原因失败过的门 | 无 |
| 5e | 版本演进脚手架、受管文本历史 | 第 3 段用过就留，没用上就删 | 第 3 段 |
| 5f | 文件系统原语 | 保留原子写，链接与属主检查降级 | 无 |
| 不动 | 锁与工作认领、幂等键、制品身份校验、请求边界的 Schema、hook 落地证据、角色门与写守卫 | 保留 | 锁类等并发粒度的结论 |

六类都在 1.4.0 之内做完（用户裁决：统一完成再部署）。5c 到 5f 互不依赖，先后可以调；5a、5b 影响调用路径上的
拒绝，排在前面。

### 第 6 段：现场与发布

- tmux 一轮（我来走）与桌面一轮（用户在场），各量一次三个度量；内容至少包含：一个普通的单目标 Demand、
  一个带返工的、一个快速 Demand、一次有人直接对目标窗口说话的投递、更新路径。
- 修现场查出的，再由用户打 `v1.4.0` 并跑 `release:check`。

## 6. 风险

| 风险 | 应对 |
| --- | --- |
| 启动 git 带来新的攻击面与平台差异 | 封闭的参数清单、恶意配置的测试仓库、超时与大小上限；拿不到结论时报未核实，不拦主路径 |
| 事件形状升级破坏已有归档与黄金重放 | 新字段可选、只在出现时进摘要；升级器加重放测试；用测试工作区里的真实归档只读核对 |
| 文本预算已到顶 | 第 0 段先拆；之后有上限的文件净增行数不大于零 |
| 调用变少之后丢了本来靠多一步才暴露的问题 | 四条保证各有测试钉住；每段的现场里故意走一次返工与一次拒绝 |
| 样本窄：一个使用者、几周、一个真实 Demand；这一版做完之前正式工作区不用它 | 第 6 段的现场里走一个多仓库、带返工的真实规模 Demand；每个 Demand 页面带三个度量，正式工作区启用之后继续看 |
| Codex 上观察与发送的差异 | 每段写明 Codex 的行为；做不到对等的登记进 E 节，不阻塞 |

## 7. 只出设计结论的三件事

各写一份不超过两页的设计，1.4 收口时由用户决定进不进 1.5：

1. **任务队列**：一次投递带同一窗口的一串任务包。要回答：预排的任务包在前一份评审之后作废的比例（用第 3 段
   之后的真实数据）、谱系三层不变量的改法、返工怎样波及后面的任务包。
2. **并发粒度**：从"一个 pod 一个 Demand"降到"按窗口互斥"。要回答：Controller 一个会话同时推进两个 Demand
   的注意力成本、评审摘要与工作认领怎么改、锁类防御哪些因此必须保留。
3. **pod 重新设计**（H7、D12）：只含部分仓库的 pod、检出的摆放位置。
