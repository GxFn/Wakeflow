## 2. 需要用户先定的四件事

**裁决（用户，2026-11-09）：1 取 (a) 开发工作树；2 补充包挂到原 Demand；3 pod 重新设计放 1.4，1.3.0 只写明限制并在创建时提醒；4 批 8 六项全部做完。**

1. **收敛期间怎么部署。** 正式工作区直接加载本检出的 `plugins/`，每次重建都是一次部署（ADR-0026）。八批都要重建，而真实验证排在最后：照现在的做法，正式工作区会连续收到八个没有经过现场的构建。可选：
   - (a) **开发移到仓库里的一个工作树**（`.claude/worktrees/` 下，分支 `dev/1.3`），八批的源码、制品与门都在那里；正式工作区继续加载主检出，停在现在这一版。全部批次做完后选一个正式工作区空闲的时间把 `main` 快进过去（一次部署），紧接着做终验，通过后打 `v1.3.0`。推荐。
   - (b) 维持现状：每批门过即重建部署，正式工作区是受监督的现场，出了问题当场修。
   - (c) 维持现状，但 1.3.0 完成前正式工作区不开新 Demand。
   (a) 需要给 ADR-0026 的"只在 `main` 上开发"加一条例外：收敛型版本可以用一个短命的开发工作树，合并后即删。
2. **补充需求走哪个机制（Q7，H2 / H3 / H10）。** 现在有两个各缺一半的出口：`wakeflow_continue_demand` 保留历史但带不进新的验收标准；supplement 需求包能带新标准，却会被认领成一个与原 Demand 无关的新 Demand。11 月 11 日之后给 Node 24 那个 Demand 抬底线，走的就是这条路。建议：supplement 包声明它补充的是哪个需求，`continue_demand` 的 requirement-supplement 续接引用这个包——历史留在原 Demand，新的验收标准来自冻结的包，归档里两份都在。
3. **pod 的布局与粒度（Q10 余项，H7、D12）。** worktree pod 把每个仓库的检出放在 `<仓库>/.claude/worktrees/<名字>`，仓库之间的相对 `file:` 依赖在那里解析不到——Alembic 的五个仓库正是这样互相依赖的，所以现在的 pod 对它们基本不可用；另外每个并行 Demand 都要一个满配 pod。这是一次重新设计（检出按工作区布局成组摆放、pod 只含部分仓库），要 ADR 和两种传输各一轮现场。建议：1.3.0 只把限制写明并在创建 pod 时检出这种依赖给出提醒，重新设计放 1.4；如果近期就要对 Alembic 并行开 Demand，则提到 1.3.0 的批 4。
4. **架构债那一批（批 8）做到哪里。** L1、L2、L4、L5、L6、L8 都是不改变行为的重构，用户看不到收益，回归风险却实打实。建议：1.3.0 只做 L6（宿主特定知识留在中立切片里的清查，双传输规则要求它）与 L1 的收尾，其余四项留到 1.4；如果希望 1.3.0 一并清掉，批 8 按全量排。

没有列进来、我按推荐直接执行的小决定：status 的默认档保持完整输出、摘要档按需（K5）；hook 记录不加签名或链（F5，ADR-0020 已定）；Codex 维持 preview，不在 1.3.0 做 Codex 的现场项。

### 批 1 助手进静态门（D5 / Y5；大）

> **已完成（2026-11-10，gate-log §13.238）。** 做法与下文一致，多做了一件：状态栏脚本是第三段写在字符串里的脚本，一并纳入。余项记在 open-items D5。

现状：tmux 与桌面两个助手是 3,390 行写在 `String.raw` 里的 JavaScript，没有类型检查、没有 lint；prompt 摘要、许可身份行、hook 记录读取、绑定与定位子读取在内核和两个助手里各写一份——1.3.0 第一批改一条规则就动了三处，Y17 就是这样漏出来的。

做法：
- 两个助手改成真实的源文件（`src/hosts/claude-code/assets/` 下的 `.mjs`，`// @ts-check` 加 JSDoc），进 `tsc` 的 `checkJs` 与 Biome；共用的部分（prompt 规则、hook 记录查询、有界 JSON 读取、参数解析）拆成片段，只写一份。
- 发布出去的仍是每个助手一个自包含文件：制品构建在生成阶段把片段内联，产出一个生成模块供运行时读取字节与摘要，漂移检查与 `schema:check` 同一做法。发布资产集合、路径、允许规则都不变。
- 内核的 prompt 规则与助手片段之间加合同测试：同一组向量、同一条正则源。
- 助手现有的 48 条进程级测试原样保留，作为行为不变的证据。

风险：这是对现场最敏感的代码。批内不改行为，只搬家与补类型；行为改动留给后面的批。涉及 tsconfig，按规则走完整门。

### 批 2 宿主事实与观察（A3 余项、G14、K2、X4、X28、X29；大）

> **已完成（2026-11-10，gate-log §13.239）。** 与下文一致，三点出入：宿主版本只在 `launch` 与 `self` 时读（`preflight` 的版本照旧只打印）；按引用的观察助手仍同时内联打印；`tools/list` 预算因登记请求的 Schema 增长从 104 KiB 调到 105 KiB。

- **绑定记录事实，而不只是摘要（G14、A3、X28）。** 握手时由服务端把该窗口解析后的启动参数取值（模型、思考档、权限模式）记进绑定，助手 `launch` / `preflight` 读出的宿主版本一并记下。status 里窗口的漂移按字段说话（"模型：登记时 A，现在配置 B"）；没有取值的旧绑定退回现在的摘要比较。SessionStart 的 hook 输入若带模型字段，观察器记下它，配置的模型有没有跨过桌面接管（X28）就成了可读的事实。
- **回调许可带传输（X29）。** `hostAction` 增加由宿主画像给出的传输与（桌面下）Controller 的桌面会话标识，目标不再从 prompt 的措辞里推断该用哪条路。
- **权限模式不一致进 status（X4）。** 现在只在记录结局那一次返回里出现。
- **落地结果给出字符数（ADR-0027 未决 1）。** 按身份落地时，结局结果直接给出许可与收到的字符数。
- **宿主观察按引用（K2 / Y10）。** tmux 助手把 `panes` 等观察落盘并给出引用与摘要，登记与维护工具接收引用而不是由模型逐字转抄；内联写法仍接受。收益主要在 tmux 的 pod 开关（每窗口约一万输出 token、16 窗格上限），桌面的 `list_sessions` 来自 app 工具，仍内联。

涉及绑定与两个公共请求的 Schema，按规则走完整门；向前兼容的做法与 ADR-0027 相同（可选字段，旧记录读成空）。

### 批 3 信任边界（F1 / Y7、F9；中）

> **已完成（2026-11-10，gate-log §13.240）。** 与下文一致，四点出入：写拒绝的表在助手的构建期取值里（与按角色的允许规则同一处），不在宿主画像——画像的消费者是共享层，而这张表只有助手用；Design 窗口一并带规则；受管路径多了根上的两份 Claude settings；规则语法以 print 模式在草稿目录探明，没有动用测试工作区，桌面接管后是否保留留给终验（X30）。F2（运行时调用者校验）随 F1 一起做了。

ADR-0020 决定 6 把这些控制排在"第一轮现场测试之后"，现在到期。

- **受管路径的写拒绝。** 产品与 Test 窗口启动时带上对 `.wakeflow-local/`、`.wakeflow-active/`、配置文件与账本的 Edit / Write 拒绝规则（模式由宿主画像给出）。它挡不住 Bash，ADR-0020 对 B 类对手的承诺本来就是"降低误用、保持可见"；规则的确切语法与桌面接管后是否保留，先在测试工作区探明再写进画像。
- **按窗口角色的运行时工具校验。** 每个窗口的 MCP 服务进程以该窗口的执行根为工作目录；入口按配置把工作目录对应到角色，再按归属表（ADR-0020 决定 3，已是 contracts 词汇）拒绝越权工具。认不出角色的调用（维护者工具、引导会话）不受影响。
- **隐私扫描的精度（F9）。** 不再误拒普通的 URL 路由与产品 UUID，补上 `file://`、`key:/path` 一类漏放。

## 5. 终验（八批之后，一次）

两种传输各一轮完整的窗口生命周期，外加下面这张清单；每一项都要有 hook 记录或账本记录作证，结果进 gate-log，通过后打 `v1.3.0`。

- **tmux**（一次性测试工作区，我来驱动）：插件更新路径 → 多目标 Demand 到归档；连续 `/wakeflow:next`（I21）、导入不带流修订（H11）、落地 `match` 输出；一个 worktree pod 的开与关；回调静默后的 rearm。
- **桌面**（测试工作区加正式工作区的自然使用）：1.2.0 → 1.3.0 的升级路径（C6 / V6）；按许可身份落地（带 `@` 的投递）；`landing --prompt-ref`；`permission-mode-mismatch` 的触发（X4）；配置的模型是否跨过接管（X28）；`set_session_title` 是否弹确认（X13）；一个桌面 pod（X6）与存活观察（X17）；一次 Test 投递。
- **本计划新增的行为**：受管路径的写拒绝规则在两种传输上是否生效（桌面看接管之后，X30）、角色校验拒绝越权调用（产品窗口里调一次 Controller 的工具，应得 `tool-not-for-role`）、补充需求的续接、观察按引用。
- **仍只有测试覆盖、现场触发不了的**照实列出，不算通过。

## 6. 收敛期间的规矩

- 每批：批内做完 → 一道完整门 → `smoke:artifacts` → `wf handoff` → 提交（源码与文档一笔，制品一笔）→ gate-log 一节。门不按批内的小步跑。
