# 1.4 的方向：目标、读代码之后的更正、计划与已记录的决定（2026-11-16）

> 性质：讨论记录加方向性决定，不是命令来源；登记见 `docs/references/open-items.md`（I22、H13、K9、H7、X15）。
> 来由：1.3.1 两轮现场之后与用户的讨论（任务与成果的阅读面、越级指挥留痕、小任务的轻量路径、仪式感）。
> 依据：三份委托出去的只读代码调查（投影与归档、hook 记录与评审单元、事件模型与证据），加维护者自己读的技能
> 文本与 ADR-0010 / 0011 / 0012。调查带文件与行号，**没有逐条复核**；标注"未核实"的见第 7 节。
> 用户（2026-11-16）："可以全部按照你的建议先记录"。第 5 节照此记录；其中两条本身就是"先出设计再定"。

## 1. 1.4 的目标

- **可读**：做完的 Demand，不问 Controller 也能在一页里看到要求、结果、决定和证据。
- **便宜**：单目标的小任务，Controller 一侧的工具调用降到个位数。
- **可信**：提交类证据由 Wakeflow 自己核实，而不是代理申报。
- **留痕**：投递期间有人直接对目标窗口说话，评审时看得见。

## 2. 读代码之后对此前说法的更正

1. **提交证据并没有在复制 git。** `commit` 类证据只记 `{repositoryId, commitOid}` 的投影，已经是按引用
   （`src/governance/evidence/managed-evidence-source-projection.ts`）。被复制的是 `diff`：它必须是受管路径下的
   文件，由 Controller 先手工导出再登记（文本在 `references/evidence.md`）。Wakeflow 不启动 git、不读 git 对象。
2. **"多步合成一次事务"做不到。** Demand 根的发布固定为一次提交、一个事件、流版本 1
   （`src/governance/demand/publication/`）；规划与准备投递各是一次提交，信封的栅栏绑定本次提交的预期版本。
   可行的形式是服务端按顺序执行现有命令的宏：每一步有派生的幂等键，中途失败留下的是普通路径能接着走的状态。
3. **归档前的用户确认不是设计里的确认点。** 完成工具的请求没有确认字段；文本是"把预览读给用户"
   （`references/delivery-and-review.md`）；ADR-0011 D4 与 README 只有两个确认点（发布需求、需求包要求时的
   任务计划）。现场里 Controller 停下来等确认是它自己的理解。
4. **Controller 发布最小需求包不只是权限问题。** 角色表不收窄 Controller，但发布要从 Design 面读
   `requirement.md` 与 `landing.md`，各有必需章节，还要用户确认一节与 `confirmedAt`、非空的验收标准
   （`src/capabilities/requirement/`）。需求类型只有 requirement、bug、supplement、research。
5. **每个 Demand 的可读页面已经有了**：活动期间在 `.wakeflow-active/projections/<demandId>/` 下两页
   （路线与目标表、进度），归档后的刷新把它清掉（`src/kernel/active-projection.ts`）。

## 3. 四个更深的判断

1. **Wakeflow 不读 git，是多处仪式的共同根因。** 目标上报的提交号不核对，`commit` 证据只核格式与仓库已配置；
   "这个提交改了什么"靠 Controller 手工导出 diff；已接受的结果是否合并判不了祖先（投影里写明"没有对象图不能
   判祖先"）；`commitExpectation` 只核对目标自己申报的处置。
2. **一个 pod 一次只能有一个 Demand，比仪式更硬**（ADR-0010 D3、ADR-0011 D5 / D7；`pod-busy`）。快速 Demand
   只在空闲时可用。代码里已有更细的互斥：每个窗口同一时刻至多一份工作认领，跨 Demand 生效
   （`src/kernel/work-claims.ts`）；pod 级的规则是叠在它上面的。
3. **技能文本已经顶到上限。** Controller 技能 200 / 200 行；`delivery-and-review`、`desktop-transport`、
   `workspace-and-windows` 各 400 / 400；`init`、`status` 两条命令 40 / 40。1.4 的每一项都要写代理文本。
4. **改已持久化的事件形状很贵，应当只改一次。** 结果报告存在 `result.target-result-recorded` 事件里，加字段
   要过版本编解码与黄金重放。想加的至少两处：任务包之外收到的指示；每条验收锚点的结论（技能要求逐条回答，
   报告里没有这个结构化字段）。

## 5. 已记录的决定（按维护者的建议）

1. **允许 Wakeflow 只读地读 git**：只用固定的几条只读命令；归档里始终存补丁的摘要与改动文件清单，补丁正文在
   一个大小上限之内也存，使历史被改写之后归档仍然自足。这改的是"不启动 git"这条既有原则，动手前写进决定记录。
   用户此前同意的"证据按引用记"落到这里。
2. **普通 Demand 归档前不再等用户确认**：对齐 ADR-0011 的两个确认点——归档之后报告，有东西要留给用户处理时
   才停。归档可以经续接重新打开。快速 Demand 接受即归档（用户此前已裁决）。
3. **快速 Demand 的需求载体**：倾向于不加新的需求类型，由工具从一句话生成两份最小文档写进账本，归档与历史
   索引里只有一种东西。把握不大，**先写设计再定**。
4. **并发粒度**：先出设计结论（能否从"一个 pod 一个 Demand"降到"按窗口互斥"），不承诺 1.4 实现；排在 3b
   之前想清楚。
5. **文本预算**：拆文件，不上调上限；新增的工作尽量从文本挪进工具。
6. **桌面会话号进账本（X15）**：讨论里只提了问题、没有给建议，用户未单独表态。维护者的建议：做阅读面时一并修。

## 6. 调查带回的、会约束设计的事实

阅读面：
- 账本根目录与 `archives/<demandId>/` 下修订目录的旁边，现有检查都不枚举；`requirements/<id>/` 是排他集合，
  归档 `payload/` 里多文件会在续接时判 `archive-payload-drift`。规范要求每个具体文件有声明的角色。
- 已有读取器能从归档 payload 重建"目标 → 任务包 → 结果 → 决定"的历史
  （`readArchivedDemandResultReviewSnapshot`，`src/governance/review/demand-result-review-snapshot.ts`）。
- 看板索引有意滤掉 withdrawn 与 archived，并且是硬编码的英文；"做完的 Demand"的唯一索引是看板上终态的认领
  状态文件。没有任何代码枚举 `archives/`。
- 活动投影的刷新以 `projection` 作用域观察，有意剥掉绑定、hook、归档，使刷新、status、verify 算出同样的字节；
  内核不能引入绑定存储。会话链接需要另一份本地投影。
- 需求原文不在归档 payload 里，由清单按引用与摘要指向账本记录。

越级留痕：
- hook 记录对 `user-prompt-submit` 记 `promptDigest` 与 `promptPermitIds`，不存正文；只按 30 天年龄清理，
  没有按 Demand 的留存。只对已绑定的会话写记录。
- 宿主包裹在算摘要前被剥掉，记录里没有"是否跨会话消息"的标记。
- 评审现在只读结果上报之后的目标会话记录；查询只有 `since` 没有 `until`。
- `nudge` 的文本摘要没有落盘；就地重启的首条 prompt 只发给 Controller 自己。
- 评审单元的结果 Schema 是封闭的；它不带投递落地的记录号（那个号只在结局事件里）。
- Codex 上记录形状相同，但落地常由发送返回证明，没有落地记录可以当区间的起点。

轻量路径：
- 一次提交可以带至多 64 个事件，但一次提交只对应一条命令；今天只有评审决定会产出多个事件。
- 证据发布有自己的事务，每个 Demand 一个固定的日志槽位，一次一份清单、一个事件。
- 评审快照的摘要含流版本：检查之后每追加一条证据，已检查的摘要就失效，所以现在是"检查 → 记证据 → 再检查 →
  决定"。
- 任务包里由调用方写的字段很多（目标、已确认的上下文、边界三段、完成预期、锚点的 claim / probe / expected）；
  需求只提供每条验收标准的 `{itemId, text}`。实现任务的 `assignment.windowId` 是必填，文本却说"窗口由
  Wakeflow 推出"。
- 20 个结果 Schema 里 19 个带 `next`，但只有第一个前沿的种类、不带标识；标识在同一个结果的其他字段里。
- 有预览与应用的工具共 8 个；其中认领与记证据是代理自己预览自己应用，偏离 ADR-0012 D2"只用于宿主效果、
  不可逆或需用户确认的步骤"。

## 7. 没有核实的

- 调查没有读测试目录；pod、端点、维护三块只读到头部或提纲。
- `/clear`、`/compact` 会不会改变会话标识；宿主对命令行参数、斜杠命令、排队消息是否触发 `UserPromptSubmit`。
- Codex 的工具发送是否产生 hook 记录（登记册里的现场笔记说没有）。
- 把并发粒度降到窗口之后，Controller 一个会话同时推进两个 Demand 的注意力成本，没有任何现场数据。

## 8. 用户补充的原始设想与旧版工作区的事实（2026-11-16）

用户的三点（原话的意思）：

- Controller 把任务拆给各个子仓库时**可以存在多个任务包**，子仓库的窗口根据这多个任务包自己安排完成。
- 过多的加固可能是此前的过度防御，**可以拆分、删除**。
- 原本的想法是用更多 JS 脚本快速读写文件，让机械的内容自动、快速地完成；可以选更多工具来强化这一部分，
  **最好能异步并行，不影响 Agent 的推进**。

用户允许简单了解旧版（0.9.x）正常工作的那个工作区。只读看到的事实（只记数字，不记内容）：

- 账本里 25 份需求设计；38 个状态根、519 份任务包，每个需求的任务包中位数 10 份、最多 72 份。（此前这里写的
  "52 个状态根、约 820 份"把留存区里的归档副本重复数了一遍，已更正；见第 9 节。）
- 564 个派发组里 559 个只有一个目标，没有一个组给同一个窗口两份任务；`group-ready` 与 `per-target` 两种
  回传方式因此在实际中没有区别。（此前写的 196 个组、193 比 3 只是留存下来的那部分传输记录。）
- 账本与活动区的记录是给人读的 Markdown（待办板、需求链台账、记录映射、当前状态、每个需求的进度页）。
- 旧版流程的成文规则里有两句与现在不同：只给"在下一个真实阻塞之前能安全推进"的窗口建任务包；同一个窗口
  宁可一份有分量的任务包，不要很多零碎的 prompt。
- 只读参考树里的旧版 JS 约 12.5 万行，但那是 0.9.6 的重写；真实工作区里的记录出自更早的脚本时代构建，
  那一代的源码不在参考树里。

由此得到的判断：

1. **真实的用法是"一个需求、很多任务包、基本串行地喂"**，多窗口同时派发很少。现在的模型把它收窄成"一个仓库
   同一时刻一个未完成的目标"，每一份任务包都要 Controller 完整地走一遍规划、投递、评审——对拆成十几份的需求，
   重的正是这里。恢复"任务队列"比提高跨窗口并行更贴近真实用法。
2. **速度的瓶颈不在工具而在模型的回合**：正式工作区第一个 Demand 里工具调用各 1 到 3 秒，调用之间模型思考
   30 到 120 秒。脚本的价值在于少几个回合，不在于单次更快。
3. 减法要先有清单再动手：每一处防御护的是什么、代价多大、现场里有没有因为真实原因触发过，再定留、简化还是删。

对计划的影响（待用户确认后并入第 4 节）：

- **任务队列**：一次投递可以带同一个窗口的一串任务包，窗口按顺序做、每份各交一次结果，Controller 按组评审；
  要改的是聚合里"一个仓库一个未完成目标"与"依赖必须先被接受才能投递"两条规则。
- **机械层脚本化、事件驱动**：只读 git、证据、历史页、快速 Demand 的宏都放进由 hook 或后台任务触发的脚本，
  不占模型的回合。
- **减法**：防御清单，按类别删，每类一道门。

## 9. 深度调研之后的修正（2026-11-16）

四路联网调研加三路本地只读调查（旧版代码与工作区、新版的防御清单、新版的机械层与队列约束）之后，对本文
前面的内容有六处修正。调研报告在本机的忽略目录里，没有入库；下面只记结论，联网来源见报告。

1. **旧版从未有过"任务队列"。** 519 份任务包每一份都只有一个目标、一个窗口；Controller 建一份、约 50 秒后
   发出、评完再建下一份，窗口手里已建未发的任务包几乎恒为 1。旧版与新版是同一条"一个仓库一份未完成的
   任务包"，差别在每一圈的成本：旧版 Controller 一侧约 6 次工具调用加 1 次宿主发送，六成任务包只有编号、
   一段自由文本说明与目标窗口；新版一个小 Demand 42 到 54 次调用。第 8 节的"任务队列"因此改为：先做
   "一份任务包承载同一窗口的多个工作项、逐条给锚点结论"与"接受上一份并续接下一份压成一步"；队列只出设计。
   这是判断，没有测量比较过预排队列与评审后即时生成。
2. **hook 与后台任务不能替模型推进流程。** 命令型 hook 不能调工具，异步 hook 不能阻断，MCP 进程没有后台
   工作（ADR-0003、0009、0023 放弃过）。"事件驱动"的准确落点是把机械步骤做进模型本来就要发的那次调用，或
   助手脚本的同一条命令——包括做进**目标窗口**导入结果的那次调用，使 Controller 被唤醒时证据已经在。
3. **"Wakeflow 不启动 git"字面上不成立。** 运行时已有 `git check-ignore`（`src/foundation/git/`），助手已在跑
   `git worktree`。只读 git 的决定是扩展一个已有的封闭能力，决定记录仍然要写。
4. **减法的次序是先调用路径、后底层。** 防御性主题约占手写源码的 47%，但使用者感受到的"重"在调用路径上
   （自我预览与应用、随每条证据失效的评审摘要、反复读 status、手抄助手输出）；减底层防御省的是维护者的
   时间。现场里真拦对过的（幂等重放、制品身份校验、请求边界的 Schema、hook 落地证据）保留；事务恢复与
   摘要陈旧两类自己造成过死路，先简化；锁与认领要等并发粒度的结论。
5. **计划顺序。** 合同批（只读 git 的决定记录、含四值锚点结论的一次事件升级、文本拆分）→ 便宜路径与调用
   路径上的第一批减法，阅读面与之并行 → 越级留痕与快速 Demand → 队列、并发粒度与 pod 只出设计。
6. **补充项。** 锚点结论采用"通过、失败、受阻、未运行"四值；阅读面加一栏"正在等使用者的事项"；实现按
   角色的工具子集；拒绝文本改成可操作的；每个 Demand 页面带三个度量——Controller 回合数、手写字节数、
   评审阶段的秒数。

证据不足、不应当作结论的：单用户本地工具需要多强的耐久；脚本化能省多少回合；预排队列是否划算；一个
Controller 同时推进两个 Demand 的注意力成本。防御清单里"真实、摩擦、注入"的分类有一部分出自委托的子调查，
没有逐条复核。

**用户裁决（2026-11-17）："同意你的调研结果，你来设计安排开发计划吧"。** 第 9 节的六处修正因此成立：不做任务
队列（只出设计），机械步骤做进已有的调用而不是 hook 或后台，减法先调用路径后底层。开发计划见
[1.4 开发计划](./2026-11-17-1.4-development-plan.md)。
