# Wakeflow Upgrade Plan

> Generated 2026-06-19 from an adversarially-verified deep audit; this is a proposal, not executed work.

## 1. Executive Summary

Wakeflow is **architecturally sound and disciplined**. The core spawn-by-allow-list MCP boundary, the host-profile sync seam, the host-ownership gate on every state write, the activity-monitor pid-reuse guard, the readback fail-closed posture, and the process whitelist / path-traversal fences all verified clean (F6, F7, F29, F30, F31, F44). No data-corruption or single-file-write-safety defect was found; the only hypothesized P0 ("non-atomic durable write corrupts authoritative state") was **refuted** — `wakeflow-state.json` and `controller-events.jsonl` writes are crash-safe (atomic rename + O_APPEND). The headline counts after adversarial verification: **P0 = 0, P1 = 7, P2 = 13** (plus 33 observations / confirmations / by-design items that require no action).

The **single most important risk** is operational, not correctness: in unattended multi-group mode every automation dispatch starts a detached `caffeinate` keep-live lease (F24) that **no result/reduce/decide/complete transition ever releases**, so leases accumulate and keep a macOS controller awake well past completion. Paired with this, the transport runtime and completed state roots have **zero garbage collection** (F32, F33) — files accumulate forever and are re-parsed on every `wakeflow_status`, a compounding latency/context-size and battery hazard on long-lived workspaces. These are degradation/leak issues, not state breakage, which is why nothing reaches P0.

## 2. Method

The audit ran across **8 dimensions**: (1) module organization + script-to-lib classification; (2) connectivity / dead-code / reachability; (3) state-machine correctness + edge cases; (4) delivery / transport / lock / host-ownership; (5) local file storage relationships, archiving, GC; (6) error handling / process boundary / write safety / validation; (7) dual-edition parity + Codex edition; (8) test and validation coverage gaps.

Every raw finding then went through **per-category adversarial verification**: each claim was re-checked against the cited `file:line`, escape hatches were hunted (e.g. "is it really untested?", "does any consumer read this?"), and several were empirically reproduced on the repo Node runtime (the `spawnNode` no-error-handler crash F38, the no-op `--require-todo` flag F11/F40, the `core/`-rooted `ERR_MODULE_NOT_FOUND` F14). Verification reclassified roughly a third of the P1 items down to P2 once their "pinned forever / dead / untested" framing was found overstated (F1, F9, F12, F18, F34, F41, F47, F52).

**Of the raw findings carried into verification, 0 were refuted** as false. Every finding below is `confirmed-real` or `partial` (real mechanism, narrower scope than first stated). The refutations that did occur happened *inside* findings — sub-claims trimmed (e.g. the keep-live "per-window file accumulation" sub-claim in F36 was a false positive; `progress-log` "untested" in F1 was false; F47 exports are test-asserted) — and those trimmed sub-claims are **not** carried as action items. This zero-refuted-as-whole rate, with multiple in-finding corrections, is the evidence of rigor: claims survived re-derivation from source, and the ones that did not survive were removed rather than shipped.

## 3. Answers to the Four Asked Questions

### (A) Overall Architecture & Real-Code-Implementation Problems

The architecture is a dual-edition (codex + claude-code) plugin sharing a byte-identical `core/` synced into both editions, with only host-profile / host-send-adapter / host-artifact-checks specialized per edition. The seam is clean (F6, F7, F50). The real implementation problems are localized, not structural:

| Area | Problem | Finding |
| --- | --- | --- |
| Process boundary | `spawnNode` registers no child `error` handler; a spawn-launch failure (EAGAIN/EMFILE in a long-lived forking server) crashes the whole MCP stdio server | F38 (P1) |
| Process boundary | `spawnNode` timeout sends SIGTERM with no SIGKILL escalation — `timeoutMs` is best-effort, not a hard cap | F42 (P2) |
| State commit | Multi-file state commits are not transactional: a crash between `writeJson(state)` and `appendJsonLine(events)` advances `revision` with no matching event row, diverging the audit/replay trail | F41 (P2) |
| State machine | Sticky `reviewDecision=rework` mislabels a clean same-task re-import as `needs-rework` (escape via `decide-review accept` always exists; tested workflow adds a new task package) | F18 (P2) |
| State schema | `.state` enum omits the written value `dispatched` and lists 4 never-written values; both editions ship the identical wrong enum (unenforced today — no Ajv) | F19 (P2) |
| Schema layer | No JSON-schema is enforced at runtime; all 7 state-machine schemas are documentation/test artifacts only — schema/code drift is possible and undetected | F5, F15 (observation) |
| Concurrency | Reducers read-then-write with no fresh re-read (unlike `render-progress`); two same-host reducer invocations lose an update (cannot fire under single-controller single-host) | F20 (P2) |

### (B) Local File Relationships & Archiving (Storage Graph + What Lacks GC/Cleanup)

The storage graph has three tiers with sharply different durability and cleanup posture:

| Tier | Location | Contents | Git status | GC / cleanup |
| --- | --- | --- | --- | --- |
| State roots (business) | `.workspace-active/workspace/current/<slug>` | `wakeflow-state.json`, `controller-events.jsonl`, `projection.json`, `target-results/`, `task-packages/`, `transition-candidates/`, `intake/`, `evidence/` | **gitignored** | **None** — `complete-demand` does no move/archive; dormant `archived` state has zero writers (F33) |
| Transport runtime | `.workspace-local/wakeflow-delivery/{dispatch-packets,dispatch-groups,delivery-envelopes,delivery-runs,target-results}` + `hosts/<host>/{thread-registry,window-config,keep-live}` | one+ JSON per dispatch/result; per-window registration | **gitignored** | **None** — store exposes only `removeWindowLock`; `wakeflow_status` + `buildReplaySummary` read+parse every artifact each call (F32) |
| Ledger (long-term) | `wakeflow-ledger/` | archived docs, record map | **committed** (kept out of gitignore) | Has archive flow; never holds state roots or envelopes |

**What lacks GC/cleanup:**

- **Transport runtime accumulates forever** (F32, P1): no `removePacket/removeRun/removeResult/removeEnvelope`; scan cost grows with workspace lifetime, not just disk. Each `wakeflow_status` is a full `listJsonArtifacts + parse` over five directories — a compounding latency/context-size hazard.
- **Completed demands are never archived** (F33, P1): state roots pile up in the gitignored `.workspace-active/current` — the controller's primary orientation surface — one tree per demand ever run.
- **Recoverability gap** (F34, P2): state roots and the delivery envelopes they cross-reference both live in gitignored trees; the only committed long-term surface (`wakeflow-ledger`) holds neither. A lost `.workspace-local`/`.workspace-active` leaves no version-controlled recovery path. This is a deliberate design posture, so it is a doc/guidance + (optional) archival concern, not malfunctioning code.
- **Rework orphan results** (F35, P2): the MCP `record_target_result` path writes timestamped `tr-<taskId>-<stamp>.json` on collision and never removes the prior file; each is re-parsed on every later import. (The delivery-script path has a `superseded/` subdir; the state-script path does not.)
- **Retired-window staleness** (F36, P2): thread-registry / window-config files for windows removed from config are never cleaned (`replace-window` overwrites in place, so it is *not* a source of orphans — that sub-claim was trimmed; the keep-live "per-window file" sub-claim was a false positive).

**Verdict (B):** Storage is correct but unbounded. The fix is a single dry-run-default GC/archive capability (see P1 wave 2) scoped strictly to fully-accepted / superseded / config-removed artifacts, plus a decision on whether archived state roots become committed ledger history.

### (C) The Script-to-Lib Organization Decision

**The `core/scripts` vs `core/scripts/lib` seam is already correct and should NOT be reorganized.** Verification (F6) confirmed: no `scripts/lib/*.mjs` helper is an entrypoint (no shebang, not in the allow-list, not spawned by filename), and no top-level `scripts/*.mjs` is imported as a module by another script (cross-script coupling is exclusively `child_process` spawn-by-filename). There is no mis-placed pure helper masquerading as an entrypoint and no entrypoint hiding in `scripts/lib`. The `core/lib` runtime kernel (`wakeflow-runtime/process/trace/mcp-tools`) and the `core/bin` shim seam are likewise sound (F7).

The **runtime allow-list `Map` in `core/lib/wakeflow-runtime.mjs:18-44` is the entrypoint authority**: it is the only gate the MCP boundary (`runWakeflowRuntime`) honors. A second, *independent* invocation system exists — the intra-script `child_process` spawn graph (e.g. `demand-sequence → wakeflow-state/render-progress`; `verify → 7 check scripts`) — and the two can drift (F8). This is exactly why a script can look "alive" (allow-listed) while being dead (no spawner).

**Verdict (C): Do not move any top-level script into `lib/`, and do not move any `lib/` helper up to top-level.** The seam is clean by the allow-list-as-authority test. The only organizational debt is reachability/ownership, not placement:

1. **`wakeflow-compact-index.mjs` is genuinely dead** (allow-listed, documented as part of archive, but no sanctioned caller) — wire it or retire it. This is the one true script-to-lib-adjacent action item, and it needs user confirmation either way because it changes a documented capability.
2. **`commandRecordTargetResult`** is a dual-recorder divergence (a `lib/` export with a live CLI caller but off the MCP path) — consolidate the shared logic, do not relocate the file.
3. **`bin/wakeflow-mcp.mjs`** is a dead shim pinned by its own validate existence-check — remove or annotate.

The conservative recommendation is to **harden the authority instead of reshuffling files**: have `wakeflow-check-scripts.mjs` cross-validate that every allow-list entry has at least one real caller (MCP map, CLI subcommand, or spawn). That additive check (F8) would have flagged `compact-index` automatically and prevents future allow-list/spawn-graph drift — making "is anything mis-placed or orphaned" a machine-checked invariant rather than a manual audit.
