# ADR-0020 威胁模型与信任边界

> 状态：`accepted`
> 日期：2026-10-11
> 裁决日期：2026-10-18（用户：按技术债务复审的建议接受三类对手与可接受残余的定义；F1/F2/F5 的剩余控制与 K4 角色子集排在第一轮现场测试之后）
> 来源：2026-10-07 技术债务深挖簇 C 与未决问题登记 F 主题：安全取舍散落在代码注释里各自决定，没有一处写下对手、资产与边界（F7）；Q5（威胁模型范围）待裁决；批次 3 要求先写本记录，再做不依赖裁决的控制。
> 相关：ADR-0017（运行证据主体与窗口运行身份）、ADR-0018（当前基线）、§13.150 隐私与准入复验（回调标为不可信、凭证扫描）、§13.165–§13.167 技术债务批次 0–2。登记项 F1、F2、F4、F5、K4、E2 以本记录为对照。

## 背景

Wakeflow 让多个 Agent 窗口在同一台机器、同一个操作系统用户下分工：Controller 推进 Demand，Design 发布需求包，产品窗口在仓库里实现，Test 窗口在真实环境里验证。它们共享同一份文件系统权限，而其中的产品与 Test 窗口会读取并执行不受信任的仓库内容。到本记录为止，各文件各自假设了不同的模型：`rooted-directory.ts` 以"受信任的单用户工作区"为前提，`hook-observations.ts` 把记录称作"私有权威"，调用者身份交给技能文本约束，而产品窗口又在处理不受信任的内容。审查者因此无法判断 F 主题的各项究竟是缺陷还是已接受的取舍。

当前实现的相关事实（2026-10-11）：

- 所有窗口以同一操作系统用户运行；Claude Code 上放置不在工作区根的窗口以 `--add-dir <工作区根>` 与缺省 `auto` 权限模式启动。
- 每个 Wakeflow 管理的根的 `.claude/settings.json` 放行整个插件 MCP 服务器（通配规则），而不是该角色实际使用的工具。
- MCP 工具请求只带工作区根，没有调用者或窗口身份；Controller 专属动作（评审决定、完成、取消、pod 变更）只受技能文本约束（§13.140 已从产品窗口的 cwd 复现）。
- hook 观察记录是 0600 的普通 JSON 文件，没有签名或链；它证明"宿主在那个时刻观察到了什么"，不证明文件此后未被同用户进程改动。
- Claude Code 的 tmux 助手是工作区运行时根里的普通文件，Controller 以精确到路径的允许规则免提示运行它；verify 的 `host-settings-assets` 门事后核对字节，运行前没有核对。
- 回调文本已标为不可信数据、Controller 指令只读 inspect（§13.150）；凭证扫描守住进入 git 跟踪 ledger 的证据（§13.150、§13.161、§13.165）；事故记录不含消息与路径（§13.166）。

## 决定（Q5 裁决：2026-10-18 接受）

1. **三类对手与各自的立场。**
   - **A 类：诚实但会出错的 Agent 与宿主。** 中断、重复、误读、幻觉、过期视图。这是运行时必须防住的对手：幂等键、fence、CAS、从证据派生处置、精确正文准入、三态观察、事故记录。现有控制以此为设计对手，继续作为主要防线。
   - **B 类：被仓库内容牵引的产品或 Test Agent。** 它在同一用户权限下行动，可能把不受信任内容里的指令当作任务执行。Wakeflow 的承诺是**降低误用、保持可见、不替用户授权**：允许规则只放行该角色使用的工具（F2），回调与报告永远是引用数据而不是授权（F3），Controller 在签发投递许可前由服务器核对助手字节（F1），遗留的指令块与宽泛允许规则被点名（F4），自述证据与宿主观察分级标明（E2）。Wakeflow **不承诺**同用户进程级的隔离：用户在宿主上选择的权限模式与 `--add-dir` 范围是最终边界。
   - **C 类：同一操作系统用户的其他进程，或用户本人直接改文件。** 不在防护范围之内。Wakeflow 只做检测与报告（verify 门、三态观察、事故记录、准入拒绝），不引入签名、HMAC 或链式摘要。F5 据此归为"检测而非防护"，直到 Q5 另有裁决。
2. **证据分级写进合同与文本。** 三个等级：`host-observed`（hook 记录：宿主观察所得，同用户进程可改）、`agent-reported`（`host-send-return`、`agent-declaration`：Agent 自述，Wakeflow 只记摘要）、`controller-judged`（评审决定：Controller 的判断）。status 与评审投影显示投递结局的 `evidenceKind`；任何文本不得把 `agent-reported` 称作宿主证据，也不得把 `host-observed` 称作防篡改。
3. **状态转移的归属表。** Controller：全部工具；Design：`wakeflow_inspect_board`、`wakeflow_publish_requirement`、`wakeflow_status`；产品窗口：`wakeflow_import_target_result`、`wakeflow_status`；Test：`wakeflow_import_target_result`、`wakeflow_record_evidence`、`wakeflow_status`。这张表是技能文本、Claude 允许规则与未来运行时调用者校验的共同来源；允许规则按它收窄（F2 第一步），运行时按窗口身份拒绝越权调用（角色令牌或进程祖先匹配）待 Q5 裁决。
4. **永远不进入 git 跟踪 ledger 的内容。** 凭证（扫描阻断归档）、绝对路径与机器标识、未典型化的会话或线程标识、宿主通知与消息正文。本条已有实现，列在此处作为资产清单的一部分。
5. **已接受的残余风险（到 Q5 裁决为止）。** 同用户进程可以改写 hook 记录、绑定、声明与事件流；产品窗口可以写工作区根（含助手、配置与活动 Demand 文件）；窗口可以绕过助手直接驱动 tmux；Codex 的落地证据是自述。这些都只能被检测或降低，不能被阻止。
6. **Q5 的建议裁决。** 接受 B 类为设计对手、C 类为检测对象；批次 3 先做不依赖裁决的四项（F1、F2、F4、E2）；裁决后再进入 `--add-dir` 收窄、角色令牌或进程祖先校验、hook 记录链式摘要、按角色暴露工具子集（K4）。若用户裁决 C 类也要防，则 hook 记录需要存放在 Agent 不可写位置的密钥与链，这是另一份记录。

## 实施

批次 3 落地第 2、3 条里不依赖裁决的部分：服务器侧的助手字节核对进入 `wakeflow_prepare_delivery` 的前置条件并由 status 展示（F1）；Claude 的允许规则按归属表收窄，归属表作为 contracts 词汇由测试对照技能文本与工具目录（F2）；遗留残留的只读观察进入 status 与 verify，fresh-initialize 对工作区根的遗留标记拒绝（F4）；`host-send-return` 的摘要定义为发送返回值规范 JSON 的 sha256，由 Wakeflow 计算，status 与评审投影显示 `evidenceKind`，文本标明自述（E2）。

## 验证边界

单元与门测试覆盖规则表、核对、观察与投影；真实宿主上允许规则收窄后的权限提示行为、助手被改写后的拒绝路径与 Codex 发送返回的形状都未在现场验证，记为未执行。本记录不宣称任何抗篡改能力。
