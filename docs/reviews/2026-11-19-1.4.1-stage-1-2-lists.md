## 1. 对 ADR-0032 的修订

### 1.1 改掉的五处

1. **决定 4"新建两次同步"改成三次，顺序同今天。** 写暂存、同步暂存、链接到目标、同步父目录、删暂存、同步父目录。去掉的是今天夹在中间的两次重复的文件同步与三次读回。"链接之后、删暂存之前"的那次父目录同步不能省：今天的恢复靠"目标旁边没有暂存，就说明目标已经落盘"这一条——新建中途被杀留下的双链接暂存，会让下一个写入者先把目标与父目录同步、再清暂存。省掉它，进程死在删暂存之后、同步之前时，目标在、却没有落盘，也没有暂存提醒任何人；重试的调用方把"目标已存在"当作成功继续往下做（强制释放回执就是这样写的），再掉电就会两头落空。"删暂存之后"的那次也不能省：工作认领、窗口绑定、Demand 根的几个子目录与维护事务目录的清点不认暂存名字，返回之后暂存再冒出来会挡住命令。ADR 里"暂存残留留给下一次准入清理"这句删去，清理留在今天的地方（同一把锁的下一次获取、同一个目标的下一次写入、维护的显式恢复）：只读命令与维护的预览不进操作作用域，在准入时清理等于在互斥之外写盘。
2. **决定 5"协调用的：不同步"收窄成七类锁，并保留一次内容同步。** 完全不同步的话，掉电后锁文件可能是空的或半截的，现有代码把读不懂的锁判成 `unsafe-lock`，立即拒绝，调用方只会把它报成"锁不安全"，没有找到任何清理它的路径。保留"链接之前同步一次内容"之后，锁文件要么不在、要么完整。降档的是 L1 到 L7（操作作用域的闩锁、写者锁与读者租约，投影锁，看板锁，pod 变更锁，Demand 发布锁，账本记录锁）：它们留下来之后，下一次获取会按"属主已死"清掉。另外五类留在权威档：绑定登记锁留下来的时候，准备投递、评审、pod、状态这些只读清点会一直失败到下一次登记；维护的门锁留下来会让每条变更命令报 `maintenance-recovery-required`；配置、`.gitignore` 重组、程序指令重组三把锁没有任何代码会清。
3. **决定 5"可重建的派生物：不同步"在 1.4.1 不做。** 逐种核过，只有事件快照在文件被删、是空的、读不懂时都能自己恢复。其余的派生页如果降档，每次只省一次同步，却会带来两件事：掉电之后 `verify` 的活动投影门与看板一致性门会一直报失败到下一次变更；看板索引被删之后由认领路径重建时不带语言，会按英文写。任务包投影本来就不该在名单里：没有任何读路径重建它，投递提示又把它的路径直接交给目标窗口。所以活动投影页、看板 `index.md`、`history.md`、归档页都留在权威档（替换 3 → 2），降档留到 1.4.2 逐种补齐证明之后。
4. **决定 3"写入一律是原子的"与背景里"上层没有一处直接用 `node:fs`"都不成立。** 发布到工作区的脚本直接往最终文件名写；整目录发布与追加候选的成员就地写在最终名字上；权限收敛对已发布的文件就地 `chmod`；`CLAUDE.md`、`.gitignore`、宿主设置、设计草稿、证据来源由人、编辑器、git 与宿主来写；账本的记录树进 git。入口层有四个模块直接用 `node:fs`。所以短读的范围要收窄，见 3.1 节。
5. **决定 2"准入一次、在命令外壳里"改成按目标路径判定、当场核对；ADR 的第二个未决问题有了答案。** `status` 读 hook 记录走的是工作区根加完整的相对路径，不是在私有目录里另开的根；一次快速 Demand 的应用跑 6 个命令外壳、打开工作区根 8 到 10 次。所以判定只能是"这次读写的目标落在声明过的私有区域里，并且那个区域根当场核对合格"。不合格就照今天的完整路径走，不新增任何拒绝——`private-mode-reconcile.test.ts` 把两棵私有目录连根放宽之后，要求 `verify` 照常回答并报 `private-mode-drift`、对账的预览给出收敛计划，在外壳里拒绝的话这些都走不到。短路径放在现有原语内部（未决问题二的答案）；标记怎么来是新的问题，见 3.3 节。

### 1.2 补上的三条

6. **删除跟随被删记录的档。** 权威记录的删除同步一次父目录（今天两次，先同步被删的文件那一次没有用处）；轻档的删除不同步。权威记录的整目录删除，删完之后同步一次父目录：终态移除 Demand 根与关 pod 时删回执树，今天都不同步。
7. **掉电之后的状态怎么证明。** 进程被 `SIGKILL` 分不出同步与不同步，今天按同步次数杀进程的扫点证明不了掉电。轻档只含锁与租约，要求定成：这七类锁所在的目录里，死锁文件与死暂存的任意组合，下一条命令都能自己清掉。"任意组合"是因为不能假定文件系统按顺序提交目录操作：代码只在维护的预览里看一眼卷的类型，读不到也放行，`hfs` 这个名字还包括关掉日志的 HFS+。做法见 2.4 节。
8. **"今天已经不同步的"单列一类，第 1 段不碰。** 流索引、事件快照、事故记录（诊断用，丢了只影响一个计数）、各处的修剪删除、发布到工作区的脚本自己写的观察与催促文件。这是对"默认都是权威"的明确例外，范围不扩大。

一处事实更正，不改决定：Node 的 `datasync` 与 `sync` 在这台机器上一样慢（这次单独量了 150 次写入加同步：3.2 与 3.3 毫秒；计划第 2 节在服务进程里量到的平均是 2.6 毫秒），所以 Git 那种"逐个写出、最后刷一次盘"在 Node 上做不到。

## 2. 第 1 段清单：写入

### 2.1 协议的前后对照

| 操作 | 现在 | 之后 |
| --- | --- | --- |
| 原子新建（权威） | 5 次同步，读回比对 3 次 | 3 次：暂存内容；链接之后父目录；删暂存之后父目录。不读回 |
| 原子替换（权威） | 3 次同步，读回 2 次，整份比较重读 2 次 | 2 次：暂存内容；重命名之后父目录。比较保留 1 次 |
| 精确删除（权威） | 2 次 | 1 次（父目录） |
| 事件追加 | 3 次：候选内容、链接步骤里同一个文件再一次、`commits` 目录 | 3 次：候选内容、`commits` 目录、删掉候选之后的 `append-candidates` 目录 |
| 整目录发布（F 个文件、D 个子目录） | 2(D+1) + 2F + 1 到 2 次 | F + D + 2 次，暂存与目标不在同一个父目录时再加 1。每个文件同步一次内容；每个目录在成员都写完之后同步一次 |
| 单独新建一个目录 | 2 次 | 1 次（父目录） |
| 整目录删除（权威） | 0 次 | 1 次（父目录） |
| 锁与租约 L1 到 L7（一个周期） | 7 次同步、读回 3 次 | 1 次（链接之前的内容） |
| 锁 L8 到 L12（一个周期） | 7 次 | 4 次（按权威：新建 3、删除 1） |

事件追加的次数不降，这是我替你做的取舍。今天候选在 `commits` 目录同步之后才删、删除不同步，掉电后候选会带着两个链接回来；Demand 根的清点要求 `append-candidates` 是空的，于是这个 Demand 每次加载都失败，直到跑一次维护。把那次没有用处的"同一个文件再同步一次"换成对候选目录的同步，这个隐患就没有了。不想要的话可以降到 2 次，隐患维持今天的样子。

hook 的观察记录留在权威档，不降：每条从 5 次降到 3 次，每新建一级日期或分片目录另加 1 次（今天是 2 次）。它是落地证明。这回答了 ADR-0032 的第一个未决问题。

### 2.2 两档怎么写进代码

- 新建与删除两个原语的逐次选项多一个取值 `content-only`（候选原语里已经有这个词）：链接之前同步内容，不同步父目录；删除不同步。只有锁原语对 L1 到 L7 传它。`none` 维持今天的那几个调用点，不新增。
- 根的级别仍然取更弱的一档：187 个测试文件经 `useDisposableDurability` 把根开成 `none`，它们照旧不同步。
- 传 `content-only` 或 `none` 的调用点登记在 foundation 的一张表里；一条测试核对"源码里的降档调用点"与这张表逐项相等。默认是最强的一档，漏登记只会多同步。
- 每一档的同步次数由 foundation 的测试在真实同步的根上钉住（2.1 节的数）。
- 逐种归档见[落盘归档表](2026-11-19-1.4.1-record-kind-table.md)。

### 2.3 掉电之后会看到什么

- **权威文件**：与今天相同。调用返回之后，新状态已经落盘，目录里没有暂存；掉电落在调用中途时，看到的是进程在那一步被杀的样子，恢复规则不变。
- **锁与租约 L1 到 L7**：内容在链接之前同步过，所以文件要么不在、要么完整。目录项不同步，所以掉电前不久跑过命令的话，那条命令的锁、租约甚至一个没来得及链接的暂存会留在目录里，属主已死。今天这只在进程正好死在临界区里时出现；之后会常见，失效锁的清理从少走的路径变成常走的路径。
- **一处残留的例外**：锁记录带 pid 与 `ownerBirth`（开机会话标识、pid 与进程启动时间的摘要），重启后 pid 被别的进程占用也认得出来。但获取锁时读不到 `ownerBirth` 的那种记录，遇到 pid 重用会被判成"不确定"、不清。这是现有行为，登记。

### 2.4 做的顺序

1. **变更接缝。** foundation 里直接改动目录项的调用有 14 处（独占新建 3、`unlink` 4、`link` 2、`rename` 2、`mkdir`、`rmdir`、`rm` 各 1），另有 3 处在 git 临时目录上。把它们收到一个可以被测试挂钩的出口，行为不变。整目录删除今天是一次递归 `rm`，中途的样子挂不到，要么改成逐项删、要么写明不覆盖。
2. **快照扫点。** 子进程里跑一条命令，每次经过接缝之后把两棵私有目录、账本根（账本记录锁在那里）和工作区根上的锁与配置文件一起拷出来；子进程退出之后锁的属主就真的死了，父进程对每一份快照跑下一条命令，要求它照常完成，或者走到一个写明的恢复出口。一个场景只起一次子进程。场景：共享与独占两种作用域的进出，L1 到 L7 各一个周期，事件追加，终态移除 Demand 根。先在今天的代码上跑，列出恢复不了的状态。
3. **组合状态。** 对 L1 到 L7 所在的每个目录，直接摆出"死锁文件、死暂存"的各种组合，要求下一条命令清掉。这一步不依赖文件系统按顺序提交。
4. **修掉恢复不了的状态。** 已知的两处见 2.5 节；扫点与组合跑出别的，先报给你再定。
5. **换协议。** 2.1 节的表，加上 `content-only` 与登记表。
6. **量。** `wf metrics storage` 的前后对照写进门日志。

### 2.5 调研找出的现有隐患

这些今天就在。前两项在锁降档之后会变得常见，必须修；后两项便宜而且明确，建议一起修；其余登记。

| 隐患 | 现在的后果 | 处置 |
| --- | --- | --- |
| 操作作用域里，死掉的 `latch.lock` 旁边有别的文件的死暂存 | 之后每条变更命令等到超时 | 修：清失效锁之前，先清同目录里属主已死的暂存，不论它是谁的 |
| 多把锁放在同一个目录里（看板、pod 变更、Demand 发布、账本事务），别的锁的死暂存挡住失效锁的清理 | 那一把锁卡住 | 修：同上 |
| 追加候选掉电后复活 | 那个 Demand 每次加载失败，直到跑一次维护 | 修：2.1 节的追加顺序 |
| 终态移除 Demand 根与关 pod 删回执树都不同步，随后的日志删除是同步的 | 掉电后可能根还在、日志没了，`recover` 报 `journal-absent` | 修：删完之后同步一次父目录 |
| Demand 根的清点不认属主已死的暂存名字：根目录、`task-packages/`、许可目录、`transactions/`、`index/` 都拒绝；`snapshots/` 在清点里容忍、读快照时不容忍 | 进程死在这些目录里的一次新建中途，那个 Demand 每次加载报 `tree-shape` | 登记；第 1 段不让它更常见。扫点跑到的话按第 4 步处理 |
| 绑定登记锁在场时，只读的清点一律失败；登记锁自己的双链接暂存不在它的恢复范围里 | 进程死在登记的临界区里，准备投递、评审、状态一直失败到下一次登记 | 登记；这把锁留在权威档，掉电不会让它更常见 |
| 配置、`.gitignore` 重组、程序指令重组三把锁没有失效持有者的清理 | 进程死在这三段临界区里，之后的写入一直超时 | 登记；同上。清理随 1.4.2 的"恢复只有一条路"做 |
| 看板索引被删后按英文重建；催促记录读不出来时被当作不存在，那次催促随后被数成投递之外的输入；活动投影按列表顺序清页，前面的页会被后面那页的死暂存挡住；证据负载的 `content` 暂存在候选检查之前没有恢复（最后一条是按代码读出来的，未运行核实） | 各自一处错误或卡住 | 登记 |

### 2.7 不再有的保证

| 拿掉或简化的 | 不再有的保证（一句话） | 现场记录 |
| --- | --- | --- |
| 写入之后的读回比对；新建时链接之后、删暂存之后各一次对同一个文件的重复同步；替换的同类一次；删除之前对被删文件的同步 | 没有对应的保证：内容在发布之前同步过一次，目录项由保留下来的父目录同步落盘。 | 无。 |
| L1 到 L7 的目录项同步与删除同步 | 掉电前不久跑过命令的话，那条命令的锁与租约会留在目录里、属主已死，下一条命令先清掉再继续。今天这只在进程死在临界区里时出现。 | 进程级的清理在现场走过；掉电没有发生过。 |

### 2.8 度量的设计值

快速 Demand 应用的同步 257 次 → 估计 110 到 130 次；记结局 38 次 → 不超过 20 次。计划里写的"不超过 110"是按新建两次同步、派生页不同步算的，不再成立；实数以量出来的为准。测量工具已经补上目录遍历的计数（这次第 0 段做的）；它只数 MCP 服务进程，hook 观察器进程与发布到工作区的脚本不在内。

## 3. 第 2 段清单：读与准入

### 3.1 哪些读走短路径

目标落在两棵私有目录（`.wakeflow-local`、`.wakeflow-active`）里的读。foundation 之外的读调用点按表数是 194 处，142 处在这里，约四分之三；`status` 的约 1,200 次 `open` 里，估计近九成是这里的 hook 记录文件与 hook 目录。

其余保持今天的读法：账本（记录树进 git，git 会改写；读者遇到半截文件是拒绝，不是当作不存在）、配置（Wakeflow 原子地写它，但没有任何东西拦着人、编辑器与 git 去改）、工作区根的混合文件、支持面、产品仓库与 pod 检出、工作区之外。账本要不要进短路径，等这一段量完再议。

私有目录里那几种不是原子写入的文件（1.1 节第 4 条）不需要另设例外，理由在 3.2 节的"退回"一条。

### 3.2 短路径是什么

调用数的对照（d 与 n 是路径段数，e 是目录项数）：

| 操作 | 现在 | 之后 |
| --- | --- | --- |
| 读一个文件 | 17 + 8d + k（五段深、一次读完是 58 次） | 6 次：`realpath`、打开、`fstat`、读、`fstat`、关 |
| 列目录 | 22 + 8d + 4e | 6 + e 次：`realpath`、目录的 `lstat`、打开、逐项读、关、目录的 `lstat`，每项一次 `lstat` |
| 检查一个路径是否存在 | 6 + 4n | 2 次 |
| 打开父目录准备写 | 新建过程中复核 19 遍，替换 10 遍（未逐条核实） | 打开时一遍，发布之前一遍 |

确切的调用序列由原型定；下面这张"保留与拿掉"才是约定。

- **保留的。** `realpath` 的结果必须等于请求的路径：路径上任何一级是软链接，或者名字只是大小写、Unicode 归一化不同的别名，都在这里被发现（在这台机器的 Node 24 上试过；请求 Schema 里有几种调用方给的名字允许大小写混用，所以这一步不能省）。最后一段是软链接的不打开。不是普通文件的、超过上限的不读。调用方给了预期节点的，与第一次 `fstat` 比较。读前读后句柄上的节点不一样（包括变长了），不算读成功。返回值里的节点快照仍是 12 个字段，上层各存储自己对属主、权限位、链接数的核对与"比较后替换"的预期值都不用改。列目录时目录自己的节点读前读后要一样（修改时间在内），所以列的过程中有人增删会被发现。
- **退回。** 上面任何一步不对，就整个按今天的读法再读一遍，由它给结论。所以最终的拒绝原因与今天相同；但这是一次隐含的重试——文件正被就地改写时，今天这一次直接报 `source-changed`，之后是再读一遍，那时写完了就成功。目标不存在的情况不退回：确认父目录的规范路径之后直接报不存在。
- **拿掉的。** 读之前与读之后各把路径从根逐段走一遍，并逐级确认还是同一个目录；打开之后把句柄与路径上的节点对一次；打开之前先看一眼类型（改成不阻塞地打开之后再看）；每次读都确认根没有被换（改成打开根时一次）；列目录时列两遍、每项 `lstat` 两遍。
- **调用方不改。** 短路径放在现有原语内部。有 8 个测试文件挂在 `inspectExistingResource` 上，其中几条并发用例的停顿点落在私有目录里的锁文件上；读锁走短路径之后那个方法不再被调用，这几条的停顿点要换到变更接缝或一个新的读接缝上，否则会挂住。

ADR-0032 决定 7 说"单个文件的权限位或链接数被改，不再由读它的工具当场拒绝"，这在 1.4.1 里还不会发生：那些核对在上层各存储里，用的是读返回的节点快照，不花路径调用，随 1.4.2 的端口一起收。

### 3.3 目标怎么知道自己在私有区域里

- **声明区域（建议）。** 命令外壳与 hook 观察器在开头按规范路径声明"这两个目录是这个工作区的私有区域"。声明不是授信，只是说私有区域的规矩在这里适用，按路径去重、进程内一直有效；一个根对象第一次碰到某个区域时当场核对区域根（真实目录、属主是当前用户、权限位 0700），结论只记在这个根对象上，所以每条命令都重新核对。经工作区根按相对路径读、与在区域里另开的根，都按目标的绝对路径判定。没有声明过的进程（比如单独打开根的调用者角色门）照今天的路径走。
- **显式选项。** 工作区根带上私有前缀，区域里另开的根逐处传选项。要改每个打开点，而且测试里替换 `RootedDirectory.open` 的那层包装今天会把不认识的选项整个丢掉，得先改成合并。

第 2 段开头先做"声明区域"的原型，用 `wf metrics storage` 量 `status`、`verify`、一次记结局；数字不对或者做不干净，再试另一种。

### 3.4 `verify` 补的检测

私有目录的权限普查有两处漏：不查链接数；普查本身不可用或抛错时不出任何代码，那一道门是通过的。第 2 段补这两处。另外两处（账本布局门只覆盖三个固定的容器；读路径上没有任何地方查工作区根的属主）随 1.4.2。

### 3.5 量过再定的三件

- **每次读的那一次 `realpath`。** 原型里量它占多少。占比大的话，对名字完全由 Wakeflow 生成的那几类（小写十六进制的标识）再议要不要省。
- **配置快照的位置探测。** 每读一次配置快照，都从文件系统的根逐段 `lstat` 走到每个已配置的区域根，并各打开一次；一次公共调用里会读好几次。占比大就让一次公共调用里只探一次。
- **`status` 的读集合。** 它把每个宿主留着的每一条 hook 记录全文读一遍，没有按时间筛；记录按标识的前两位分片，平均每个分片目录 1.17 条；超过 30 天的要等下一次 hook 写入才被修剪。短路径把每个文件的代价降下来之后，如果 `status` 仍然超过设计值，再按日期目录收窄读集合。这改的是观察的逻辑，不是存储原语，所以不预先放进清单。

### 3.6 要改写的测试

foundation 里钉住读复核的用例，调研数到 22 条。表里标出会受影响的有 4 条（`rooted-directory.test.ts` 与 `rooted-exact-resource-handle.test.ts` 各 2 条），是"根在操作中途被换掉"与"逐段确认还是同一个目录"这一类；断言软链接祖先与别名被拒的用例因为"退回"应当照旧通过。哪几条真的要改，以原型为准。foundation 之上是 3.2 节说的那几条并发用例的停顿点。新增：合格的区域里读、列目录、检查存在各自的调用次数；区域根不合格（权限位放宽、属主不对、是软链接）时走完整路径；别名与软链接祖先照旧被拒。

### 3.7 不再有的保证

| 拿掉或简化的 | 不再有的保证（一句话） | 现场记录 |
| --- | --- | --- |
| 读前读后各走一遍路径 | 读的过程中文件被原子地换掉时，这一次读返回完整的旧文件，不再报 `source-changed`；紧接着的比较后替换会在写的时候拒绝。只读命令与 hook 观察器都不进操作作用域，所以这种并发确实会有。 | 无。 |
| 逐级确认中间目录还是同一个；打开之后把句柄与路径上的节点对一次 | 私有区域里某一级中间目录在 `realpath` 与打开之间被换成另一个目录时，这次读不再发现，读到的是换上来的那个目录里同名的文件。Wakeflow 自己只会把同一个标识的目录换上来（发布、恢复）；别的换法属于同一用户的其他进程，按 ADR-0020 只检测不防护。 | 无。 |
| 每次读都确认根没有被换 | 工作区的私有目录在一次操作中途被整个换掉时，这次操作里后面的读不再当场发现。 | 无。 |
| 列目录时列两遍、每项看两遍 | 列的过程中某一项被就地改写（不是增删）时，拿到的是它某一刻的样子。增删仍然会被发现并重列一遍；今天这种并发直接让 `status` 把 hook 通道报成不可用，之后多数情况下重列就过了。 | 无。 |
| 就地改写时这一次直接拒绝 | 改成再读一遍；那时写完了就成功。 | 无。 |

### 3.8 度量的设计值

按补了目录遍历之后的口径，1.4.0 的基线是：一次 `status` 82,135 次文件系统调用（其中核对路径 65,851 次、`open` 1,219 次、`opendir` 与 `readdir` 1,044 次、逐项读目录 3,342 次），墙钟 1.85 到 2.07 秒。设计值：不超过 20,000 次、不超过 0.6 秒。`verify`、窗口 `inspect` 同比例；写入类调用的路径核对降到原来的五分之一以下。实数以原型为准。
