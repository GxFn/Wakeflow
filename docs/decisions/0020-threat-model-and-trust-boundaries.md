# ADR-0020 威胁模型与信任边界

> 状态：`accepted`
> 日期：2026-10-11
> 裁决日期：2026-10-18（用户：按技术债务复审的建议接受三类对手与可接受残余的定义；F1/F2/F5 的剩余控制与 K4 角色子集排在第一轮现场测试之后）
> 来源：2026-10-07 技术债务深挖簇 C 与未决问题登记 F 主题：安全取舍散落在代码注释里各自决定，没有一处写下对手、资产与边界（F7）；Q5（威胁模型范围）待裁决；批次 3 要求先写本记录，再做不依赖裁决的控制。
> 相关：ADR-0017（运行证据主体与窗口运行身份）、ADR-0018（当前基线）、§13.150 隐私与准入复验（回调标为不可信、凭证扫描）、§13.165–§13.167 技术债务批次 0–2。登记项 F1、F2、F4、F5、K4、E2 以本记录为对照。

## 背景

Wakeflow 让多个 Agent 窗口在同一台机器、同一个操作系统用户下分工：Controller 推进 Demand，Design 发布需求包，产品窗口在仓库里实现，Test 窗口在真实环境里验证。它们共享同一份文件系统权限，而其中的产品与 Test 窗口会读取并执行不受信任的仓库内容。到本记录为止，各文件各自假设了不同的模型：`rooted-directory.ts` 以"受信任的单用户工作区"为前提，`hook-observations.ts` 把记录称作"私有权威"，调用者身份交给技能文本约束，而产品窗口又在处理不受信任的内容。审查者因此无法判断 F 主题的各项究竟是缺陷还是已接受的取舍。

当前实现的相关事实（2026-10-11）：

- 所有窗口以同一操作系统用户运行；Claude Code 上放置不在工作区根的窗口以 `--add-dir <工作区根>` 与缺省 `auto` 权限模式启动。
- 每个 Wakeflow 管理的根的 `.claude/settings.json` 放行整个插件 MCP 服务器（通配规则），而不是该角色实际使用的工具。
- MCP 工具请求只带工作区根，没有调用者或窗口身份；Controller 专属动作（评审决定、完成、取消、pod 变更）只受技能文本约束（§13.140 已从产品窗口的 cwd 复现）。
- hook 观察记录是 0600 的普通 JSON 文件，没有签名或链；它证明"宿主在那个时刻观察到了什么"，不证明文件此后未被同用户进程改动。
- Claude Code 的 tmux 助手是工作区运行时根里的普通文件，Controller 以精确到路径的允许规则免提示运行它；verify 的 `host-settings-assets` 门事后核对字节，运行前没有核对。
- 回调文本已标为不可信数据、Controller 指令只读 inspect（§13.150）；凭证扫描守住进入 git 跟踪 ledger 的证据（§13.150、§13.161、§13.165）；事故记录不含消息与路径（§13.166）。

## 决定（Q5 裁决：2026-10-18 接受）

1. **三类对手与各自的立场。**
   - **A 类：诚实但会出错的 Agent 与宿主。** 中断、重复、误读、幻觉、过期视图。这是运行时必须防住的对手：幂等键、fence、CAS、从证据派生处置、精确正文准入、三态观察、事故记录。现有控制以此为设计对手，继续作为主要防线。
   - **B 类：被仓库内容牵引的产品或 Test Agent。** 它在同一用户权限下行动，可能把不受信任内容里的指令当作任务执行。Wakeflow 的承诺是**降低误用、保持可见、不替用户授权**：允许规则只放行该角色使用的工具（F2），回调与报告永远是引用数据而不是授权（F3），Controller 在签发投递许可前由服务器核对助手字节（F1），遗留的指令块与宽泛允许规则被点名（F4），自述证据与宿主观察分级标明（E2）。Wakeflow **不承诺**同用户进程级的隔离：用户在宿主上选择的权限模式与 `--add-dir` 范围是最终边界。
   - **C 类：同一操作系统用户的其他进程，或用户本人直接改文件。** 不在防护范围之内。Wakeflow 只做检测与报告（verify 门、三态观察、事故记录、准入拒绝），不引入签名、HMAC 或链式摘要。F5 据此归为"检测而非防护"，直到 Q5 另有裁决。
2. **证据分级写进合同与文本。** 三个等级：`host-observed`（hook 记录：宿主观察所得，同用户进程可改）、`agent-reported`（`host-send-return`、`agent-declaration`：Agent 自述，Wakeflow 只记摘要）、`controller-judged`（评审决定：Controller 的判断）。status 与评审投影显示投递结局的 `evidenceKind`；任何文本不得把 `agent-reported` 称作宿主证据，也不得把 `host-observed` 称作防篡改。
3. **状态转移的归属表。** Controller：全部工具；Design：`wakeflow_inspect_board`、`wakeflow_publish_requirement`、`wakeflow_status`；产品窗口：`wakeflow_import_target_result`、`wakeflow_status`；Test：`wakeflow_import_target_result`、`wakeflow_record_evidence`、`wakeflow_status`。这张表是技能文本、Claude 允许规则与未来运行时调用者校验的共同来源；允许规则按它收窄（F2 第一步），运行时按窗口身份拒绝越权调用（角色令牌或进程祖先匹配）待 Q5 裁决。
4. **永远不进入 git 跟踪 ledger 的内容。** 凭证（扫描阻断归档）、绝对路径与机器标识、未典型化的会话或线程标识、宿主通知与消息正文。本条已有实现，列在此处作为资产清单的一部分。
5. **已接受的残余风险（到 Q5 裁决为止）。** 同用户进程可以改写 hook 记录、绑定、声明与事件流；产品窗口可以写工作区根（含助手、配置与活动 Demand 文件）；窗口可以绕过助手直接驱动 tmux；Codex 的落地证据是自述。这些都只能被检测或降低，不能被阻止。
6. **Q5 的建议裁决。** 接受 B 类为设计对手、C 类为检测对象；批次 3 先做不依赖裁决的四项（F1、F2、F4、E2）；裁决后再进入 `--add-dir` 收窄、角色令牌或进程祖先校验、hook 记录链式摘要、按角色暴露工具子集（K4）。若用户裁决 C 类也要防，则 hook 记录需要存放在 Agent 不可写位置的密钥与链，这是另一份记录。

## 实施

批次 3 落地第 2、3 条里不依赖裁决的部分：服务器侧的助手字节核对进入 `wakeflow_prepare_delivery` 的前置条件并由 status 展示（F1）；Claude 的允许规则按归属表收窄，归属表作为 contracts 词汇由测试对照技能文本与工具目录（F2）；遗留残留的只读观察进入 status 与 verify，fresh-initialize 对工作区根的遗留标记拒绝（F4）；`host-send-return` 的摘要定义为发送返回值规范 JSON 的 sha256，由 Wakeflow 计算，status 与评审投影显示 `evidenceKind`，文本标明自述（E2）。

## 验证边界

单元与门测试覆盖规则表、核对、观察与投影；真实宿主上允许规则收窄后的权限提示行为、助手被改写后的拒绝路径与 Codex 发送返回的形状都未在现场验证，记为未执行。本记录不宣称任何抗篡改能力。

## 2026-11-10 补记：决定 6 里排在第一轮现场之后的两项控制（1.3.0 批 3，gate-log §13.240）

第一轮现场（§13.185）与正式工作区的首个 Demand（§13.232）之后，这两项到期并落地。三类对手的划分与承诺不变——仍是"降低误用、保持可见、不替用户授权"，不是隔离。

- **运行时调用者校验（决定 3）用服务进程的工作目录，不用角色令牌或进程祖先。** 每个窗口的会话在它的执行根里启动，宿主把该会话的 MCP 服务进程起在同一个目录。公共入口把这个目录对到配置里的窗口：恰好是某一种角色的窗口的执行根时，归属表之外的工具以 `tool-not-for-role` 拒绝。没有选令牌：同一用户下没有哪个位置是 B 类对手读不到的，令牌只是多一份要保管的东西；没有选进程祖先：它依赖宿主的进程结构，两个宿主、两种传输各不相同。工作目录不需要任何新状态，认不出时不收窄，所以它不会挡住维护者工具、引导会话或 Codex（Codex 的窗口都从项目根启动，这道门在那里不起作用）。它防的是"被仓库内容牵着走的 Agent 顺手调了 Controller 的工具"，换个目录另起一个服务就绕过去了——那已经是 C 类。
- **受管路径的写拒绝（决定 5 的残余收窄一步）。** Controller 之外每个角色的会话带 deny 规则启动，指向 `.wakeflow-local`、`.wakeflow-active`、配置文件、根上的两份 Claude settings 与账本。决定 5 里"产品窗口可以写工作区根（含助手、配置与活动 Demand 文件）"因此改为：宿主的编辑工具与它认得的文件命令写不了这些路径，任意子进程仍然可以。`--add-dir` 的范围没有收窄：这些窗口要读任务包与账本。Design 一并带规则，它与产品、Test 同样挂着工作区根、同样读仓库内容，而自己只写 Design 面的草稿。
- **验证边界。** 规则语法在 Claude Code 2.1.303 上以 print 模式探明（目录、单文件、带空格的路径；Write 与 Bash 重定向被拒）；服务进程的工作目录等于会话启动目录是本机观察所得，宿主文档没有写。真实窗口里的两项核对归 1.3.0 终验；桌面接管之后规则是否保留未核对（open-items X30）。Codex 没有对应的 deny 载体，也认不出角色：这两项控制目前只在 Claude Code 上有效。

## 2026-11-15 补记：只重装私有资产的 reconcile 由 Controller 应用（用户裁决，gate-log §13.247）

终验的 tmux 一轮里，插件更新之后的 reconcile 只有两步——把工作区私有运行时目录里的状态栏脚本与 tmux 助手换成新制品里的字节——预览却把应用交给用户确认。同一类确认此前已经去掉过一次（私有模式收敛，§13.226）；剩下的这一次，用户在每次更新之后都要回答，而它不碰用户的任何文件。

**裁决：这样的计划由 Controller 自己应用。** 判断是结构上的：计划的每一步都是宿主入口声明为"私有资产"的操作（Claude Code：`statusline-asset`、`tmux-asset`、`desktop-asset`）。计划里只要还有一步别的——共享步、`settings.json` 的允许规则、`settings.local.json` 的状态栏条目——整份计划仍由用户确认。

**与威胁模型的关系。** 助手带着一条预先批准的允许规则，替换它等于替换一段免提示运行的代码，所以这不是一个无关紧要的确认。它成立的理由有三条：换上的字节来自用户自己安装或更新的插件制品，服务端按制品里的摘要核对，不来自工作区、仓库或模型的输入；目标路径在 Wakeflow 的私有目录里，非 Controller 窗口对它有写拒绝规则（2026-11-10 补记，决定 5 的残余收窄）；另一条路——不换——意味着窗口继续由上一版助手启动，新版本的控制（写拒绝规则本身）进不来，终验正是这样查出问题的（open-items Z1）。预览与应用仍是两步，计划摘要照旧比对；Controller 应用之后要说明重装了什么。

**没有改变的。** 这不是隔离：同一用户的进程仍然能改写这些文件（决定 5 的残余风险）。首次初始化、reconfigure、detach 以及任何触及用户文件的 reconcile，确认点不变。

## 2026-11-16 补记：写拒绝规则在桌面传输下不生效，拦截改用 hook（用户裁决，gate-log §13.249）

2026-11-10 的补记把"规则能否跨过应用的接管"留作未核对。终验的桌面一轮核对了：接管之后的产品窗口往 `.wakeflow-local` 写文件成功。规则是启动参数，应用接管时用自己的参数重起会话。

- **这一版**只把话说实：README、技能文本与桌面助手的输出都写明桌面传输下没有这些规则，只有指令文件一道约束。tmux 传输下规则照旧生效（终验实测被宿主拒绝）。
- **1.3.1**：在插件的工具调用 hook 里按窗口角色拒绝对受管路径的写。它不依赖窗口是怎么启动的，两种传输、续接与接管之后都是同一套；仍然不是隔离（决定 5 的残余风险不变）。

## 2026-11-16 补记（二）：写守卫 hook 的做法与边界（1.3.1，gate-log §13.251）

上一条补记定了方向，这里记下做成之后是什么。

- **载体。** 插件的 `hooks/hooks.json` 多一个事件：`PreToolUse`，matcher 是编辑工具的精确名字列表（`Edit|Write|MultiEdit|NotebookEdit`），同步、5 秒，启动的还是 `hooks/observe.mjs`，argv 以 `--wakeflow-write-guard-v1` 开头。进程入口按这个标记把调用交给 `src/entrypoints/wakeflow-hook-write-guard.ts`；观察这一种调用不变（不写 stdout、不控制）。没有加第二个 launcher：制品的文件布局不动。
- **判定。** 三件事同时成立才拒绝：这个会话在某个匹配的工作区里绑定着窗口；绑定的每个窗口在配置里都是 Controller 之外的已知角色；工具要写的路径落在那个工作区的受管路径里。受管路径与角色同决定 6 的启动规则是一张表（宿主层 `CLAUDE_CODE_MANAGED_WRITE_DENY`；守卫的闭包不含宿主层，表在入口里是字面量，测试核对两处相等），账本根读配置。工作区的定位与绑定的读取同观察器共用一份（`wakeflow-hook-workspaces.ts`）：记录写进哪个工作区，守卫就在哪个工作区生效。
- **拿不准就放行。** 没有绑定的会话、Controller、认不出的角色、读不出的配置、不合形状或超限的 stdin、任何内部故障、hook 超时——都放行。理由：这一层挡的是误改，不是对手；一个出错的守卫如果挡住编辑，受害的是每一个装了插件的会话（包括与 Wakeflow 无关的）。所以不用宿主的 `onFailure: "block"`。
- **注（2026-11-19，1.4.1）：守卫的处理器显式带 `onFailure: "continue"`。** 上一条的"hook 超时放行"在实验性的 Code Mode（2.1.323 起，缺省关）里不成立。`onFailure` 未设时：2.1.323 到 2.1.328 上，没给出决定的 `PreToolUse` hook（起不来、被杀、意外退出码、超时）都让那次调用被拒；2.1.329 的更新日志把"出错"改成与普通会话一样放行（"a PreToolUse hook that errors no longer refuses a script's tool call"），Code Mode 文档（"Tool call refused by a hook"）写明超时（`the hook did not finish`）仍被拒，要放行就设 `"onFailure": "continue"`。hooks 参考给这个键 `"continue"` 与 `"block"` 两个值，2.1.295 起可用。加上之后两种模式、各个版本下守卫的故障与超时都放行。更早的宿主没有 Code Mode，hooks 文档没写它们怎么处置未知键，这一点没有一手文档可引；能找到的都指向忽略：宿主更新日志 2.1.274（修掉插件 hooks 文件顶层 `$schema` 的 "unknown key" 提示，可见此前是提示而不是拒收）与 2.1.197、2.1.229、2.1.267 上的第三方报告（有的版本提示一句），所以加这个键不会让旧宿主丢掉观察 hook。本机 2.1.325 与 2.1.328 的 `claude plugin validate` 接受 `"continue"`、对不认识的处理器键不报；但认识这个键的宿主遇到非法取值会让 `PreToolUse` 所在的整份 hooks 不生效，取值只能是那两个之一。
- **拒绝的形式。** 退出码 0，stdout 一行 `hookSpecificOutput.permissionDecision: "deny"` 与一段给那个窗口里 agent 的说明（不含路径；要它别换工具或 shell 重试，需要改那里就在结果里说）。宿主文档里这是 `PreToolUse` 的拒绝形式之一；hook 的拒绝先于 allow 规则与权限模式：宿主的 hooks 指南（"Hooks and permission modes"）写明 `PreToolUse` hook 在任何权限模式的检查之前触发，返回 `permissionDecision: "deny"` 的 hook 在每一种权限模式下都拦住这次调用，包括 `bypassPermissions`、`--dangerously-skip-permissions` 与 `dontAsk`；真实宿主上只试过 `acceptEdits` 与 `auto`。一处保留：没有受管设置、`managed-mcp.json` 或 Team/Enterprise 登录的环境里（用 API key 或长期 `CLAUDE_CODE_OAUTH_TOKEN` 运行的会话也算没有那种登录），用户自己装的 mod 可以放行被 `PreToolUse` hook 拒绝的调用（同一节的说明；权限文档"Precedence among rules, hooks, and mods"）；plan 模式下 mod 只能放行只读的调用，文件编辑不在内。
- **它不做什么。** 不看 Bash：命令文本判不准写的是哪里。tmux 传输下启动规则仍然带着（宿主认得的 Bash 文件命令由规则拦）；桌面传输下 shell 写这些路径没有任何拦截。不写观察记录，不记"拒绝过一次"——那是新的记录种类，没有消费者之前不加。Codex 的片段不接这个事件。
- **代价。** 插件启用的每个会话里，每次编辑工具调用多一次 `node` 启动，本机实测约 80 毫秒（空 `node` 约 30 毫秒）。
- **核实到哪里。** 宿主合同在真实宿主上核过一次：Claude Code 2.1.325，无头会话，`acceptEdits`，候选制品经 `--plugin-dir` 装入——绑定为产品窗口的会话写受管路径被拒（工具结果里是守卫的说明，文件没有出现），同一会话写自己的仓库、未绑定的会话写同一路径都成功。桌面 app 里的会话没有核过（要用户在场），登记在 open-items X30。

决定 5 的残余风险不变：以用户身份运行的进程写得了这些路径。
