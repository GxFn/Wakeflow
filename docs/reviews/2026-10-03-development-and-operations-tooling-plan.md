# Wakeflow 开发测试与运行工具规划

> 状态：`accepted`
> 基线提交：`04769897`
> 建立日期：2026-10-03
> 上位文档：[开发文档系统](../README.md)、[开发计划](../plan/typescript-reimplementation-plan.md)
> 范围：代码审查与工具规划；用户已确认继续实施，按批推进，不改变现行运行时合同。

实施入口与当前边界见[维护工具使用说明](../references/maintainer-tools.md)。第一批提供 verify、环境/制品 doctor 和耗时建议导出；第二批增加双产品 lab、生成 stdio readiness 场景、受控清理和固定故障回归选择；第三批增加项目聊天行动单/尝试记录/一致性核验、隐私命令模型及独立平台 CI 配置与报告校验。第四批增加固定单产品/双产品/worktree业务实验、资源封存保护和工作区doctor，并修复Node CLI重排导致真实派发不遵循耗时队列的问题。随后在单一外层项目完成10聊天的Codex main/worktree原生业务与清理，见[gate-log §13.158](../progress/consolidation-gate-log.md)。宿主自动关联、回调hook、现场故障包、其他模型和impact仍有未完成范围。下文中的初次审阅数字保持原始基线。

当前最值得投入的是三项能力：可追溯的验证执行记录、能区分安装与实际运行的只读诊断、可重复建立和回收的测试环境。在这些基础上增加故障复现与原生验收协助。暂不建设通用工作流平台、第二套 Controller 或大规模业务代码生成器。

先读第 3 节的场景与优先级，再读第 4 节的具体设计和第 7 节的实施顺序。第 2 节给出初次审阅的代码证据，第 8 节说明外部实践如何取舍。后续章节保留设计目标；已实现的 `wf` 命令、实际范围和验证记录以维护工具说明及开发日志为准。

## 1. 审阅范围和方法

本轮重点读取构建、安装检查、测试执行、夹具、MCP 边界、作用域、原生聊天启动说明、观察和发布检查的实际实现，并核对近期修复及真实场景记录。已有图谱的逐文件审阅记录用来定位关联模块，不把库存或历史审阅数量冒充本轮逐行审阅数量。

在基线提交上按文件枚举得到：360 份手写运行时 TypeScript、10 份 tooling TypeScript、95 份 JSON Schema 和 95 份生成 TypeScript；297 份测试相关 TypeScript 中有 264 份 `.test.ts`、25 份 `.fixture.ts`。根 `package.json` 有 22 个 npm 命令。仓库未跟踪 `.github` 工作流，不能据此推断外部没有其他 CI。

最近的完整门记录是 [gate-log §13.151](../progress/consolidation-gate-log.md)：1244 项通过、二十个端到端场景、双宿主制品 smoke 通过，测试阶段约 636.6 秒。该时间是一次机器和并发度为 6 的运行，不是通用性能基准。本轮没有重跑完整测试、安装插件或启动新的宿主会话。

以下判断是基于现有代码和现场记录的工程建议；新增工具的接口、优先级及验收条件均是提案。

近期故障说明了工具应解决什么：多次重启来自安装、hook 与进程身份混淆；测试目录和原生聊天创建曾与桌面项目归属混淆；四个边界缺陷分别来自诊断截断、释放责任、对象展示和词法白名单。前两类需要可观察、可重做的操作流程，后四类需要针对不变量的回归生成和故障实验。单纯再加一批 shell 别名无法解决这些根因。

## 3. 按场景和种类排序

P0 表示建议立即建设的最小基础；P1 表示在基础完成后补齐；P2 表示有明确重复需求后再做。成本为相对工程复杂度，未承诺工期。

| 场景 | 工具族与拟议入口 | 必要性及优先级 | 最小范围 | 成本 |
| --- | --- | --- | --- | --- |
| 日常修改、交接、复验 | 验证执行与回执 `wf verify` | P0；反复出现“哪个字节跑过哪些检查”追溯成本 | 复用现有门，记录输入身份、阶段和原始结果；输出结构化测试事件 | 中 |
| 插件安装、重启、故障求助 | 只读诊断 `wf doctor` | P0；直接减少重复重启和错误归因 | 开发环境、制品、安装、MCP、hook、工作区分域报告；脱敏导出 | 中 |
| 重现问题、建立新测试区 | 可丢弃实验环境 `wf lab` | P0；现有脚本最容易重复和误用的部分 | 合成多仓库环境、所有权清单、制品 stdio 会话、受控清理 | 中 |
| 锁、日志提交、隐私和恢复改动 | 故障与性质测试 `wf fault` | P1；防止同族问题靠偶然现场测试发现 | 固定回归矩阵，少量可缩减的随机序列及复现记录 | 中 |
| 新宿主版本、插件升级、发布前现场验收 | 原生验收协助 `wf live plan/verify` | P1；发布与支持范围判断必需 | 产出行动单并核对真实宿主回执；宿主动作仍由 Agent 执行 | 中到高 |
| 跨层改动、公共合同调整 | 变更影响检查 `wf impact` | P1；先服务开发，不削减最终门 | 来源、Schema、producer/consumer、测试和制品的建议清单 | 中 |
| 合并、候选制品、正式发布 | CI 与发布准备 | P1；仓库已有检查器，缺可复用执行与留存 | 复用验证回执、分平台运行、候选差异；发布动作分开授权 | 中 |
| 重复增加回归、需求文档草稿 | 小型脚手架 `wf scaffold` | P2；重复达到一定程度才值得固化 | 回归用例骨架、Design 草稿模板；不生成业务决定 | 低到中 |

这八行是能力分类，不是八个独立框架。建议只有一个轻量开发入口，底层复用现有 npm 命令与模块。诊断导出属于 doctor，运行证明属于 verify，环境与场景属于 lab，不再分别维护多套“报告平台”。

## 4. 具体设计

### 4.1 验证执行与可追溯回执

现有测试选择与排程应保留。优先扩展 `run-typescript-tests.ts`，增加基于 `TestsStream` 的 reporter 和一次运行的封闭结果格式。Node 官方明确提醒不要把面向人的 reporter 文本当稳定程序接口；Node 24.19 已支持自定义与多个 reporter。可以同时保留终端摘要、事件记录和 JUnit，无需替换测试框架。[Node 24.19 测试报告接口](https://nodejs.org/download/release/v24.19.0/docs/api/test.html#test-reporters)

拟议验证档位：

| 档位 | 执行内容 | 可以声称什么 |
| --- | --- | --- |
| `quick --files ...` | 当前已有的静态检查与明确选择的聚焦测试；输出选择依据 | 仅这些输入与测试通过 |
| `gate` | 现有 `npm test`，完整保留失败、取消、跳过和未完成状态 | 当前源码通过完整源码门 |
| `artifact` | `build:check` 与已核对制品的 smoke | 这些确切制品完成规定的非登录冒烟 |
| `native` | 消费 live 产生的宿主证据及声明的验收清单 | 仅该宿主、版本、场景和观察时刻的原生覆盖 |

`verify` 不应隐式重写 `plugins/` 以消除漂移；提交产物重建仍是明确的独立动作。默认调用现有命令的进程参数数组，不拼接用户文本形成 shell 命令。

每次回执至少记录：源码提交及脏树内容指纹、锁文件与运行器身份、Node/平台、开始结束时间、执行档位、选中的文件、并发度、阶段退出码、测试计数、完整性状态、候选 manifest 摘要、日志相对引用与摘要。工作开始和结束分别检查输入指纹；发生变化的结果保留为不可复用记录，不能给新字节背书。

回执是验证输出，不进入 Demand 事件权威，不授予任何 Controller 权限。进程被杀或缺少完成标记时只能表示中断；不能从日志里曾出现的 pass 数推断整门完成。整体 verdict 和每个检查的 pass/fail/unavailable 分开，缺少必需证据不会被算作成功。

耗时表从同一事件记录显式生成，保留测量环境和覆盖文件数；未知项继续沿用现有保守调度。先取得完整、可比较的数据，再决定调并发或拆慢文件，不能承诺减少某个未经测量的百分比。

验收：旧的 1244 项结果集合不减少；取消、非零退出和缺结尾记录不为绿；旧编译测试残留不进入选择；耗时记录覆盖当前 264 个文件或明确指出未测项；开发者无需解析终端文字即可核对验证身份。

### 4.2 只读诊断与安装激活核对

第一版面向有源码的维护者，扩展现有 `install:check` 和 MCP 客户端采集即可。普通安装用户暂时继续使用已有 status/verify；需要支持“无源码且 MCP 启动失败”的用户时，再增加单独的轻量诊断入口，不能让安装包反向依赖 `tooling/`。

环境部分先检查当前 Node/npm/Git、宿主可执行文件的存在和版本、工程引擎约束及路径解析差异；只读取必要信息，不输出环境变量值，也不自动安装运行时或更改宿主配置。

诊断应区分下列事实，不能压成一个版本号：

| 事实 | 证据来源 | 缺失时的结论 |
| --- | --- | --- |
| 源码与候选一致 | `build:check`、内容指纹 | 未验证候选 |
| 缓存文件完整 | `verifyArtifactAgainstManifest` | 缓存不完整或无法读取 |
| 宿主选择的安装 | 宿主正式清单或显式提供的选择信息 | 宿主选择未知 |
| 本次 MCP 运行身份 | 实际调用返回的 `runtime` | 进程身份不可验证 |
| hook 观察器身份 | 真实 hook 记录的生产者摘要 | 观察缺失或不可读取 |
| 角色聊天、项目和执行目录 | 创建回执、宿主回读、真实命令和 SessionStart | 按缺失维度分别报告 |

`artifactOnDisk: same` 不代表磁盘所有文件重新验过；新 SessionStart 不代表目标 MCP 或技能已重载；缓存存在不代表宿主正在选用它。doctor 自行启动的 stdio 探测进程只证明该新进程，不能证明既有聊天中的 MCP 身份；后者必须由对应会话的实际调用提供证据。所有比较应带观察时间和证据引用。宿主不提供持续的窗口到 MCP 关联时，仍输出 unavailable，不用 PID、cwd 或聊天标题凑出成功。

doctor 默认只读，只给下一步和所需证据；恢复仍调用已有 maintenance preview/apply/recover。缺少 hook 不直接解释成“未信任”，因为还可能是没有触发、输入不符或观察器失败。官方要求用户信任当前 hook 定义，安装和启用本身不完成信任，工具不应绕过这一机制。[OpenAI 插件打包与 hook 信任](https://developers.openai.com/plugins/build/plugins)

诊断包分为私有原始材料与可分享摘要。摘要采用字段允许列表、根目录别名和显式来源分类，默认不包含原始会话标识、整个 transcript、环境变量值、任意 stderr 或文件内容。现有隐私扫描作为补充检测，不能作为“已经证明没有秘密”的唯一门。该取舍与 OpenTelemetry 的最小采集原则一致，不要求现在部署 Collector。[OpenTelemetry 敏感数据处理](https://opentelemetry.io/docs/security/handling-sensitive-data/)

验收：能准确区分未安装、缓存损坏、宿主选择未知、MCP 仍旧版、hook 未观察、工作区状态阻塞；检查前后业务文件零变更；私有原始材料不进入分享包；不支持的宿主信息明确为未知。

### 4.3 可丢弃实验环境与制品场景

建议三个最小预设：单产品主流程、双产品独立 Test、产品 worktree pod。只支持当前格式的新环境，遵循 ADR-0018，不顺带引入旧文件结构迁移。

拟议流程为 `lab create`、`lab run`、`lab inspect`、`lab dispose --preview`。创建前要求明确的可丢弃根、目标为空且真实路径符合范围；生成外层 Workspace、合成产品仓库和 Design/Test 草稿。环境清单只记录本次创建资源和清理依据，不能替代 Wakeflow 配置或成为业务状态来源。

隔离合同应包含：唯一根、当前配置摘要、产品 Git HEAD、创建的分支/worktree、制品摘要、持久化档位和保留的证据。默认新环境，不复用活动业务区。失败保留复现材料；清理只处理明确归属本次实验的资源，遇到未知文件、链接越界、HEAD 漂移或未处置分支时停下并报告。禁止按目录前缀或年龄批量删除测试区。

复用 `createPreparedWorkspaceStore` 的权限和迁移检查理念，但不把 `tests/` 整体变成生产工具依赖。公共制品场景通过 SDK 和生成 MCP 入口构建业务状态；Node 测试特有生命周期仍在 `tests/support/`。可共享无测试运行器依赖的连接、清理和数据预设，不应让 `tooling` 导入整个 `.build/tests` 来假装有稳定 API。

特别分开两种持久化档位：功能夹具可沿用现有 `durability: none`；故障、崩溃和耐久性用例必须保留真实 fsync。档位写进回执，不能混算覆盖。

验收：相同预设在两个新根上可运行，产物不含另一根的私有路径；公开工具回读配置和结果；失败能保留最小复现；清理在越界、未知资源和用户修改条件下拒绝；不会生成侧栏子项目。

### 4.4 原生多窗口验收协助

这个工具应帮助执行和核对，不接管业务判断。`live plan` 输出一个有明确场景和预期的行动单；Agent 在当前宿主里调用已有工具，并保留实际返回；`live verify` 核对回执、目标观察、文件与结果。用户授权来自人类与宿主，行动单或回执自身不授予权限。

拟议场景分层：

| 层级 | 验收对象 | 不能替代的证据 |
| --- | --- | --- |
| 进程内 | 决定、聚合与错误合同 | 不能证明生成包可启动 |
| 生成 stdio 制品 | 入口、SDK、资源闭包、协议及合成工作区 | 不能证明真实宿主信任或项目归属 |
| 原生主工作区 | 外层项目、角色执行根、投递、回传及独立评审 | 不能替代产品 worktree pod |
| 原生异常与 worktree | 重启、含混发送、恢复、独立检出和关闭 | 不能自动外推到另一个 OS 或宿主版本 |

Codex 继续使用已有 profile 的 project/local 创建说明。独立终端脚本没有这组宿主聊天工具时，只能生成行动单或运行 stdio 级测试；不得偷偷改用 `codex exec`、projectless 会话或子目录项目。产品 worktree 与外层项目自己的 worktree 也必须分别核验。Claude 复用现有 helper，不重复建设会话管理器。

续跑时先对账：运行清单中的“已尝试发送”不是投递成功。回读已有创建和发送结果，重新查询 Wakeflow 状态；含混的 host effect 不自动重发。只在已有合同允许且身份、幂等参数与预期版本不变时重放 Wakeflow 自身命令。AWS 对重试副作用及调用者意图标识的讨论支持这个区分，但不能据此给本身不幂等的聊天发送增加自动重试。[AWS 幂等 API 与重试](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

私有执行清单可保存动作和观测引用，必须能从权威记录重新对账，不能拥有独立的 Demand 阶段。手工输入的回执只能标为 imported/unverified；真实宿主返回、用户 UI 确认和推断分别标注。没有宿主签名或完整关联时，不把本地 JSON 包装成强认证证明。

验收：创建回执缺失时不重复建聊天；同一场景中断后不会重复投递；原生、合成与人工确认来源可区分；权限和信任对话框不会被脚本代按；业务验收仍通过既有 review 决定完成；聊天保留或归档遵循本次授权范围。

### 4.5 故障矩阵与性质测试

首先收敛现有故障测试和近期缺陷，不以随机用例数量作为成果。固定回归每次 gate 执行，较大的生成试验另设有界档位，并记录原始失败。

| 测试族 | 首批样本 | 不变量 |
| --- | --- | --- |
| 许可生命周期 | 读者退出、latch 释放失败、排空中止、未知文件替换 | 未取得有效许可不执行操作；清理责任不丢失；不删除未知所有者文件 |
| 追加与恢复 | 写入/rename/fsync 边界终止、损坏候选、重复 recover | 有效提交可重放；未知残留不被猜测修复；重复恢复不产生第二个业务效果 |
| 证据与隐私 | ANSI、opaque、路径规范化、UUID 前缀、诊断容量边界 | 披露判断不依赖展示截断；凭证确认不能放行；保留原始 payload 字节 |
| 投递与回调 | accepted、failed-before-send、indeterminate、重复代际、非空 Git 对象 | 不把发送尝试当落地；不重复含混发送；身份展示与已存对象一致 |
| 公共错误边界 | 截断、CRLF、BOM、符号链接、文件/目录替换；可控系统错误 | 返回稳定且脱敏的错误，记录实际副作用；零写只适用于声明零写的入口或阶段 |

不得对所有 apply 故障一律断言零写，因为某些失败依法留下可恢复 journal 或已提交事件。预期必须由各 owner 的发布边界决定，并验证其后恢复。

优先在测试进程封装已有 `t.mock.method` 故障点和 IPC 检查点，真实子进程负责崩溃；不新增可从公共 MCP 请求开启的故障开关。EACCES 之类注入错误分类的通过，也不等于真实 OS 权限场景已验收。

适合引入 fast-check 的位置是纯隐私文本、边界组合和小型命令序列。保留 seed、path、replayPath 及收缩后的样本，再固化为确定性回归。独立模型只表达不变量，不复制生产归约器；异步 scheduler 的覆盖也不能替代真实进程/文件系统竞争。[fast-check 模型测试与复现](https://fast-check.dev/docs/advanced/model-based-testing/)

验收：近期四类缺陷可由固定样本稳定发现；失败能用记录的输入复现；至少有真实进程和文件系统层与生成试验相互校验；自动重试不能把首次失败洗成绿色；测试结束无未知后台进程或越界残留。

### 4.6 变更影响检查与小型脚手架

`impact` 输入为 Git diff 或明确路径，输出受影响的源码 owner、Schema/生成文件、公共登记、提示词/技能、测试、双制品和文档提示。复用现有 SWC/dependency-cruiser；当前架构工具已因 TypeScript 版本边界选择 SWC，不建议在这里另引一套未经验证的编译器解析路径。

静态图只证明引用关系，不证明副作用和完整测试覆盖。动态宿主装配、Schema `$ref`、agent-text 占位符和共享底层变更必须显式扩展影响范围；无法解释时回退到全门。quick 的选择清单只是开发建议，不能把未选中的测试说成通过。

`scaffold regression` 只生成测试名、夹具选择、行为前提、应观察证据、错误路径和清理骨架；生成内容不能自动通过。Design 的需求/落地模板可从现有章节词汇派生，但不得填写用户确认、发明验收锚点或直接发布。

暂不做通用 capability CRUD 生成器。不同切片的状态、权威、锁序和恢复语义有真实差异，大量自动生成 service/decide 会把最需要审查的决定藏进模板。新的公共工具仍应人工明确生产者、消费者及合同。

验收：已知跨切片变更能列出相关消费者；删除、重命名和动态装配不出现空清单绿灯；脚手架不会触碰 `src/contracts/generated/` 或 `plugins/`；可以逐文件预览生成差异。

### 4.7 CI 和发布准备

CI 优先调用同一个 verify 入口，保留统一回执。首批建立平台分开的结果清单，避免把一台 macOS 的通过泛化到其他平台；Windows 先明确可运行的合同/纯函数范围和文件系统限制，不能用大量 skip 宣称完整支持。

建议把开发 PR 验证、完整源码门、制品 smoke、图谱检查和人工触发的原生验收分开。图谱继续保持独立 package；可以由 CI 分别调用，不把它接进运行时依赖或根 npm workspace。PR 的旧纯验证可取消，操作真实会话的执行不可直接套用同一取消策略。[GitHub Actions 并发语义](https://docs.github.com/en/actions/concepts/workflows-and-actions/concurrency)

只上传明确允许的测试摘要和制品；输出摘要与内部 manifest 摘要都要保存。GitHub 的上传/下载摘要校验在不匹配时可能只是告警，Wakeflow 仍须执行自己的硬失败完整性检查。[GitHub 工作流产物](https://docs.github.com/en/actions/tutorials/store-and-share-data) 第三方 Action 固定完整提交身份，具体版本在实施时核实。[GitHub Action 固定规则](https://docs.github.com/en/actions/reference/security/secure-use)

发布准备可以产出版本源差异、重建步骤和未满足的前提。保留唯一版本输入和严格 `release:check`，不把 PR 的 detached HEAD 或未打 tag 状态包装成发布通过；版本修改、重建、提交、推送、tag、发布和缓存刷新仍是不同动作。

借鉴 SLSA 把构建输入和本次执行结果分开的记录方式：源码身份、依赖、参数、构建者/工具链、输出制品分别记录。第一版只是本地来源回执，不声称已签名、达到某 SLSA 等级或抵抗同用户篡改。[SLSA 构建来源规范](https://slsa.dev/spec/v1.2/build-provenance)

验收：无宿主登录仍可执行源码与制品门；平台缺项明确列出；候选摘要与最终验证对象一致；CI 不携带真实测试区私有数据；普通验证不会触发发布或安装。

## 5. 代码归属与共享方式

以下目录是建议落点，不是已存在的实现：

| 建议落点 | 职责和依赖限制 |
| --- | --- |
| `tooling/cli.ts` | 小型命令分发；委托现有命令或导出模块，不解释 Demand 状态 |
| `tooling/testing/` | 扩展现有测试入口，增加事件 reporter、验证回执、MCP 会话辅助和耗时更新 |
| `tooling/diagnostics/` | 维护者只读诊断、证据分类与脱敏导出 |
| `tooling/lab/` | 环境归属、合成场景、制品进程管理和清理计划 |
| `tooling/inspection/` | AST/Schema/目录的派生影响报告，复用当前解析器 |
| `tooling/release/` | 复用现有一致性检查，增加明确的候选准备能力 |
| `tests/support/` | Node 测试生命周期、故障点及与正式回归的适配 |
| `assets/testing/` | 如需跨 CLI 与测试复用，仅存可移植合成输入；不存现场权威或私有标识 |

`tooling/tsconfig.json` 当前是独立编译项目，`tests/tsconfig.json` 已引用 tooling。共享代码优先保持不依赖 `node:test` 与业务测试文件；不要让 tooling 反向导入 `.build/tests`，也不要通过动态导入绕过依赖方向。需要新的项目引用时应明确检查环，而不是扩宽整个编译根。

生产宿主行为仍属于 `src/hosts/<host>/`。实验台消费现有宿主 profile 给出的意图；不能把新的 Codex/Claude 业务分支散落在通用 CLI 中。未来如要随插件附送诊断入口，其运行时代码及共享校验必须进入合适的 `src/` 层并走生成闭包，禁止运行时引用 tooling。图谱检查器继续独立维护。

首期不增加公共 MCP 工具数量。已有二十个工具及其语义继续作为运行入口；开发辅助通过仓库命令提供。需要向普通用户暴露的新诊断合同，应另行说明真实生产者、消费者和输出边界。

## 6. 统一输出和失败处理

所有工具共用少量结果字段：输入身份、执行范围、观测事实、各检查结果、整体结果、证据引用和下一步。业务拒绝、工具故障、环境不可用和运行中断分开；保留底层错误码，不用一个“失败”遮住原因。

建议将可复用结果存入被忽略的运行目录。开发报告、实验清单和诊断包是可丢弃观测输出；它们可以帮助定位，但不能用来直接修改 ledger、claim、binding 或批准投递。恢复方向始终从 Wakeflow 的 status、inspect 和已有事务协议重新求得。

报告可以带内容摘要，但本地摘要只证明字节相同，不证明是谁执行的。需要强来源证明时，必须引入宿主或受控 CI 的实际信任链；不通过多加一个 `verified: true` 字段解决。

建议先固定可测试的退出约定：成功返回 0；检查失败为非零；运行不可验证和中断有独立标记及原始退出信息。具体数值可以在 CLI 实施时统一，但不得把 unavailable 或未完成的 gate 映射成成功。

## 7. 实施批次与完成条件

| 批次 | 交付内容 | 完成条件 | 后续依赖 |
| --- | --- | --- | --- |
| 第一批 | verify 回执、Node reporter、doctor 的环境/制品核对 | 同一运行的输入、退出、测试结果及制品可追溯；能演示“安装成功但运行仍旧版”的分域报告 | 提供后续所有工具的记录格式 |
| 第二批 | lab 最小双产品环境、stdio 场景、受控清理；收敛固定故障样本 | 新根可重复复现问题，失败保留证据，清理拒绝越界；合成证据有明确标签 | 为原生验收和扩大故障试验提供稳定输入 |
| 第三批 | live 行动单与核验、定向模型测试、CI 接入 | 中断不重复宿主动作；平台与权限差异可见；根门和制品门无需登录 | 形成日常开发与发布前验收闭环 |
| 按实际收益追加 | impact、少量 scaffold、版本准备和更细性能采集 | 确有重复成本，且可以说明少维护了哪些手工步骤 | 不以工具数量作为完成指标 |

每批都先交付一个端到端的小案例，而不是先抽象一个通用平台。新增工具本身也要测未知输入、子进程失败、取消、输出不完整和清理责任。影响运行时或产物的变更继续执行现有重建、完整门与 smoke；工具不能给自己开一个较弱的替代门。

建议记录的收益指标：复现时是否还需要临时拼脚本；是否能直接回答“这些字节经过哪些检查”；安装错位是否可定位到具体域；失败样本是否能稳定重放；清理是否只涉及本次资源。性能收益在取得基线后再给目标，不设没有测量依据的加速承诺。

## 8. 业界方案的取舍

| 方案 | 本项目采用的部分 | 当前不采用的部分 |
| --- | --- | --- |
| Node 内置测试运行器 | 事件 reporter、多输出、现有进程隔离和显式并发 | 为报告能力迁移到 Jest/Vitest；直接解析 spec 文本 |
| [MCP Inspector](https://modelcontextprotocol.io/docs/2026-07-28/tools/inspector) | 维护者交互调试、人工复核 tools/list 与 tools/call；实施时锁定兼容版本 | 用 Inspector 替代业务验收，或在 CI 临时下载不固定版本；自动回归优先复用现有官方 SDK |
| fast-check | 小模型、边界数据、命令序列收缩与可复现输入 | 复制生产 reducer、随机跑大量真实会话、用 Promise 调度替代 OS 崩溃证据 |
| SLSA 来源模型 | 输入、依赖、执行、产物明确分开 | 在没有可信构建者或签名时宣称供应链等级 |
| GitHub Actions | 复用本地门、分平台结果、受控产物留存 | 自动更改生产工作区、将原生会话验证与无登录 CI 混成一项 |
| OpenTelemetry | 先采用最小采集与关联原则；必要时增加低开销诊断点 | 现在就建设服务端采集平台，或默认记录原始 prompt、环境变量和 transcript |
| Nx/Turborepo、通用 CLI/插件框架 | 暂无引入理由，现有单仓库 npm 与构建器足够表达阶段 | 为少量入口新增任务平台、插件系统或依赖缓存权威 |

核心判断来自 Wakeflow 自己的故障模式，外部资料只用于验证可复用机制和限制。MCP Inspector 的协议能力不能证明 Codex 的项目归属，云端幂等实践不能让聊天发送天然可重试，来源摘要也不能代替真实宿主的身份关联。

## 9. 现阶段明确不做

- 不另造自动 Controller、自动验收或“继续所有阻塞任务”的总开关。
- 不直接修复私有状态、不按 PID 或超时删除未知锁、不自动迁移旧开发版工作区。
- 不自动信任 hooks，不访问宿主私有数据库来弥补正式工具缺口。
- 不通过更长超时、失败自动重跑或跳过真实 fsync 掩盖稳定性问题。
- 不再建一个万能安装器，复制替代官方插件管理；先把检查、执行和激活证据分开。
- 不立即加入重型遥测、统一事务层、强制 monorepo 工具或全量业务代码生成。

仍需业务或宿主层解决的事项，包括可信窗口到 MCP 关联、角色身份安全边界、某些后续需求语义和支持平台范围，不能靠脚本改成“已解决”。工具建设的目标是让这些边界更清楚、更容易复现和验收。

## 10. 原始规划审阅范围和后续实施

初次规划时读取了上述代码路径、当前文件库存、已有完整门和原生使用记录，并查阅所链接的官方资料。当时只新增提案和开发文档索引，未修改运行时代码、测试、Schema、插件版本、安装缓存或现有图谱。

初次规划没有执行新的完整测试、故障试验、原生窗口验收、CI 或安装流程。用户确认后，按维护工具使用说明分批实施；未覆盖部分保留为计划。运行结果以开发日志的对应实施记录为准，规划文档自身不能计入产品验收。

## 11. 原生场景后的脚手架优先级补充（2026-10-04）

这是基于[两份实际Demand](../progress/consolidation-gate-log.md)提出、随后经用户确认实施的优先级。当前已实现的有限入口见[维护工具 §10–11](../references/maintainer-tools.md)；本节仍区分其余计划。主流程与worktree流程已完成，局部问题集中在临时测试脚本和宿主证据整理；现有运行时的限定重试、原始记录保留及两段关闭均按合同工作。

优先建设一个小型测试记录骨架：从冻结task package取得执行根、implementationBaselines和重试步骤集合，以不可变managed evidence及Git提交摘要绑定实际模块；每次尝试使用独占的新输出文件，分别保留stdout/stderr、命令与元数据。断言仍由Test按冻结合同编写。脚手架不得固定读取可轮换的event-sourcing快照，也不得自行批准重试、改期望或重跑已通过步骤。这次真实harness-defect比增加更多默认场景更直接地证明了该需求。

原生证据整理应复用现有live记录：区分创建/发送/归档的请求、成功返回、独立回读及人类UI确认，统一回执摘要的生成和核对；缺少某一来源时保持缺失。新聊天列表漏报与最后一条归档列表遗漏说明，既不能从调用意图推出事实，也不能把有限列表当成不存在的证明。该整理层不执行宿主动作，不补造hook，不创建第二个Controller，也不把来源未验证的JSON升级成宿主证明。

现场故障包与impact保持原优先级。前述两个骨架应先以本次明确失败和恢复路径作为验收样本，再决定接口；不为此改动快照保留策略、增加运行时状态或另建审批层。


第五批已实现 `wf capture prepare/run/inspect` 与 `wf live receipt`。capture 从配置中的指定Test窗口定位执行根，从冻结任务包、投递信封和前次结果核对尝试范围，从实施结果引用与明确提交绑定已提交的干净Git检出。可选取不可变event commit中的唯一信封，不读取派生快照；副本封存后不依赖原输入文件存活。执行单条显式命令、保留原始流和前后观察，稳定独占标记阻止同次步骤因换输出目录或重新prepare而重复。导入身份与实际授权仍由调用方核验，工具不拥有Controller判断，也不自动登记证据。

首版只接受committed实施基线，不处理未提交的dirty实现；只观察选定文件和Git状态，不扫描所有忽略文件/传递依赖，也不充当命令沙箱。live receipt逐字节保存导入请求/返回，同时标明文件摘要与完整返回JSON序列化摘要，永远保留导入未验证来源。自动关联真实请求、独立回读和人类确认的通用现场证据包仍未实施。

后续若要让仅安装插件的Test窗口直接使用捕获能力，需要单独明确发布入口和私有记录归属；不能把当前开发仓库的 `.build/capture` 写权限隐式转授给产品窗口。当前先验证维护者用法，不为此扩展运行时公共工具或新增跨工作区授权。


第六批将只读故障包落到doctor：自动保留配置与候选清单，另复制明确选择的工作区文件；SDK观察投影与原始文件分开保存，异常、取消、预算和前后变化均留在私有包。独立分享摘要使用封闭字段/值类别，保留未验证来源，不复制任意诊断文本，不自动上传。成功判定补齐两次成功调用、候选信息和观测时间的一致性，完整包可脱离源环境复验。

真实试验区分了宿主错配、损坏配置、正常0600私有文件与0644权限漂移。测试夹具改为明确chmod，避免把文件存在本身当故障或依赖调用方umask。上一批完整门的279文件耗时建议已显式用于调度，本批仍运行新的完整门，未把旧通过结果用于新输入。无源码诊断、自动宿主取证、impact与远端CI保留后续范围。
