<a id="foundation-document-role"></a>
## 1. 文档职责

本文不是某个当前 review 文件的需求，也不是逐文件修改日志。它是 Wakeflow 全局架构级需求，用来回答：

> Wakeflow 的哪些通用机制应下沉为基础服务，哪些相似实现必须保留在领域 owner，统一抽象应如何构造，以及后续怎样一次性、安全地迁移真实 consumer。

逐文件 review 只是事实入口。任意文件中发现的重复机制、环境构造、路径规则、错误模式或生命周期问题，只有可能影响 Wakeflow 全局基础架构时才登记到本文。

以下内容不进入本文：

- 单个文件的中文注释补充记录；
- 范围明确的小 bug 修复流水；
- 纯格式调整、局部命名改善或测试文案修改；
- 不产生全局抽象影响的领域内部重构。

这些局部工作仍可在逐文件 review 中随时进行，并在当轮代码 handoff 中说明。若一个“小问题”暴露了多处共同根因，则只把共同根因登记为基础服务候选，不把局部 bug 台账搬入本文。

<a id="foundation-background"></a>
## 2. 背景

Wakeflow v3 已经形成配置、布局、状态、artifact、transport、identity、Pod、host seam、维护事务、迁移、观察和打包等多个领域 owner。当前代码为了确保各 owner fail closed，在许多模块中分别实现了 plain object 检查、deep freeze、root 规范化、路径 containment、时间生成、错误转换和运行时 context 构造。

部分重复是必要的独立校验，部分重复已经产生过合同漂移。另一方面，现有 `canonical-json`、typed identifiers、config snapshot、layout descriptor、filesystem safety、atomic write 和 workspace mutation 等模块已经承担基础能力。R1–R67 已经覆盖主要真实 producer/consumer 和宿主、工具链、测试支撑面及物理源码闭包；哪些机制最终共享、扩展现有能力或保留本域，仍须在 G1 按候选做独立语义交叉审查，不能直接从重复数量推导。

因此，本需求不从“函数多”“文件长”或“应该面向对象”出发，而从以下问题出发：

1. 哪些不变量必须只有一个实现来源？
2. 哪些能力只需要纯函数，哪些需要冻结 context factory，哪些确实拥有资源或状态生命周期而适合 class/service？
3. 哪些表面相似的实现包含不同 authority、lock、TOCTOU、redaction 或 recovery 语义，不能合并？
4. 基础服务如何保持 host-neutral，同时允许 Codex/Claude Code 拥有独立实现？
5. 如何在统一实施时一次性迁移 consumer，不长期保留新旧两套基础合同？

<a id="foundation-goals"></a>
## 3. 目标

1. 建立 Wakeflow 全局基础能力地图，覆盖运行时、宿主接缝、维护/迁移、测试与构建验证。
2. 以 R1–R67 全量代码 review 为事实基线，持续维护经过真实调用链验证的重复机制和抽象缺口。
3. 区分 `new-foundation`、`extend-existing`、`reuse-existing`、`keep-domain-local`、`merge-call-pattern` 和 `reject-abstraction` 六类结论。
4. 为每个确认下沉项明确唯一职责、输入、输出、状态寿命、错误边界、依赖方向和真实 consumer。
5. 形成统一抽象构造方案，但在全局设计冻结前不开始基础服务代码迁移。
6. 设计统一实施顺序，使基础 primitive、context、effect 和 domain consumer 按依赖关系一次收敛。
7. 为实施阶段准备 focused、跨领域、双宿主、packaging、smoke 和全仓验收标准。
8. 防止基础服务演变成万能 manager、第二状态机、隐式 workspace registry 或 host 事实泄漏面。

<a id="foundation-non-goals"></a>
## 4. 非目标

- 不要求所有重复函数都被抽取。
- 不预设 class 优于函数，也不预设函数式模块必须继续保持单文件。
- 不创建掌管当前 workspace、当前 demand、当前 host 或当前 mutation 的全局 `WakeflowEnvironment`。
- 不新增机器全局 workspace registry，不通过 `cwd`、语义标题或最近访问目录猜选 workspace。
- 不把 domain state、event、journal、lease、transport 或 review 决定搬进通用基础服务。
- 不抹平各领域稳定错误码，也不让 low-level error 直接泄漏到公共工具面。
- 不把 Codex/Claude Code 的真实 profile 值、handle、locator、session 或 host effect 放进 host-neutral `core/`。
- 不统一目标产品仓库的 Node、Python、构建、测试和部署工具链；这些仍由 repository、TaskPackage 和 TestCard 合同负责。
- 不借基础服务重构重新开放已冻结的 legacy normal runtime、全局 registry 或第二配置权威。
- 不在需求发现阶段创建半成品公共 API、兼容 wrapper 或待迁移新模块。

<a id="foundation-review-implementation-separation"></a>
## 5. Review、局部维护与统一实施的分界

**基础服务发现与基础服务实施必须分开。先完成全局事实和统一设计，再开始抽取与迁移。**

### 5.1 Review 期间允许的局部工作

逐文件 review 可以继续：

- 为已经共同理解的职责和边界补充精确中文注释；
- 修复不改变公共API、authority、host seam或跨模块抽象的范围明确小 bug；
- 为小 bug 增加focused regression test；
- 做必要的语法、whitespace和生成副本同步；
- 运行只读诊断、focused tests和现有validator确认事实。

局部修复若需要同时修改多个领域 owner、引入共享模块、改变公共输入输出、重排锁/事务或迁移大量 consumer，则不再属于“小 bug”，必须登记到本文并延后统一实现。

### 5.2 Review 期间禁止提前实施的内容

- 新建基础服务文件并开始迁移 consumer；
- 把多个本地 helper 批量替换为尚未冻结的统一 helper；
- 创建全局 context、service locator、manager class 或 compatibility facade；
- 为未来基础服务预留未使用字段、参数、exports 或 schema；
- 因当前文件方便而冻结会影响全局调用链的API设计；
- 把局部 bug 修复伪装成基础服务首批落地。

### 5.3 阶段划分

| 阶段 | 工作 | 代码边界 | 退出条件 |
| --- | --- | --- | --- |
| G0 全局发现 | 随逐文件review登记基础候选、现有服务和差异 | 可注释/修小bug；不实施基础抽取 | 主要runtime/domain/host/tooling面均有事实记录 |
| G1 语义交叉审查 | 展开每个候选的全部真实consumer、失败和生命周期差异 | 只做必要局部维护 | 每个候选可判定为共享或本域 |
| G2 统一抽象设计 | 冻结服务清单、依赖图、API、class/function选择和迁移批次 | 不开始consumer迁移 | 用户逐项确认全局方案 |
| G3 开发实施文档 | 新建独立实施计划，写清任务、顺序、RED和验收 | 仍不修改基础实现 | 实施计划获确认 |
| G4 统一实现 | 按计划创建/扩展基础服务并迁移consumer | 仅执行确认范围 | 所有迁移和验证闭合 |

截至2026-08-24，G0退出条件已经满足：R1–R67覆盖共享runtime、全部当前domain owner、双宿主接缝、schema、模板、Skills、commands、README、发布/同步工具、历史夹具、测试支撑及物理源码闭包。排除`.git`、`node_modules`、仓库内部运行状态目录和`.DS_Store`后，实际审计`7910`个文件，其中`774`个当前源码/证据文件、`7136`个测试夹具文件；`482`个MJS/CJS全部通过`node --check`，`1469`个JSON与`6`个JSONL（`58`条记录）全部解析通过，`6`个shell launcher通过`sh -n`，源码范围内零symlink。shared-core/双宿主生成关系及最终`npm test`也闭合：`1821 tests / 1820 pass / 0 fail / 1 Windows-only skip`。该结论只表示“发现面完整且有可复核证据”，不表示11个候选已经通过G1处置，更不授权开始基础服务实现。

### 5.4 逐文件中文注释标准

已经完成共同review并确认真实职责的生产源码，后续统一按以下标准补充中文注释：

1. **文件头提供能力导航。** 对包含多个职责分区的文件，先说明它在全局调用链中的定位，再列出“能力 → 关键入口方法”的阅读地图；这些能力是同一owner或composition的不同步骤时，必须明确不是多套平行authority。
2. **按职责边界分区。** 使用简短中文章节标识合同校验、authority读取、领域编排、effect、projection、recovery或公共入口等区域，使读者无需先通读全部实现即可找到主链路。
3. **关键方法说明输入、输出和边界。** exported API、复杂编排、authority/effect/recovery方法应说明消费什么已验证事实、产出或执行什么，以及明确不负责的决定或副作用；不得只把函数名翻译成中文。
4. **机械helper保持一行。** 排序、摘要、字段选择、简单映射等无独立业务边界的方法使用一行职责注释，避免大段注释淹没控制流；方法简单不等于可以误写其authority语义。
5. **优先解释“为什么”。** 注释重点说明owner、source of truth、fail-closed原因、TOCTOU/lock/recovery边界、projection与authority区别，以及为何不能从文件存在性得出业务结论。
6. **只描述已实现事实。** 不在源码注释中写候选基础服务、未来API、猜测性TODO或尚未接线的能力；跨文件职责应指明真正owner文件或层级，不能让当前文件看起来拥有不存在的能力。
7. **中文只写在完整注释行。** `//`注释独占一行；JSDoc的`/**`、正文` * ...`和`*/`分别独占行，不使用`/** 中文 */`或代码尾部中文注释。这样既保持diff清晰，也让validator继续精确区分中文注释与禁止进入可复用runtime的中文字符串/模板文本。
8. **保持合同同步。** 若方法、公共operation、gate数量、状态词汇或执行顺序发生变化，同一改动必须更新相关中文注释和focused tests；注释不得成为独立于代码与schema的第二规范。
9. **共享源只改`core/`。** 双宿主共享文件先修改`core/`，再通过`sync:core`生成Codex/Claude副本并执行`check:core`；不得分别维护三份注释。

本标准不要求给每一行代码添加解释，也不以注释数量作为review完成条件。验收重点是：公共入口、非平凡helper和关键边界均可被准确理解，且注释没有扩张当前实现职责。

<a id="foundation-definition"></a>
## 6. 基础服务与统一抽象定义

### 6.1 基础服务准确定义

本文中的基础服务可以是：

| 形式 | 适用条件 | 示例职责 |
| --- | --- | --- |
| 纯函数模块 | 无跨调用状态，相同输入得到相同输出 | canonical data、typed ID、portable ref |
| 冻结值对象工厂 | 需要把一组同时验证的事实绑定成单次快照 | config/workspace authority context |
| Effect primitive | 拥有一个严格、可测试的底层副作用合同 | safe inspect、atomic single-file write |
| 有界运行时服务 | 多次调用共享静态资源或确有释放/重试生命周期 | installed asset/host adapter loader |
| class | 实例确实拥有资源、受控可变状态、dispose或真实多态 | 只在生命周期证据成立时采用 |

静态class只用于给函数分组，不比模块导出提供更多语义，因此不自动成为目标方案。普通JSON authority也不因方法调用方便而转成依赖prototype的model class。

### 6.2 基础服务必须具备

- 一个主要职责；
- 明确的host-neutral或host-specific归属；
- 闭合输入、输出、错误和副作用合同；
- 不依赖隐式current workspace/demand/host；
- 至少一个真实consumer，且能解释为什么由基础层统一；
- 独立focused test以及真实consumer回归；
- 不拥有domain acceptance、transition或外部host effect决定。

<a id="foundation-hard-boundaries"></a>
## 8. 全局硬边界

1. `wakeflow.config.json`、`.wakeflow-active`、`.wakeflow-local`、ledger、BusinessArchive和host profile的authority分类保持不变。
2. workspace/config context按显式root和每次操作构造；不得跨公共操作缓存成“当前环境”。
3. write-capable owner进入自己的lock/mutation gate后，仍须重读权威或校验exact digest；基础context不能替代提交前栅栏。
4. composition层可以构造丰富context，但传给domain owner的输入必须继续窄化；context不是授权包。
5. shared primitive只返回中立事实或执行已授权mechanical effect，不决定accept/rework/dispatch/archive/host activation。
6. lexical path、physical containment、future target admission、atomic CAS和domain transaction是不同安全层级，不因实现都调用Node `path/fs`而合并。
7. host capability schema可以共享，真实host values、raw handle、locator、mutex和physical effect留在宿主接缝。
8. domain error code由domain owner拥有；基础服务可以提供cause/details，但公共层必须完成稳定映射与脱敏。
9. normal runtime不得重新依赖legacy parser、semantic-name identity、local result authority或旧registry。
10. `core/`继续是双宿主共享真源；host-specific文件不进入shared sync集合。

## 12. 候选下沉准入条件

每个候选进入统一设计前必须回答：

| 检查项 | 必须取得的证据 |
| --- | --- |
| 全部定义 | 当前相关符号、模块和host副本，不只搜索同名函数 |

| 权威安全 | 不产生第二config/state/journal/registry或隐式授权 |
| 并发安全 | lock、TOCTOU、CAS、replay、recovery不能因抽象而削弱 |

| 迁移闭包 | consumer迁移批次、旧实现删除门和temporary compatibility策略 |

以下理由单独出现时一律不足：

| 理由 | 为什么不足 |
| --- | --- |
| “函数很多” | 可能只是schema/domain grammar的清晰拆分 |

### 12.1 BFS-01 Strict Data Contract：G1 语义交叉审查

**审查状态：**`g1-proposed-split / user-confirmation-pending`。本节只记录真实代码结论和建议处置，不冻结文件名、export 签名或 consumer 迁移批次，也不授权创建基础模块。

#### 12.1.1 审查范围与计数口径

本轮从当前 `core/` 正典共享源、`tools/` 源码以及真实 host-specific facade/adapter 反向审查定义和 production consumer；Codex/Claude Code 中由 `sync-core` 生成的共享副本只作为 parity 与打包证据，不重复计作独立设计来源。测试用于证明既有安全合同，不以测试 helper 冒充 production consumer。

按当前 `core/ + tools/` 精确源码搜索，排除双宿主生成副本后可见：

- `80` 个文件本地定义 `deepFreeze`；
- `69` 个文件本地定义 `plainObject`、`isPlainObject` 或 `assertPlainObject`；
- `13` 个文件定义命名明确的 dense/passive array snapshot helper；
- `46` 个文件直接使用 `JSON.parse(canonicalJson(...))` 构造独立纯数据副本。

这些数字只证明存在广泛机制重复。逐个读取 `wakeflow-canonical-json.mjs`、config owner、result review、process、ledger、tracked materialization、release packaging、Claude host facade 和代表性 records/service 后，真实输入域至少分成以下六类，不能按函数名直接合并。

| 合同族 | 当前真实用途 | 不能丢失的差异 |
| --- | --- | --- |
| canonical JSON 数据树 | record/plan/result 的无行为副本、稳定字节与摘要 | 只接受 JSON 值；标准数组；plain/null prototype；拒绝 accessor、隐藏字段、Symbol、额外/稀疏数组字段、外来原型、循环、非有限数和超过 128 层结构 |
| closed shallow request | process options、owner request、operation input 等当前调用边界 | 只被动读取 own enumerable data property；字段集合、必填项、标准 prototype 要求、容量和类型由当前 owner 决定；值可以包含 callback、Buffer 或 facade，不能强制 JSON 化 |
| projected extensible facade | host profile、adapter、participant、callback arguments 等允许上游扩展的对象 | 只投影当前 consumer 真正使用的字段；未知字段可能合法，不能套用 closed-record 规则，也不能递归冻结调用方持有的完整 facade |
| callable registry | MCP handler、maintenance handler、host adapter map 等数据驱动函数表 | 必须固定 own data-property 函数引用并防止 await 后替换；领域路由表、函数签名、调用顺序和 verdict 仍归 composition/owner |
| dense data array | argv、环境/报告列表、host observation、private Buffer operation 等 | standard prototype、最大长度、错误还是 diagnostic issue、是否允许非 JSON 元素及返回是否冻结并不一致 |
| domain record codec | demand、transport、window、Pod、ledger、archive 等 portable record | 字段语法、跨字段关系、typed ID/ref、集合闭包、稳定错误码、redaction 与 state authority 都是领域合同，不是通用 data helper 的职责 |

`result-review-orchestration` 中较宽的 `isPlainObject()` 也不是反例：所有公共输入先经过 `canonicalReviewInput()`，后续 helper 消费的是已规范化快照。相反，`wakeflow-process`、tracked materialization 和 Claude host facade 必须保留函数、Buffer 或只读 facade，因此不能先走 canonical JSON。该前置条件差异证明“同名 helper”并不代表相同输入合同。

#### 12.1.2 建议拆分处置

| 子项 | G1 建议 | 统一职责 | 明确保留/拒绝 |
| --- | --- | --- | --- |
| BFS-01A canonical data snapshot | `extend-existing` | 扩展现有 canonical JSON 能力，使调用方可从同一验证过程取得独立 canonical plain-data snapshot；可进一步组合为冻结 snapshot | 现有 canonical bytes/digest 和 golden digest 不变；调用方继续映射领域错误、执行字段与关系校验、决定容量和授权 |
| BFS-01B passive own-data structure | `new-foundation` | 提供浅层、descriptor-first 的 own enumerable data-property 读取，以及 standard dense own-data array 的中立快照事实；验证过程不读取字段值 getter，不忽略 Symbol/隐藏/扩展槽位 | 不递归解释字段值，不决定 allowed/required schema、prototype政策、最大长度、callable签名、host身份或业务 verdict；G2 再决定是返回中立 snapshot 还是 descriptor facts |
| BFS-01C immutable validated result | `merge-call-pattern` | 对 BFS-01A 产出的 canonical tree 或模块自己刚构造的已验证无行为结果，复用确定的冻结组合 | 不导出“递归冻结任意外部对象”的万能 helper；含 Buffer、typed-array、Error、callback、facade 或特殊生命周期的结果继续由领域 owner 明确处理 |
| BFS-01D domain codec/facade/registry | `keep-domain-local + reuse-foundation` | owner 可复用 01A/01B 的机械事实，再执行自己的 schema、关系、错误与回调合同 | 不把 record parser、host adapter、MCP dispatcher、maintenance composition 或 error mapping 合并成全局 StrictData service |
| BFS-01E generic validator/manager | `reject-abstraction` | 无 | 拒绝带 current workspace/host/domain registry 的 class、service locator、可配置递归“snapshot anything”、全局 error manager和第二 schema 系统 |
| JSON Pointer 单独导出 | `keep-local` | canonical JSON 继续私有转义自己的错误路径；validator/fixture 各自保留真实局部用途 | 当前只有少量、方向不同的 encode/decode consumer，尚无必须公开共享的不变量；不为两行重复增加公共 API |

BFS-01A 与 BFS-01B 是两个不同层级：01A 负责完整 JSON 数据树的规范化与复制，01B 负责不能 JSON 化或只应浅投影的运行时边界。两者都应是无状态纯函数，不需要 class、实例缓存、dispose、资源生命周期或继承体系。

#### 12.1.3 权威、错误与依赖边界

基础层只能拥有以下事实：

- 某属性是否为 own、enumerable、data property；
- 某数组是否为标准、稠密且没有额外 own authority；
- 某完整值是否属于现有 canonical JSON 数据域；
- 从已准入输入产生的副本是否与调用方对象解除可变别名；
- 中立结构错误的精确路径与原因。

调用方必须继续拥有：

- 标准 `Object.prototype` 与 null prototype 的选择；
- allowed/required 字段、字段类型、最大项数/字节数和跨字段关系；
- domain error code、公共错误文案、cause 脱敏和 diagnostic issue 降级；
- callback/facade 的函数签名、引用冻结时点和 await 后 fence；
- Buffer/typed-array 的防御复制与生命周期；
- config/state/evidence/host observation 的 authority、lock 内重验和 acceptance 决定。

依赖方向必须保持为“中立 data primitive → canonical JSON 或 domain consumer”。基础模块不得反向 import config、record、public runtime、host profile、schema registry 或 workspace mutation。若 G2 选择让 canonical JSON 复用 01B 的底层 descriptor primitive，必须先证明不会形成循环依赖；否则两者保持同层独立即可。

基础错误可以携带稳定的结构原因和无敏感值路径，但不得直接成为所有公共面共享的用户错误。每个 owner 继续把 cause 映射为自己的稳定 code/details，release packaging 这类纯评估器也继续有权把报告内部畸形表示为 `issues` 而非抛出异常。

#### 12.1.4 G2 设计与迁移门

若用户确认上述拆分，G2 只需冻结以下尚未决定的设计点：

1. 01A 是只增加 canonical snapshot，还是同时提供冻结 snapshot；不得改变现有 JSON 文本、bytes、digest 或错误路径。
2. 01B 返回冻结浅副本、entries 还是 descriptor facts；closed record 与 projected facade 必须是明确不同的调用模式，不能靠含糊布尔参数切换业务语义。
3. standard dense array primitive 如何接收调用方给出的最大长度；“最大值是多少”继续由 domain owner 决定。
4. 中立结构错误的最小 shape，以及 domain wrapper 如何保留原有 code/path/details/cause。
5. 哪些现有 local helper 语义完全等价可迁移，哪些因 null prototype、Buffer、issue 降级、host facade 或 callback fence 继续保留。

后续 G4 迁移应按语义簇原子进行，而不是按文件名批量替换：

1. 先为 canonical snapshot/frozen snapshot 增加 RED 与 golden 回归，再迁移语义完全等价的 `JSON.parse(canonicalJson(...))` wrapper；
2. 再迁移 closed shallow request、projected facade/callback snapshot 与 callable registry 的被动读取骨架，同时保留每个 owner 的字段和错误测试；
3. 再迁移 standard dense array consumer，并明确跳过允许特殊元素、特殊 prototype 或 diagnostic 降级的调用点；
4. 最后只删除已被 01A/01B 覆盖的 deep-freeze/shape helper，保留有 Buffer、typed-array、Error、facade 或已证明不同前提的实现；
5. 每个迁移簇在同一改动中接通全部目标 consumer、删除等价旧 helper，不保留永久 compatibility wrapper；共享源变更统一从 `core/` 同步到双宿主 artifact。

#### 12.1.5 验收证据要求

G4 实施至少必须证明：

- canonical JSON 现有 key 排序、数组顺序和 golden digest 字节完全不变；
- accessor、继承 `toJSON`、隐藏字段、Symbol、外来原型、稀疏/扩张数组、循环和过深结构继续 fail closed，且行为代码执行次数为零；
- closed record 不误接纳未知 own authority，projected facade 不因上游合法扩展被误拒绝；
- callback/handler 引用在首次异步边界前完成快照，不因统一 helper 恢复 TOCTOU；
- Buffer/typed-array/private operation 不被 canonical JSON 误处理，也不因 generic freeze 在 Node.js 中抛出新异常；
- config、records、process、release packaging、maintenance、MCP/CLI 和 Claude host consumer 保留各自原有稳定错误与结果语义；
- focused、相邻领域、双宿主 parity/validator/smoke、packaging、`npm test` 与 `git diff --check` 全部通过。

**待用户确认的 G1 决定：**接受“01A 扩展 canonical snapshot + 01B 新建浅层 passive structure primitive + 01C 仅合并已验证结果冻结调用模式”的拆分，并明确拒绝全局 StrictData class/manager。确认前 BFS-01 仍不是 G2 已冻结设计。

## 14. 统一抽象构造需要回答的问题

G2最终设计至少要明确以下结构关系：

1. plain data基础能力是否独立于canonical JSON，还是由canonical模块扩展；
2. workspace authority context包含哪些稳定字段，哪些字段必须由domain owner另行加载；
3. context是否分为host-neutral workspace snapshot与installed host runtime两类，如何避免相互污染；
4. portable path vocabulary、physical admission和write effect分别由哪个层级拥有；
5. record codec可以共享到什么程度，怎样保留domain schema与set-level invariant；
6. lock/journal/recovery只共享数据词汇、共享primitive，还是保持完全独立；
7. public MCP/CLI/maintenance怎样共享composition机制又不合并权限面；
8. host capability、live observation和physical effect的接口如何分层；
9. diagnostic issue是否需要统一shape，谁有权给出next action；
10. shared source inventory、validator exact exports和release packaging能否由一个正典清单派生；
11. 每个抽象采用函数、factory、service或class的生命周期证据；
12. 最终模块依赖图和禁止import方向。

这些问题全部确认前，本文不指定最终文件名和export签名。

## 16. 基础服务统一实施验收

一个确认的基础服务只有同时满足以下条件才算完成：

1. 只有一个主要职责，没有吸收domain business decision。
2. 全部计划consumer接通，旧重复实现已删除或有明确不同语义。
3. 不存在未使用API、未来占位字段或永久compatibility wrapper。
4. context不缓存跨操作workspace authority，mutation不丢失lock内重验。
5. public结果不新增绝对私有路径、raw handle、PID、token或内部journal信息。
6. Codex/Claude共享合同一致，host-only实现和文件仍正确分离。
7. focused tests覆盖正向、错误映射、stale/race/recovery和相关安全负向场景。
8. `npm run sync:core`、`npm run check:core`及双artifact实际diff检查通过。
9. 受影响的双host validator、smoke、packaging和consumer回归通过。
10. 最终候选执行`npm test`与`git diff --check`；真实host/WakeWorkspace未执行项如实记录。
