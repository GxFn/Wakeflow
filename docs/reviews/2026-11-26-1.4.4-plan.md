## 2. A：pod 重新设计——三个小实验的结果

1. **`claude --worktree` 能不能指向仓库之外的位置：不能。** 它的参数是一个名字（`-w, --worktree [name]`），位置由宿主定在仓库里的 `.claude/worktrees/<名>`。镜像布局下 tmux 传输不能再用它，要和桌面一样以检出为工作目录启动。
2. **桌面应用怎么看镜像位置的检出：不当成 worktree 会话。** 在一次性测试工作区里把一个产品仓库的检出建在工作区下的另一个目录（不在仓库里面），照助手的做法起会话并交给桌面应用：会话的元数据里没有检出路径、检出名与分支，"原仓库"就是这个目录自己。对照：检出在 `<仓库>/.claude/worktrees/<名>` 时这三样都有。也就是说应用是按路径约定认 worktree 会话的，不是按 git 认。**归档这样的会话，检出不会被摘下分支**：检出干净，归档之后 HEAD 仍在自己的分支上，半分钟后再看也一样（对照 §13.283：同样干净的检出在仓库里面的位置上，一归档就被摘）。所以镜像布局顺带去掉了 X33 的那个行为，助手里的核对仍留着兜底。
3. **`file:../X` 依赖在镜像布局里的行为：成立。** 五个产品仓库用的是 npm；锁文件里这些依赖记为链接（`resolved: "../AlembicCore"`、`link: true`），安装出来是指向相对位置的符号链接。镜像布局里仓库之间的相对位置与主检出相同，所以只要被依赖的仓库也在 pod 里，链接就指向 pod 自己的那份检出。没有真的跑安装（那要从网络取包）。

检出位置的假设在代码里集中在 Claude Code 宿主这一层：两个助手共用的检出准备（路径拼在仓库里面）、启动指令（tmux 的 `--worktree`、窗口的落点）与文本。窗口登记的回执核对、hook 的工作区定位按 git 的 worktree 指针认检出，与位置无关。

## 3. D：内核咨询锁——本机复核

Node 24.22、APFS 本地卷，打开文件时带独占锁标志（非阻塞）：另一个进程持有时被拒（`EAGAIN`）；持有者被强杀之后立刻拿得到；同一个进程里第二次打开同样被拒；一次"拿、探、放"约 0.2 毫秒。与 2026-11-19 的实测一致。重排文档列的条件仍然要逐条回答：多个版本并存时两套锁的互认；只能非阻塞轮询、没有排队公平；拿到之后仍要核对路径指向的节点；只读的"是否被持有"会变成试锁；不支持咨询锁的卷怎么认；句柄必须显式关闭；诊断里"谁持有"怎么给。
