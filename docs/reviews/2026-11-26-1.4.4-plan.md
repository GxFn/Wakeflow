## 2. B：字段减法

**现状。** 任务包的持久格式要求"已确认的上下文""完成预期""边界里的范围之内"三个列表非空；评审决定要求至少一条独立核对，每条的"方法""观察"必填，"理由"必填。Controller 因此每个目标都把这些写满。任务包存在规划事件里，决定存在评审事件里，两个事件都在版本 1。

**设计。**

1. 任务包：必填只留"目标"与"验收锚点"（测试任务是测试契约）。"已确认的上下文""完成预期"与"边界"的三段在请求里改成可选；持久格式里成员照旧都在，只是这三个列表允许为空。
2. 评审决定：决定是"接受"时"理由"可以不写；独立核对仍然至少一条，每条的"方法"可以不写，"观察"与"结论"照旧必填。返工、受阻、升级三种决定不变。接受一个"待复核"结果时锚点到证据的对应照旧必须齐全。
3. 格式：**原地放宽，不升事件版本。** 已有的记录全部满足放宽后的 Schema，字节与摘要不变，读入不需要任何步骤。设计结论里原先写的"一次版本升级步骤"不需要了——那一步唯一的作用是让旧版本的制品报"版本不支持"而不是报 Schema 不符，两种都是拒绝。
4. 文本：规划参考写明这三样只在需求包与验收锚点没有说到的时候才写（例如只针对这个目标的一条禁令）；评审参考写明接受时不必复述核对；投递提示与每个 Demand 的页面在这几段为空时不渲染标题。
5. 一起做的两处文本（已裁决）：一份包带多个工作项怎么写、什么时候该拆成两个目标；部分成立时替代的任务包只带没有成立的那几条。

**不再保证什么。**

- 任务包可以不带上下文、边界与完成预期：目标窗口这时只有目标、验收锚点和需求包。Schema 不再强迫 Controller 写出"不许做什么"；目标技能里的常驻规则（只动指派的检出、不推送等）不受影响。
- 接受的决定可以没有理由、核对可以没有方法：记录里仍有每条核对看到了什么、结论是什么，"怎么查的"可能缺。
- 1.4.4 之前的制品读不了用了短写法的 Demand（Schema 拒绝）。

不变的：每条验收标准都要有锚点或测试步骤；每个决定至少一条独立核对；小版本之内不删公共请求的成员（只把必填改成可选，拿着旧工具定义的会话照旧写满也能过）。

**大小与验证。** 两批：合同与解析、渲染（三份领域 Schema、三份请求 Schema、提示与页面）；文本三处。预期每目标的手写字节从约 5,000 降到 3,000 上下——这取决于 Controller 用不用短写法，要在现场一轮里量。

## 3. A：pod 重新设计

**实验的结果（四个）。**

1. `claude --worktree` 的参数只是一个名字，位置由宿主定在仓库里面。镜像布局下 tmux 传输不能再用它，要和桌面一样以检出为工作目录启动。
2. 桌面应用按路径约定认 worktree 会话：检出在镜像位置时，会话的元数据里没有检出路径、检出名与分支；**归档这样的会话，检出不会被摘下分支**（对照 §13.283：检出在仓库里面的位置上时一归档就被摘）。镜像布局顺带去掉了 X33 的那个行为，助手里的核对仍留着兜底。
3. 五个产品仓库用 npm，相对依赖在锁文件里记为指向相对位置的链接。镜像布局里仓库之间的相对位置与主检出相同，被依赖的仓库也在 pod 里时链接指向 pod 自己的那份。没有真的跑安装（要从网络取包）。
4. 补做（2026-11-25，一次性的 tmux 测试工作区）：在镜像位置的检出里用清空过的环境起一个普通的 `claude`，直接进到输入提示，**没有信任对话框**。

**代码的现状。**

- 配置里每个 pod 本来就带着自己的仓库清单（每个仓库一条，指向这个 pod 里它的产品窗口）。"满配"是两条规则造成的：创建时从全部仓库派生窗口；配置校验要求 worktree pod 里每个仓库恰好一个产品窗口。
- 规划时仓库在这个 pod 里没有窗口，已经会被拒绝。
- 检出的位置写死在 Claude Code 宿主层的三处：两个助手共用的检出准备、启动指令（tmux 的 `--worktree` 与窗口的执行位置）、文本。检出回执的核对与 hook 的工作区定位按 git 的 worktree 指针认，与位置无关；公开结果对检出位置的边界（工作区根之内或它的父目录之内）镜像位置也满足。
- 正式工作区现在只有主 pod，没有按旧布局建的 pod。

**设计。**

1. **只含部分仓库的 pod。** 创建的请求多一个可选的仓库清单，缺省是全部。配置校验放宽成"worktree pod 里每个仓库至多一个产品窗口、至少有一个"。配置的形状与版本号不变。
2. **依赖要闭合。** 预览读清单里每个仓库的 `package.json`，它用相对路径依赖的仓库不在清单里时拒绝，并点名缺的是哪几个；Controller 带着补全的清单重来。不自动补进，也不放符号链接。
3. **pod 不再带自己的 Design 窗口。** 需求包发布到看板，与 pod 无关；使用者在主 pod 的 Design 窗口起草，由 pod 的 Controller 认领。只动一个仓库的 pod 于是是三个窗口（Controller、Test、一个产品窗口）加一个检出。
4. **镜像布局。** 检出放在 `<工作区>/.wakeflow-pods/<pod 名>/root/<仓库的配置路径>`：配置允许仓库在工作区根之下或恰好在它旁边（路径以 `../` 开头），多出的 `root/` 这一层让两种情况下仓库之间的相对位置都与主检出相同。两种传输都由助手准备检出、以检出为工作目录启动，tmux 不再传 `--worktree`。工作区根自己是 git 仓库时，这个目录进受管的 `.gitignore` 块（照受管文本的规矩登记旧的渲染）。
5. 规划被拒时说明出路：这个仓库不在本 pod，换一个带它的 pod，或者在主 pod 里做。创建时的相对依赖提醒随第 2 条变成拒绝，原来的提醒文本删掉。
6. Codex 宿主：第 1、2、3 条是共用代码，两边都生效；第 4 条只在 Claude Code 上做——Codex 的检出位置由 Codex 自己定，D12 在那边不变，照旧登记。

**不再保证什么。**

- 一个 worktree pod 不再含全部仓库：Demand 做到一半发现要动 pod 之外的仓库时，规划被拒，要换 pod。
- 依赖闭合只看 `package.json` 的四张依赖表；别的生态（工作区清单、别的语言的路径依赖）看不见，要使用者自己把仓库列全。
- pod 里没有 Design 窗口：在 pod 的 Controller 里想补需求，要到主 pod 的 Design 窗口去写。已经建好的 pod 保留自己的 Design 窗口直到关闭。
- 按旧布局建的 pod 升级之后对不上位置：升级之前要关掉。正式工作区现在没有这样的 pod；测试工作区里的由我关。不做两种布局并存。
- tmux 上 pod 的产品窗口不再经 `--worktree` 进入，宿主对那条检出加的锁不再有。它挡的是什么、少了之后 agent view 会不会来清这些会话，要在 tmux 一轮里看。
- 配置里一旦有不满配的 pod，1.4.3 及更早的制品读不了这份配置，直到那个 pod 关闭。

**大小与验证。** 四批：① 部分仓库与依赖闭合（配置校验、pod 的计划、请求 Schema）；② 不带 Design 窗口（窗口派生、pod 作用域的类型、状态与文本里提到 pod 的 Design 窗口的地方）；③ 镜像布局（共用的检出准备、两种传输的启动指令与助手、受管的忽略块）；④ 文本。然后 tmux 一轮（建一个两仓库的 pod，其中一个依赖另一个，在检出里真的跑一次安装与测试；走一个 Demand；关 pod），部署之后桌面一轮。

## 4. D：内核咨询锁

**本机核实的（Node 24.22、APFS 本地卷）。** 打开文件时带独占锁标志（非阻塞）：别的进程持有时被拒；持有者被强杀之后立刻拿得到；同一个进程里第二次打开同样被拒。带共享锁标志：共享与共享并存（跨进程、同进程都是），有共享时独占被拒，有独占时共享被拒。一次"拿、放"约 0.02 毫秒。还核实了一个反例：锁文件被删掉之后，新建的同名文件可以在旧节点仍被持有时拿到锁——所以**锁文件不能删**。

**现状。** 十一类锁：七类轻档（操作作用域的闩锁、写者锁与读者租约，投影锁，看板锁，pod 变更锁，Demand 发布锁，账本记录锁）与四类权威档（绑定登记锁、三把工作区根的锁），另有维护的门。锁是"独占创建一个带属主记录的文件"，释放时删掉并同步父目录；持有者死了靠进程号加出生时刻判断，再由下一个获取者清掉，连同它旁边的暂存。

**设计。**

1. 锁 = 在私有目录里一个常驻的空文件上持有内核锁。文件只建不删；拿到之后核对一次路径指向的仍是手里这个节点。
2. 操作作用域的"闩锁加写者锁加读者租约"三样换成一个文件上的共享锁与独占锁。读者租约文件、数到 64 再清、准入目录的残留上界都不再存在。
3. 按记录、按 Demand 命名的锁改成每类一把（账本一把、Demand 发布一把）。这个量级的并发下没有可见的差别，并且不再往账本目录里放锁文件。
4. 绑定登记锁与三把工作区根的锁一起换。**维护的门不换**：它记的是"有一笔维护事务没做完"，不是互斥，掉电之后必须还在。
5. 持有者死掉不再留下任何东西，所以"清死锁"整套删掉。原来清死锁时顺带做的"恢复它旁边的暂存"改成每次独占获取之后做一次（今天只在发现死锁时做）。
6. 诊断：拿到锁之后把进程号写进锁文件，只给人看，不参与任何判断。只读的"是否被持有"变成试一次共享锁、马上放。
7. 不支持咨询锁的卷（网络共享）：第一次获取失败时以点名的原因拒绝，不退回文件锁。

**重排文档列的条件，逐条的回答。**

| 条件 | 回答 |
|---|---|
| 多个版本并存 | 旧进程用文件锁，新进程用内核锁，两边互不相认。靠的是已有的那道门：每个变更入口先核对磁盘上的制品清单有没有被换，换了就拒绝（1.4.3 的桌面一轮里现场走过）。漏的是更新那一刻已经过了这道核对、还在跑的一次调用——所以更新仍然只在没有活动 Demand 时做 |
| 只能非阻塞轮询、没有排队公平 | 与今天一样，今天也是等一会儿再试 |
| 拿到之后核对路径指向的节点 | 锁文件不删，核对一次即可 |
| 只读的"是否被持有" | 试锁（见第 6 条） |
| 不支持的卷 | 拒绝并点名（见第 7 条） |
| 句柄必须显式关闭 | 获取与释放只有一个入口，用 `try/finally` 包住；进程退出时内核收走 |
| "谁持有" | 锁文件里那行进程号，可能是上一个持有者留下的，只作提示 |

**不再保证什么。**

- 锁文件不再说明"谁在持有"到可以据此判断的程度：诊断里的持有者只是提示。
- 与 1.4.5 之前的进程之间没有锁上的互斥，只有"制品被换就拒绝"那道门。
- 工作区放在不支持咨询锁的卷上时不能用（今天的文件锁在那里能用）。
- 账本记录之间、Demand 发布之间不再各有各的锁：两个 pod 同时发布各自的 Demand 时会先后排队，各等对方几十毫秒。

去掉的隐患见第 5 节。

**大小与验证。** 决定记录先行（ADR-0033，写完请你过目再动代码）。然后四批：① 新的锁原语与它自己的测试（真实子进程：持有、强杀、再获取；共享与独占的组合；节点核对）；② 操作作用域与读写作用域换上去；③ 其余九类逐类换，每换一类删掉它的清理代码；④ 删旧原语、旧测试与文本里提到锁文件的地方。预期净减：源码约 1,200 到 1,500 行、测试约 2,000 行——这是按模块大小估的，照例以做完之后数的为准。证明靠三样：原语的真实进程测试；场景链；tmux 一轮里做一组杀进程演练（在几条变更命令各自持锁时强杀，再发下一条命令）。扫点工具已经删了，不重建。

- **已收或已过时（5 条）。** 绑定登记锁挡住只读清点、三把根目录的锁没有清理（1.4.2 已修）；有路没路标的点（段 1b 已收）；没有调用能救的点（规划、完成、创建三组段 1b 已收，维护的 10 个点 1.4.2 已收）；扫点工具自己缺的自测与生成规则的局限（工具已删）。
- **随 D 消失（9 条）。** 锁记录读不到出生时刻时进程号复用判不清（锁的那一半）；两个进程同时清同一把死锁；首次初始化被死锁文件挡住；释放时删除没落定就跳过同步；按记录命名的锁没人再拿、永久留下（两处）与读者租约攒到 64 个才清；轻档获取输掉链接时暂存的删除不同步；全新初始化的端到端测试没有建（准入目录里不再有锁文件，这条测试不再需要）；卷的类型只在预览里看一眼（并进 D 的第 7 条）。
- **值得单独修（7 条）。**
  1. 看板的索引页被删之后，认领路径按英文重建，`verify` 一直报到下一次维护——重建时带上语言。
  2. 催促记录读不出来时被当作不存在，那次催促随后被数成投递之外的输入——读不出来单独报。
  3. 发布需求包之后进程被杀，第一次撤回必然被拒、重试才过——撤回先结算暂存再算期望。
  4. 规划、投递、证据、评审打开 Demand 被清点拒绝时不带出口；`pod-busy` 只带标识——把"拒绝要指路"在这几条命令上补齐。
  5. 活动投影按顺序清页时被后一页的死暂存挡住、证据负载的暂存在候选检查之前没有恢复——这一条是读代码读出来的，先写测试摆出盘面，成立再修。
  6. 证据的 recover 照点名的调用治不治得好，没有在真实进程里跑过——补一条真实进程的测试。
  7. 创建的 recover 遇到需求包已被撤回时怎样结束，没有核实——补测试，按结果定。
- **继续只登记（10 条）。** 只在掉电且目录操作乱序时出事的那一类（"沿用之前先落盘"没补的分支、懒建的日志目录那一种没有出路的、发布暂存树里单链接快照丢内容）；要有人动过手脚的（根的位置上是符号链接）；要一次竞争的（续接的补充包被别的 pod 认领、共享范围的写者不拿 pod 锁）；旧版本留下的盘面；不挡任何命令的残留；只在模型里出现的；非常见 umask 下建目录的窗口；Demand 根自己、许可目录与事务目录的严格清点；看板状态文件的双链接、配置与支撑记忆、三种整文件发布的严格清点（1.4.2 筛过，没有会卡住的证据）；清不掉的暂存残留；每次加载查进程表的开销。

**大小。** 七条共两批，都带各自的测试；第 5、6、7 条先证明再决定改不改。

## 6. C：统一存储接口

**调研之后剩下的收益。** 存储层计划当初有两个理由：速度与重复。速度那一半已经做完——逐段核对路径、多余的同步在 1.4.1、1.4.2 拿掉，hook 记录的读法在 1.4.3 拿掉。剩下的是重复：97 个模块自己核对节点，12 个自己调暂存恢复。它不影响使用者看到的任何东西，收益是以后改存储时只改一处，以及"恢复只有一条路"能把第 5 节里"先清再判"那一类问题一次收掉。

**风险。** 这是全工程引用面最大的一次改写；每个存储崩溃之后的行为要重新定义，而逐点杀进程的证明工具已经删了；1.4 第 5 段的教训是这类改写的行数事先估不准。

**设计（只到试点）。**

1. 在 foundation 建接口：读、列目录、独占新建、比较后替换、删除、整目录发布、在锁内执行。节点、属主、权限位、链接数、暂存恢复都在接口后面。D 做完之后"在锁内执行"就是内核锁，接口因此比 11 月 19 日设想的薄。
2. 挑引用面最小的一个存储做试点（候选：窗口绑定登记，或看板）。量三样：这个存储自己少了多少行、它的调用方改了多少处、行为有没有变（它的测试原样通过）。
3. 带着数字回来请你定：继续按层迁移，还是到此为止、只保留接口供新代码用。

**不再保证什么。** 试点不改行为，没有清单。继续迁移的话，每一批开工前各给一份。

## 7. 先后、分版与验证

**先后：B → A → D → E → C。** B 最小、收益最直接，并且与另外四项互不相干。A 是正式工作区用 pod 的前提。D 排在 C 前面，因为它决定接口里"锁"那一部分长什么样；E 的 9 条随它消失，剩下的 7 条跟着做。C 最后，并且只到试点。

**分版：建议三次部署。**

| 版本 | 内容 | 门与现场 |
|---|---|---|
| 1.4.4 | B、A | 一道门；tmux 一轮在部署之前，桌面一轮在部署之后 |
| 1.4.5 | D、E | 一道门；tmux 一轮带杀进程演练；桌面一轮 |
| 1.4.6 | C 的试点 | 一道门；不改行为，现场只做更新路径 |

理由：五项里 B、A 改的是使用者看得见的流程，D 改的是每一条变更命令脚下的锁。放在一次部署里，现场出了问题分不清是哪一项的；分开之后每次部署各有自己的一轮现场，回退也只退一版。代价是多两次"关会话、更新、重开"。

每一版照现在的规矩：各批做完之后先现场一轮、再过一道门；门在沙盒检出里跑；快进 `main` 等你的话；推送与 tag 是你的。

## 10. 裁决与执行记录

**用户裁决（2026-11-25）："A 和 B 先延后吧，优先做 C D E，代码量上的收益也很重要，我期望整洁的代码实现"。** 维护者的读法：

- A、B 延后，设计留在第 2、3 节，不在这一轮做。已经做完的三处"一份包多个工作项"文本不受影响。
- C 的目标从"试点之后再定"改成"做完"：代码量的收益是要拿到的东西。试点仍然是第一批——用它量出每一批能删多少、定下迁移的写法——但它不再是做不做的关口。
- 先后仍是 D → E → C。理由：内核锁决定接口里"在锁内执行"长什么样；先做 C 的话，接口要先把"判断属主死活、清死锁、顺带恢复暂存"包进去，D 再把它删掉，那一层是白写的。
- 分版：1.4.4 = D + E，一次部署；C 接着做，单独成版。第 7 节的表按这个读。
- 第 8 节里没有被改动的各条按建议执行：D 的决定记录先行、写完请用户过目再动 D 的代码；E 修那 7 条，不重建扫点工具。
- "整洁"在这三项里的意思：删除优先；一类事只有一个入口；不留新旧两套并存的分支；每一批报告净减的行数。

**写决定记录时对第 4 节的两处更正（2026-11-25，[ADR-0033](../decisions/0033-kernel-advisory-locks.md)）。**

- 第 4 节设计第 4 条说"维护的门不换"，不对。读代码之后：维护"没做完"的记号是事务目录里的意图文件；门只是一把锁，进程死在"拿到门、还没写意图"之间留下的死门锁今天要专门退役。所以门也换，换了之后那种盘面不再出现。
