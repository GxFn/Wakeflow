## 1. 当前结论与实测边界

正常流程已经跑通，但几个关键约束只在局部模块里成立，尚未跨越公共入口、并发进程和需求生命周期保持一致。最需要优先处理的是恢复入口不可达、pod 并发认领、取消传播和全量验收覆盖。它们均在本轮得到了可重复的进程或文件系统证据。

测试使用单独的一次性工作区。除基线整门和制品 smoke 自带的临时目录外，本轮新增脚本、故障注入目录、Git 夹具和输出均保存在该工作区。真实产品仓库与前轮工作区没有被用来制造故障。制品是当前生成的 Codex MCP server，经官方 SDK 的 stdio transport 启动；进程中断点只暂停调度，不伪造提交文件。崩溃路径使用默认 `fsync`，夹具建立仍使用现有测试辅助模块的可丢弃初始化策略。

## 2. 根因：局部保护正确，边界没有闭合

| 边界 | 已经存在的保护 | 断点 |
| --- | --- | --- |
| 事件文件到 Demand 入口 | no-replace 提交、候选分类和精确退役 | 严格健康清单先拒绝候选，领域入口到不了恢复器 |
| pod 检查到发布 | 单包 claim 锁、单 Demand 发布锁 | pod 不变量涉及两个不同包和两个不同 Demand，现有锁不覆盖这个集合 |
| MCP 到执行器 | 下层普遍接受 AbortSignal | 注册回调丢弃 SDK 请求上下文，取消从未传入 |
| 单任务到需求完成 | 引用必须指向真实标准，结果必须满足所选锚点 | 只验证选中的集合，没有和需求标准全集比较 |
| agent 角色到状态写入 | skill 分工、任务与投递围栏 | server 没有可信调用窗口上下文，Controller 动作不校验调用角色 |
| 制品到已安装数据 | 字节摘要、严格 Schema、自洽托管 marker | 摘要相等性被用于版本新旧判断；旧渲染和旧状态模型缺少长期读取策略 |

这些根因不支持重新造一套工作流状态机。修复应尽量复用现有事件存储、命令外壳、资源锁、维护事务、版本编解码和 currentTargets 接缝；缺失的是它们之间的可达路径、共同约束和明确的兼容边界。

## 3. 恢复、并发和取消的修复设计

### 3.1 候选恢复：观察、恢复和健康准入分别负责

`src/governance/demand/event-sourcing/demand-event-sourcing-root-inventory.ts` 的 `inspectDemandEventSourcingRootInventory` 把 appendCandidateCount 定义为字面量 0，并执行 `assertEmpty(candidates)`。`demand-file-event-store.ts` 的 `recoverAppendCandidates` 却只在 Demand 发布前被接入。公共上下文必须先经过严格 root authority，因而恢复逻辑被挡在入口之后。

提交后残留还有第二层障碍：候选和 commit 是同一个 inode 的两个硬链接，普通读取要求单链接。因此仅把 `assertEmpty` 删除并不能得到正确修复。也不能统一删除候选或修改历史摘要来让加载通过。

建议设计：

1. 增加有界、只读的残留观察结果，区分健康、已知可恢复、写入者活动、所有者不明及未知结构。status/verify 可以展示事实和稳定原因，保持零写。健康加载和归档封存继续要求严格清单。
2. 在变更入口进入严格 authority 加载之前，为该 Demand 建立排他恢复边界。优先复用现有 Demand 作用域锁的布局和基础锁原语，并明确正常追加、恢复、取消、归档共同遵守的范围；不能只让恢复器取一把写入器不知道的锁。避免嵌套取得同一非重入锁。
3. 在锁内重新观察，而不是信任 preview 的旧文件清单。只有身份、权限、链接关系、所有者状态均可证明的残留才交给已有恢复器。活动 owner 返回可重试冲突；unknown 和未知文件保持阻塞并给定位原因。
4. 候选未提交时只退役候选；已经提交时先结算目标持久性，再退役额外链接，保留原 commit 的全部字节。并发失败方不覆盖胜者。随后重新走健康加载，并由原请求的幂等路径补齐投影或声明释放。
5. 自动恢复只覆盖已证明安全的资源结算。需要人工判断的异常通过现有维护工具的受限 preview/apply 扩展处理，不能把普通 status 变成清理器，也不能让恢复顺带替 Controller 接受结果。

已有 `result-review/service.ts::replayImport` 会重做条件化的围栏释放，`tasking/service.ts` 的幂等路径会重建任务包投影。这些应保留并纳入中断矩阵，避免另造“已完成但再跑一次业务决定”的分支。

验收必须覆盖创建候选、候选写到一半、link 之前、link 之后、目标 sync 之后、候选退休之后、索引/快照/投影刷新之前。每点都分别检查未提交不冒充成功、已提交不丢失、重复恢复不追加事件、活动和未知 owner 不被清理。本文只完成其中两个落盘点的公开进程复现。

### 3.2 锁恢复由资源所有者接入

`src/kernel/requirement-board.ts::withClaimStateLock` 只 acquire，不调用失活锁退役；`src/kernel/active-projection.ts::publishActiveProjection` 只有 `recovering:true` 才退役，而正常刷新和 reconcile 路径没有打开它。Foundation 不擅自偷锁是正确边界；缺少的是知道业务资源及相关 stage 的上层调用者。

建议复用 `wakeflow-window-host-binding-store.ts::prepareStaleLockRecovery` 的模式，但分别验证 board 与 projection 自己的暂存文件和原子目标，不能复制一段忽略所属目录的“删锁”代码。退役必须使用真实 inspect 签发的观察对象，校验节点、摘要、token 和 owner 仍相同。其他恢复者抢先完成时重新观察，不能把恢复竞争当作文件损坏。

PID 复用与 EPERM 仍是源码确认的风险，本轮没有伪装成现场复现。EPERM/unknown 不应被强制视为死亡。增强 owner identity 时可加入进程启动指纹或 boot identity，但需要版本化读取旧锁，并定义平台无法取得这些事实时的保守行为。不要用 mtime 超时替代身份判断。

projection 是派生物。刷新失败不应否定业务提交，但应返回或观察到明确的降级状态；死锁不应使每次变更都白等 10 秒。投影锁应在业务锁释放后取得，避免派生物反向阻塞权威资源。修复窗口投影的 B6 时还要核验 binding/config 来源摘要；对输出文件做 CAS 并不能证明渲染输入仍然新鲜。

### 3.3 pod 不变量需要覆盖同一资源集合的临界区

`demand-event-sourcing-publication-service.ts::publishDemandFromPackage` 的守卫在 `runLocked` 之前；后者按 demandId 加锁。不同 requirementId 的 claim 锁也不同。public apply 重算 plan 能缩小窗口，但不能建立互斥，R5 已用两个真实 server 证明。

建议把“重新读 pod lifecycle/config → 检查活动需求及未决发布 → 发布 Demand/认领”放进同一个 pod 作用域临界区；continue 重新激活与 pod close 进入 closing 也必须使用同一个边界。单 Demand 锁及单包 CAS 保留，负责幂等与各自资源的完整性。

不能只在 claim 前再加一次扫描：这仍存在检查与写入之间的窗口。也不能在异常后直接删除第二个 Demand；已发布事实需要明确的修复决定并保留历史。

实施前绘制真实锁调用图，固定 pod、Demand、board、config 的取得顺序；不得在锁内等待 Agent 或宿主回复。配置变更与运行时写入的 B6 需要单独的协调方案，pod 锁本身不解决整个 workspace 的维护并发。先用现有配置摘要和维护 gate 确定哪些变更可以并行，涉及拓扑切换的 apply 必须取得共同的短期变更边界，再在边界内复验快照。

回归条件：两个不同包在同 pod 争用恰有一个成功；不同 pod 不被无故串行化；create/continue 与 close 交错不能生成 closing pod 上的新活动需求；持锁者崩溃后下一次操作能按同一 owner 规则恢复。原有真实 worktree 关闭保护仍需保留。

### 3.4 取消修复必须接当前 SDK，并尊重提交点

`wakeflow-public-mcp-tool.ts` 的 executor 类型只收 value，注册回调只收 request。当前依赖是 MCP SDK v2，其取消信号为 **`ctx.mcpReq.signal`**。旧审计建议中的 `extra.signal` 不能直接照抄。客户端 v2 的 `callTool(params, options)` 也只有两个参数，本轮测试器已据此纠正并核对实际取消通知。

建议给内部 executor 增加窄的执行上下文，把 SDK 信号送到 shared executors 和两个宿主 composition root，再传入已有 `options.signal`。这是内部执行参数，不应暴露为模型可填写的 JSON 字段。隔离的单工具入口已经证明该路径使现有领域锁等待及时中止，业务状态不变。

取消不等于回滚：提交前停止等待和新副作用；不可逆提交之后继续必要的持久性结算与精确清理，依赖幂等重试确认结果，不能向调用方保证“没有写入”。投影刷新可以中止，但不能因此把已提交事实误报成未提交。还需要区分请求取消、transport 断开和进程关闭。

`wakeflow-mcp-stdio.ts` 当前仅接 SIGINT/SIGTERM。本轮证明 SIGHUP 会终止写到关键点的 server。补 SIGHUP 的优雅关闭有价值，但 SIGKILL 永远无法捕获，所以它不能替代磁盘恢复。信号处理、SDK close 和在途执行器的等待顺序应单独测试。

### 3.5 hook 容量与损坏条目

`hook-observations.ts` 在目录过滤前执行 16384 项上限，写入后的修剪只按 30 天年龄，因此近期有效记录达到上限时，继续写入也不能让查询恢复。提高常量只会推迟同一失败。

建议把记录按时间范围分片，按查询涉及的分片与记录名做有界流式枚举，并明确是否完整扫描。单分片仍需考虑突发量，不能仅按“天”分目录后保留同一个硬上限。最新窗口启动、指定 prompt 和完成记录的查找需要可证明的结果；不能简单取最新 N 条后把没找到解释成未发生。来源不完整应为 unavailable，而非否定落地事实。索引只能是可重建加速器。

保留策略与活动投递依赖要分开：尚被活动工作引用的证据需要可验证的稳定留存或显式过期结局，不能为了容量静默删除。B13 的未知原子暂存名不应自动删掉；应局限它的影响范围，暴露损坏原因并提供限定目标的恢复操作。底层对未知文件保持保护，观察层不能把通道损坏伪装成空通道。

## 4. 升级与历史兼容的设计

### 4.1 固定已发布格式，先保存真实字节回放基线

`demand-event-stream-commit.ts::applyDemandEventStreamCommit` 用当前 reducer 演进，再与持久化的 resultingStateDigest 比较。事件 upcaster 能升级事件形状，但不等于能证明旧状态摘要。`demand-event-sourcing-state-version.ts` 当前只支持 v1。

推荐 Q3 采用保留完整性校验、明确版本分派的路线：固定 v1 的验证语义，需要改变历史状态形状时新增状态模型版本和显式迁移，不删除校验来“兼容”。纯调度、取消、恢复接线、错误投影及准入改进尽量不改既有事件字节。新完成门可以约束未来的 complete，不应回头把已封存归档判成当时未完成。

golden 必须从旧构建实际写出的字节冻结。用当前 reducer 每次重新生成期望值没有兼容验证意义。原始私有归档可以继续在本地只读回放；公开 fixture 应在对应历史构建上用合成身份和文档生成，再冻结字节。不能在已经封存的文件里替换私人路径和 ID 后仍声称它是原始摘要的兼容语料。

应覆盖 publication、规划、投递、re-arm、结果、accept/rework、测试重跑、blocked 恢复、escalate 决策、continue、完成与取消，以及每段流的中间前缀。已有七份旧归档和前轮两份新归档通过的结果继续有效，本轮没有把它们改回“从未回放”。剩余缺口是这些证据尚未成为固定的持续回归门，以及未来格式策略未定。

### 4.2 托管文本使用历史渲染接缝

`wakeflow-managed-text-authority-transition.ts` 已有正确的 currentTargets 机制；断点在调用者只提供当前构建重新渲染的正文。marker 只能证明字节自洽，不能证明插件有权覆盖它。

建议为承诺支持的前序版本保留可按配置重算的 renderer/模板，送入现有 currentTargets；正常 reconcile 只接受当前或已知前序输出。R11 的对照验证了这个接缝能保留用户块外字节。动态配置含 ID 和路径，因此不能只登记一个全局固定正文摘要就宣称覆盖所有安装。

长期若用维护回执记住上次实际物化的组件、源配置、renderer 版本和正文摘要，必须把回执定义为受管的版本化资源，并说明从没有回执的旧工作区如何迁移。不能把用户文件自带 marker 升格为该回执。未知修改仍应给精确差异并阻塞覆盖。

### 4.3 版本号、运行身份和工作区目标身份各有职责

同一个 1.0.0 已对应不同字节。修正应从发布规则和可验证身份入手：每个对外版本不可变；manifest 明确版本、源码提交与构建身份；安装后比较宿主将加载的完整制品，而不是只读 package.json。当前未提交启动修复不能冒充一个已发布的新版本。

`resolveWakeflowArtifactIdentity` 只重读进程自己所在的目录；它正确检测原地覆盖，却不可能单凭这个事实知道另一个目录已经成为宿主安装目标。不能用摘要判断新旧，也不能把“旧路径读不到”当作“没有更新”。

设计应引入来自宿主安装状态的明确目标，或由一次升级计划选定并记录工作区的目标构建。该事实通过 host adapter 或版本化维护回执进入共享层；没有可信目标时显示 unknown。升级/降级应以选定目标的能力与兼容检查为准，不按目录 mtime 或最大版本号猜测。混用构建时准确指出本 server、目标构建和窗口间的差异，维护 apply 复验选定目标。

配置及维护 intent 也需要版本分派。当前恢复会用现代码重算旧计划，算法变化可能破坏恢复。短期可要求升级前结清事务并保留原构建供恢复；长期则保留旧 intent 的解析和执行规则。只在 intent 加一个版本字段、却仍用新 planner 重算，并不能解决问题。

## 5. 验收、需求续接和角色边界

### 5.1 一个验收解析器供发布、规划和完成共用

`requirement/decide.ts::derivePublishBlockers` 检查章节和确认；`tasking/decide.ts::parseAcceptanceCriteria` 只解析验收节里的顶层列表。章节存在不等于列表可用。bug/supplement 的必需章节表又没有验收标准，而实现任务必须有至少一个指向该列表的锚点。这解释了 R6，不是 Agent 填错了后续参数。

建议把无 I/O 的验收解析移动到共享的需求语义模块，由发布、规划与完成共同调用，避免 capability 相互依赖。对 requirement、bug、supplement，在确认摘要中列出实际解析出的 itemId 和条目数，发布前就拒绝零条目。是否支持表格应作为显式语法能力实现并测试；在实现前给明确格式错误，不能预览接受、规划拒绝。research 保持独立语义，不强迫它伪造实现锚点。

既有不可变包不能原地补标准。工具应给取消并重新发布/替代的合法路径，保留原包和失败记录。

### 5.2 完成必须核对全集，豁免必须显式

`tasking/decide.ts::deriveAnchorReferenceBlockers` 证明“所引用的标准存在”；`demand/lifecycle.ts::planTerminal` 和 `demand-verify-gates.ts` 没有证明“所有标准均已满足”。R7 直接展示了这两个命题的区别。

建议增加纯的 coverage 派生：从不可变需求包取得标准全集，用当前有效谱系的已接受实现锚点和当前测试代际已接受的逐步结果建立覆盖矩阵。复用现有谱系与 `currentTestTargetsOf` 选择逻辑，不能把 superseded 或历史测试的通过记录随意算进当前工作。规划过或报告自称完成不算已验收。

最小结果是逐条给出 implemented、tested、uncovered 及证据引用；controller-only 与 real-environment 分开显示。在 real-environment 下建议对每条标准要求有效的测试证据，Controller 判断“不适用”也应明确记录，不能把实现覆盖并集当作测试覆盖。该语义需在 Q8 中确认。

推荐默认阻断 uncovered；若允许豁免，则用附理由和需求条目引用的正式决定记录进事件流与归档，不以自由文本总结代替。preview、apply、status、verify 使用同一计算；apply 在提交前重新读标准、谱系和证据，防止 preview 后状态变化。新公共结果、决定或事件字段属于合同变化，实施前按文档系统形成 ADR。

### 5.3 续接与补充需求划清语义

现有 continue 保持原 authority，可保留历史；supplement 能携带新需求，却没有父工作的机器链接。建议以最小变化区分：同一需求标准内的优化或缺陷修正使用 continue；引入新标准使用新 supplement 包，并显式记录父 requirement/Demand 与基线。它可以保持独立生命周期，又能追溯原工作，不必把一个已经封存的 authority 静默改写。

awaiting-decision 时应先用现有 record-decision 恢复，或明确取消后另开需求。文档中的“直接认领补充包退出阻塞”与当前 pod-busy 约束冲突，应同步改正。research 和 indeterminate 的合法出口优先补齐到所属 skill，不应为文案遗漏新造一个状态机。

### 5.4 角色约束与防恶意隔离分开

R8 的含义是 server 不使用调用窗口事实约束 Controller 动作，并不是证明操作系统沙箱被绕过。带有正确 snapshotDigest 的请求只能证明客户端观察了某个状态，不能证明它有权作决定。

建议由宿主边界提供已验证的 workspace、windowId、binding generation 和 role，在执行器入口对工具权限做确定性检查；参数里的 windowId 或角色自报不作为授权。目录按角色裁剪用于降低误用和成本，执行时仍需同样的检查。初始化/重新绑定保留有界 bootstrap 能力，绑定变化使旧上下文失效。

必须先证明宿主能提供哪些身份。SDK 的 MCP sessionId 不天然等于 Codex chat ID；仅添加一个可由 Agent 自己填写的 JSON role 也无效。当前 `CODEX_THREAD_ID` 环境探针说明这份实现没有使用它，不代表所有真实宿主都保证给 MCP 注入了可信该变量。

若威胁模型包含能读写整个工作区的恶意产品 Agent，角色检查不足以保护共享文件；需要权限隔离或外部可信边界，单纯增加 HMAC 而把密钥留在同一可读目录也无效。Q5 应明确先保障合作 Agent 的分工，还是承诺对抗该类攻击。F10 的 recordedBy 是记录权威语义，不能作为这次调用者鉴权的替代，也不应误改为一个新的“采集者”字段。

## 6. 使用体验、成本和退出设计

工具入参应引用所属模块的实际 wire Schema，减少自由 JSON 让 Agent 猜结构。错误投影保留安全的字段路径、失败条件和下一步；继续不回显凭证、私人路径或完整原始输入。不要把 Schema 全文附在每个错误里。优先修维护 selection、需求 package 以及评审决定中最常遇到的分支。

响应默认给当前阶段、摘要、必要证据引用和下一责任；完整任务包或完整历史按需展开。服务端做评审校验时仍读取完整权威，不能因 UI 摘要而放宽安全检查。记录 tools/list 字节数、单步结果字节数、重复读入量和操作时延，分别归因，不把历史估计的 token 数当作本轮实测。

R13 的候选子集只说明目录裁剪有明显空间：Design 的 publish/inspect-board/status，Product/Test 的 record-evidence/import-result/status。实际权限表还需覆盖初始化、诊断及角色转换，不能直接拿这个最小集合当作完成设计。Controller 会话轮换应靠受管状态重建上下文，并在静默点验证旧绑定退休与新绑定注册，不把聊天历史当第二套状态。

`wakeflow-static-materialization-preview.ts::reconfigureTopologyChange` 明确只准拓扑新增。移除仓库不能通过放宽此检查单独实现。建议提供有序 detach 计划：检查活动 Demand/claim 和 worktree → 处置并退休相关窗口 → 仅撤去已知所有权的集成块及配置项 → 激活新配置 → 验证归档仍可读。用户改过的正文保持冲突，不做无条件删除；历史归档里的 repository/window 身份保留。重开旧 Demand 若涉及已移除仓库，应明确要求重新映射或拒绝，不能悄悄恢复托管。

Git 分支、检出和宿主聊天的清理仍由 Agent/host adapter 执行，并回读实际结果。前轮完整清理是维护者完成的真实验证，不等于插件已经有自动 detach 或一键退出功能。

## 7. 可实施的顺序与完成门

| 批次 | 具体范围 | 合同与决策边界 | 修复后必须成立 |
| --- | --- | --- | --- |
| 1 | MCP SDK v2 取消传播、关闭信号与提交点语义 | 优先内部执行上下文，不改用户请求；两个宿主 composition root 同步 | 等待中取消不提交；提交后取消不破坏已提交事实；真实通知与落盘同时断言 |
| 2 | Demand 候选观察/恢复接线，board/projector 失活锁恢复 | 保留事件字节与 Foundation 精确删除边界；公共诊断/恢复形状变化须 ADR | 本轮四个中断用例可走公开恢复；重复恢复幂等；活动/unknown owner、未知文件保持保护 |
| 3 | create/continue/close 的 pod 互斥与配置复验 | 复用资源锁；并发模型及锁序写入 ADR | 同 pod 双创建恰一成功；不同 pod 可并行；关闭交错与崩溃恢复可复现 |
| 4 | 统一验收解析、全集覆盖、明确补充路径 | Q6/Q8 决定发布要求、阻断与豁免；扩展事件前先定兼容 | 三种不可规划包在发布前被拒；缺 9 条标准不能无记录完成；旧归档仍可读 |
| 5 | 固定历史回放基线、历史 renderer、升级身份及发布规则 | Q2/Q3；版本变化、构建、提交、tag、发布、缓存刷新分别处理 | 旧字节回放；块外正文不变；新旧目录并存与旧目录缺失不被误判 current |
| 6 | hook 分片、有界查询、损坏定位 | 涉及记录路径/读写合同；旧目录的读取与迁移同时设计 | 超过当前上限仍能精确找目标记录；不完整读报 unavailable；未知条目不被误删 |
| 7 | 角色上下文、Schema/错误、响应摘要、会话轮换 | Q5 与宿主可信身份事实先明确；目录裁剪不冒充鉴权 | 产品窗口不能决定 accept/complete；旧绑定不能继续用；错误点名字段；指标可复测 |
| 8 | 部分 pod 范围和 detach/退出 | Q9/Q10；保留历史身份与用户所有文件 | 有活动工作时阻止移除；干净退出后归档可读；外部资源清理有真实回读 |

前四批是本次实测支持的正确性优先项；第五批是对外发布前的兼容门。单批先做最小连贯补丁和 focused 回归，再更新所有真实生产者、消费者与所属 skill，生成双制品，跑 `npm test`、`smoke:artifacts` 和 `git diff --check`。不把所有批次揉成一个无法独立审阅的大提交。

已有 Q1 的“尚未跑通真实 Codex 会话”前提已被 §13.138/139 的证据覆盖；剩下是发布定位与明确支持范围，不应继续把它当作需要重做同一正常流程的理由。需要改变已接受约束的选择仍是 proposed，本轮没有借测试授权默认接受它们。

## 8. 交付与后续验证使用方式

私有测试工作区保留 `harness/`、`evidence/`、`logs/`、`cases/`，含原始失败输出和纠正后的结果。复现脚本通过源码仓库根参数定位 `.build` 测试辅助模块与当前制品；运行前需要本仓库已完成类型编译，不能把 `.build` 缺失误判成产品失败。它们目前是审阅诊断程序，实施补丁时应把“缺陷存在”断言改为目标行为并移入对应 tests owner，保留真实子进程故障注入能力。

本轮没有提交、推送、打标签、发布或刷新安装缓存；原有未提交启动修复保留。本地 main 与本地 origin/main 在基线时一致，未用远端 fetch 把这个事实扩展为“远端没有新提交”。除本审阅文档与事实登记更新外，生产源码、测试、制品和安装输出保持基线。
