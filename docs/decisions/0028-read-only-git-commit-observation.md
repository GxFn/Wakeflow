## 背景

- 实现目标交回结果时，报告里的 `repositoryChange.commits` 是目标自己申报的提交号。没有任何代码拿它去对仓库：`commitExpectation` 只核对申报的处置；`commit` 类证据只核格式与"仓库已配置"，记下的是 `{repositoryId, commitOid}` 的投影（`src/governance/evidence/managed-evidence-source-projection.ts`）。
- "这个提交改了什么"因此靠 Controller：手工导出 diff 写成文件、预览、应用，再登记成 `diff` 类证据。1.3.1 的现场里，一条带一次返工的小 Demand 有 12 次记证据的调用；测试工作区 7 份归档的 102 个事件里 36 个是证据记录，每条是一次预览加一次应用。
- "已接受的结果合并了没有"只能比分支尖端（`src/governance/observation/active-projection-facts.ts`："没有对象图不能判祖先"）。
- "Wakeflow 不启动 git"在多处文字里出现，但字面上并不成立：运行时已经在 `src/foundation/git/git-ignore-observation.ts` 里以固定的只读参数启动 `git check-ignore`，清掉 `GIT_*` 环境变量，限制输入、输出与 5 秒超时；文件头写明"未来 repository、worktree 与 status 观察应继续作为 `foundation/git` 下的独立能力"，并且只在出现第二个真实的进程协议消费者之后才提取共享的 runner。助手脚本也早就在跑 `git worktree`。
- 业界的旁证：主流平台的记录权威是 git、PR 与 CI；代理自述"做完了"而实际没有，是有量化记录的常见偏差（见调研报告，未入库）。

## 问题

提交是按内容寻址的事实，Wakeflow 却把它当作一段要由代理转述的声明。不改的话，评审的每一轮都要为"证明提交存在、说明它改了什么"付出若干回合，归档里关于实现的证据也始终是代理手工制作的文件。

## 决定

1. **能力的位置与形状。** 在 `src/foundation/git/` 下新增"提交观察"这一个具体能力，与 `check-ignore` 并列。它是第二个进程协议消费者，所以这一次提取两者共用的 runner；runner 只接受代码里写死的子命令表，不接受调用方传入的参数数组，不成为通用的 Git 客户端。
2. **读什么（封闭清单）。** 对一个仓库检出与一个或两个提交号，只取这些事实：提交是否存在且是提交对象；它的父提交；它相对第一父提交改动的路径与状态（不做重命名推断）；它的补丁（统一格式、不经外部 diff 驱动、不经 textconv）的摘要与字节数；一个提交是否是另一个的祖先。不读工作区是否干净，不读未提交的内容，不联网，不写任何东西。
3. **怎么启动。** 沿用已有做法并补齐：清掉 `GIT_*` 环境变量；固定的只读参数；关闭可选锁、文件系统监视器、外部 diff 与 textconv、分页器与终端提示；工作目录是经根目录约束解析出来的仓库检出（pod 的任务用它的检出）；每次调用有超时、输出上限与条目上限。具体的参数表写在代码里，由测试钉住，测试仓库里放带恶意钩子、外部 diff 驱动与 fsmonitor 配置的样本。
4. **什么时候读。** 实现目标导入结果的那一次调用里（那是目标窗口的调用，不占 Controller 的回合），Wakeflow 对报告里的每个提交做观察，并把结果作为提交证据记进 Demand。评审检查时发现还没有观察过（旧记录、当时拿不到结论）就补一次。状态读取里只对"已接受、记录了分支"的结果做祖先判断。
5. **记什么。** 提交证据在现有的 `{repositoryId, commitOid}` 之外带上观察到的事实：父提交、改动路径的清单（有条目上限，超出时记总数与截断标记）、补丁的摘要与字节数、相对任务基线是否为后代。补丁正文在一个大小上限之内随证据保存，超出时只留摘要与清单。归档因此在上限之内自足：产品仓库的历史此后被改写，归档里仍然看得到当时评审的是什么。
6. **与申报不一致时。** 报告里的提交号在仓库里不存在：导入被拒，原因点名那个提交号，目标改正报告后重交。存在但不是任务基线的后代、或 `commitExpectation` 与观察到的事实不符：照实记进证据与评审单元，由 Controller 判断，不拒绝。
7. **拿不到结论时。** git 不可用、超时、仓库读不了：这一项记为未观察并带原因，导入照常完成，评审单元里显示"提交未核实"。Controller 仍可以走现有的路——自己核对并登记证据。不因为观察失败制造新的死路。
8. **`diff` 类证据的位置。** 保留，用于 git 里没有的材料（核对脚本的输出、截图、日志）。Controller 不再需要为已提交的改动导出 diff。
9. **措辞。** "Wakeflow 不执行宿主效果"不变：读本机仓库的对象不是宿主写效果，也不是替 Agent 操作窗口。凡写着"不 spawn git""不读 git 对象"的头注与 Schema 描述，改为"只经 `foundation/git` 的封闭只读能力读取"，并指向本记录。pod 检出回执仍由 Agent 交回 `git worktree list` 的原文，这一版不改。

## 后果

- 代码：`src/foundation/git/` 的 runner 与提交观察；结果导入、证据清单、评审单元、状态里"已接受未合并"的判定；新增的拒绝原因进拒绝参考（`refusals:build`）。
- 合同：提交证据清单的 Schema 加观察到的事实（可选成员，旧记录照读）；评审单元带"提交是否已核实"。
- 测试：读取器在真实的临时仓库上的组件测试，含恶意配置样本、超时与截断；导入时的三种情形（相符、不存在、拿不到结论）；两个宿主的场景链各补一条。
- 文本：证据参考里"导出 diff 再登记"的段落删去，换成"已提交的改动由 Wakeflow 记下，你登记的是你自己核对的输出"。这是净减少。
- 架构规则：进程端口仍只在 foundation；领域层不直接启动进程。
- 门：动了 `src/foundation`，走完整门。

## 未决问题

- 补丁正文的大小上限取多少（倾向 1 MiB 一个提交），改动路径清单的条目上限取多少。
- 浅克隆、子模块、合并提交相对第一父提交的补丁是否足够——第 1 段的测试里各放一个样本再定。
- 状态读取里的祖先判断每次都做还是缓存到下一次流版本变化。
