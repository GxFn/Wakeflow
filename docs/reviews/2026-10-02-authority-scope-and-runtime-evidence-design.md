## 1. 已经确认的事实

| 反例 | §13.145 基线的实际结果 | 说明及边界 |
| --- | --- | --- |
| D1：旧调用捕获配置 C1；公开 pod preview/apply 写入 C2 并刷新；旧调用随后刷新窗口投影 | 新配置下先是 0 条修复操作；旧调用返回 refreshed，写了 4 个文件；再次按 C2 预览出现 4 条修复操作 | 使用当前生产刷新器和真实文件系统。绑定锁正常工作，但不能保护传入的旧配置。没有创建宿主聊天或 worktree |
| D2：活动投影读取 C1、打开 Ledger 后暂停；公开 reconfigure preview/apply 完成 C2；恢复旧刷新 | 新状态页先包含 C2 摘要，随后被替换成 C1 摘要 | 调度暂停位于 projector 锁之前；生产渲染、发布和配置事务均实际执行。证明问题跨越两类投影 |
| D3：目标 MCP 保持旧构建；同路径安装完整新制品；新观察器收到 `SessionStart/source=compact` | 新 Controller 将该窗口判为 current，目标 MCP 自报仍为旧构建、磁盘 changed | 两个真实生成 MCP 进程与一个真实观察器进程；会话关联及 hook 输入为合成，未声称执行过真实桌面 compact |

Codex 的 [SessionStart 文档](https://learn.chatgpt.com/docs/hooks#sessionstart) 明确包括 startup、resume、clear、compact。它描述会话事件，不提供“此会话所有 MCP 和技能均重新加载”的证明。[公共 hook 输入](https://learn.chatgpt.com/docs/hooks#common-input-fields) 还说明子代理 hook 使用父 session_id，因此该字段也不能直接充当独立进程实例标识。

上轮两个真实聊天没有新 SessionStart 的具体原因仍未知。D3 证明的是当前版本判定依据不足；它没有证明那两个事件是宿主未触发、超时或写入失败。

### 设计基线的断点

- `configuration/wakeflow-config-authority-snapshot.ts` 明确规定快照不保证返回后仍然新鲜；窗口刷新却继续接受任意 `request.config`。ADR-0016 只保护绑定 inventory。
- `governance/observation/active-projection-refresh.ts` 在 projector 锁外读取配置和 Ledger 根，再把捕获值传入锁内的渲染闭包。闭包在锁内执行，不代表闭包捕获的数据也是锁内取得的。
- `capabilities/endpoint/service.ts::assertUnchangedUnderLock` 复验绑定和部分 claim，没有把当前配置作为同一作用域的条件。配置 writer、维护 gate 与运行时 writer 的互斥边界仍彼此分离。这是额外的权威变更审查范围，不把 D1/D2 的投影反例夸大为已经复现了错误业务提交。
- `entrypoints/wakeflow-hook-observer.ts` 读取观察器所在目录的 manifest，`workspace-observation.ts` 将最近的 SessionStart 摘要按 session_id 聚合，`observation/service.ts::artifactStateOf` 再把它与当前 Controller 进程摘要比较。证据的主体在这三层之间发生了变化。
- Foundation 的原子替换在检查 expected 后执行 rename；模块注释已声明它不代替领域互斥。单文件安全发布不构成多份权威事实的原子条件提交。

## 2. 根因：事实的内容正确，不代表使用范围正确

这组问题缺少三个边界：

1. **有效期**：配置快照、绑定代际、claim 和 Demand 修订在什么时间范围内可用于提交？不可变对象只保证对象没被修改，不保证外部权威没变。
2. **提交范围**：一个动作依赖哪些事实，这些事实的 writer 是否参与同一个互斥或围栏协议？仅锁输出文件无法保护渲染依赖，仅在写前再检查一次仍可能存在检查后的窗口。
3. **证据主体**：记录证明的是观察器、MCP 进程、宿主会话、安装目标，还是指令文本？同为 SHA-256 不能让这些主体相互替代；不同摘要也不能判断升级方向或协议不兼容。

应分别要求：业务权威变更在明确的提交边界内成立；派生视图可以暂时过期，但不能长期被延迟旧请求覆盖或被当作权威；远端运行事实只能由相应主体的证据支持。

## 3. 工作区操作作用域

建议保留现有资源锁，引入统一的、跨进程的工作区变更准入边界。普通运行时变更共享准入，配置或共享布局维护独占准入。这里的“共享”允许不同 pod 同时执行；同 pod、绑定、claim、事件槽等局部约束继续由各自 owner 负责。

| 操作 | 准入 | 作用域内必须完成 |
| --- | --- | --- |
| status、verify、inspect、preview | 只读；不创建准入记录 | 观察事实及读完整性；变更或无法读全时报告 unavailable。结果不是后续提交许可 |
| Demand、任务、投递记录、评审、证据、绑定等变更 | 共享运行时准入 | 重新加载当前配置、取得领域资源边界、复验预期、提交及必需结算 |
| pod 创建/关闭、reconfigure、共享布局/资产维护 | 独占结构变更准入 | 关闭新 writer 准入，等已进入 writer 退出，重算计划，执行现有事务或恢复 |
| 派生刷新 | 独立的新鲜观察作用域，按发布对象串行 | 在 publisher 锁内取得其有效来源；不得沿用已结束命令的配置对象 |

“结构变更”专指配置权威、共享布局和解释这些资源的协议；不是把每次 Demand 归档中的目录操作都升级成全工作区独占。

### 协议必须解决的细节

- 运行时取得共享许可与维护关闭准入必须通过同一个短临界区完成；“先看 maintenance gate 不在，再开始写”有窗口，不能作为实现。
- 维护发出关闭准入请求后，不再接纳新 writer，避免持续负载让维护饥饿；已经获准的 writer 可以提交或安全中止，不能在持有领域锁时再等待维护退出。
- 短准入锁只用于登记、关闭与释放，不在其内部等长操作。维护等待活跃 writer 排空时，也不能阻止它们释放许可。
- 嵌套领域调用借用同一作用域；禁止持共享许可再升级独占，禁止隐式重入。发布锁应在业务资源锁释放后取得；提交后刷新另行取得新作用域，不能因重建失败否定权威提交。
- 维护进程退出不等于维护事务结束。既有 intent/journal 未结时继续关闭普通 writer，只有所属恢复流程能重开准入。
- 每条 writer 入口及 recover 路径都必须纳入；仅修改 MCP 正常 apply 外壳会漏掉配置原语、恢复和内部回调。

不新增业务状态机、全局事件流或后台调度服务。准入只回答“此刻哪些操作可以进入”，业务接受、归档和恢复事实继续由现有 owner 持有。

### 为什么选这一方案

| 方案 | 判断 |
| --- | --- |
| 每个点继续补一次重读或摘要检查 | 可缩小窗口，不能共同排除配置/维护 writer；不作为整体方案 |
| 全工作区所有命令都用一把长独占锁 | 容易理解，但会取消已确认的不同 pod 并行，并放大慢观察和恢复的阻塞；不作为目标设计 |
| 共享运行时准入 + 独占结构维护 + 现有领域锁 | 能表达配置稳定区间，同时保留不同 pod 的运行并行；推荐，但必须先完成下述 owner 与混合版本条件 |
| 全工作区 MVCC、版本目录和新的通用事务管理器 | 会引入第二套权威与大量迁移，不是现阶段所需 |

### 不能省略的前提

当前锁 owner 主要依赖 PID。把这种判断直接用于共享许可回收，会扩大 B7 的影响。活跃 owner 不可回收；PID 复用、权限不足、工作线程与宿主重启必须有可验证的进程实例判定，无法证明时保持 unknown。超时只是等待预算，不能证明 writer 已停止；过期租约若仍允许旧进程提交，也不能作为围栏。

具体跨平台 owner 获取与持久准入记录布局仍需实现前评审及真实进程测试。不能因为抽象模型通过就称文件系统协议已正确。Foundation 可提供通用锁/实例原语，资源路径、维护 intent 和恢复权限由 Kernel/Workspace 的 owner 组合；不把宿主业务规则放入 Foundation。

## 4. 派生发布统一合同

普通刷新只接收根、宿主 profile 和有效作用域，不再让调用方传入一个自称“当前”的配置对象。进入 publisher 锁后重新取得当前配置、相应 Ledger 根和绑定/业务版本，纯渲染器由这些已解析输入生成字节。投影记录来源指纹，观察方可判断它相对哪一份配置和业务修订有效。

这里必须区分两个合法来源：

- **运行时刷新**使用已经提交的当前配置，晚到请求重新读当前值或放弃，不能把旧快照重新发布。
- **维护过渡发布**可以使用 intent 中尚未激活的目标配置。当前维护顺序是布局/资产先准备、Config 最后激活；把所有调用一律改成读取当前磁盘配置会破坏这个顺序。因此它必须持有独占的过渡作用域，绑定 operationId、source/target 配置及计划摘要，按现有 journal 恢复。

两种效果入口可共用纯渲染器，不能共用一个没有来源区别的 `config: unknown` 发布授权。preview 的渲染结果只供审阅；apply 在有效作用域内重算，不把 preview 快照当成保留的锁。

投影允许在业务提交之后、重建之前暂时过期。正确标准是：过期能被识别，不能成为业务准入依据；写入停止且一次刷新成功后应收敛到当前权威；异常退出后可由既有 reconcile 重建。无需为了避免一切短暂过期而锁住全工作区所有读写。

## 5. 运行证据按主体拆分

| 事实 | 有效证据 | 不能据此证明 |
| --- | --- | --- |
| 当前调用由哪份 MCP 实现服务 | 该运行进程固定的 build identity、实例标识及实际工具响应 | 另一个窗口的服务版本、模型已读的技能版本 |
| 某次 hook 的来源与写入结果 | 观察器自身身份、事件/source、记录与诊断 | 同 session_id 的 MCP 已重启；特别是 compact 或子代理事件 |
| 宿主当前选中的安装目标 | 宿主安装状态或明确的升级目标回执 | 目录中最大版本、mtime 或摘要排序不能代替选择 |
| 当前任务所需协议是否满足 | 冻结任务合同的需求与已验证能力/格式兼容关系 | 任意不同字节摘要都不兼容；相同版本号就兼容 |
| 指令/技能文本来源 | 被要求读取的不可变指令包引用及其版本 | 无宿主证明时，不能保证模型内部上下文整体已更新 |

`SessionStart` 留作会话活动与启动位置证据，不再承担全部运行就绪判断。缺少它时只能报告未观察到；不能推断“窗口启动错了”，也不能把新 Stop 或一次重新出现的 SessionStart 自动折算成 MCP 已更新。

版本判断至少分别呈现 serving process、selected installation、hook evidence、required protocol。差异定位到相应主体：实际服务不兼容才要求重连/重启该服务；hook 通道未知则补查通道；安装不可读则检查安装；协议兼容且有充分证据的组件不因其他组件字节变化而被统称过期。

兼容关系必须明确声明并测试，不能仅因 Schema 相同就默认兼容；必要的正确性修复也可以构成最低实现要求。验收某次补丁时，必须核对选定目标构建，协议兼容不能代替“修复已加载”。

完整 workspace verify 与单次业务准入也要保持职责区别：完整检查缺少所需事实就报告 unavailable，单次动作按自己的必需事实判断，不能把一个笼统 ready 标志变成所有操作的共同前置条件。必要的身份或版本事实未知时，阻止依赖它的动作并指出缺项；不能靠放宽门或要求反复全局重启掩盖缺项。

### 实例和信任边界

进程实例标识不等于 PID，也不等于长期复用的 session_id。若要把某个进程的就绪回执绑定到某个窗口，必须有宿主确认的调用主体或可校验的 transport/readback 关联；新鲜性还要钉住绑定代际及探测范围。当前仓库没有这样的可信调用上下文，不能假定一个环境变量、自报角色或 Agent 转述已经提供了它。

宿主不能提供关联时，只报告“本次调用的服务身份已知，目标窗口身份尚不可证实”。不要先添加 ready 字段再用弱证据填满，也不要把这项运维一致性设计写成已解决 Q5 的抗恶意鉴权方案。

### 诊断缺失事件

应区分宿主是否调度、观察器是否启动、是否收到事件、是否定位到工作区、是否写入。现有观察器能够报告部分固定错误，但无法靠自己的沉默证明宿主未触发。

保留非阻塞 hook 的原则，扩展现有脱敏 outcome/诊断：记录已知阶段、事件类型/source、观察器构建和失败原因，不保存 prompt、transcript 正文或任意环境变量。工作区定位成功后可把有限诊断留在所属私有运行区；定位前的失败或宿主超时仍需宿主执行回执。缺少外层证据时保持 unavailable，不伪造 hook、不静默重绑、不自动新建聊天。

## 6. 部署与协议演进是修复的一部分

构建输出应在其身份路径下不可变。同一发布版本对应固定字节，运行进程固定到一个构建，升级选择新目录，旧目录保留到旧进程退出和必要恢复结束。构建身份、制品清单摘要、实现兼容版本分别有含义；构建时生成身份要避免“把 manifest 摘要写回 manifest 所覆盖文件”的循环定义。

当前启动时读取的 manifest 也只是那个时刻的磁盘标签。若目录允许在模块加载期间改变，它本身不能证明已加载模块全部来自同一清单。不可变构建路径和加载前的完整性检查是该证明的前提；不能仅把“启动时读了一次”命名为强证明。

仅比较进程脚下的 manifest 仍只能诊断该路径，不能知道宿主是否已选择兄弟版本。安装目标必须来自 host adapter 或明确升级回执；没拿到就显示 unknown。

新的准入协议也不能自动约束旧 writer。只增加一个旧代码忽略的 sidecar 标志没有保护作用。启用前必须排空在途操作、结清既有事务并停止不参与新协议的 writer；协议/配置版本边界需要让不支持的旧实现拒绝进入。仅升级配置版本也挡不住已经加载旧快照的在途调用，不能省略排空与停用步骤。

迁移应单独 preview/apply/recover，保存原始数据与回执；未完成的旧维护 intent 按原协议和原构建恢复，不能交给新 planner 猜测。初次迁移建议要求活动业务与未结日志已清，旧归档按原版本读取、字节不改。若需要带活动 Demand 迁移，另行验证其冻结配置、任务包和门；本提案不承诺隐式兼容。

这涉及 C7/C11/B8 的共同边界，不能随一个投影补丁暗中完成。版本 bump、缓存切换、提交和发布仍分别遵循既有授权。

## 7. 分层落点与实施顺序

| 顺序 | 交付 | 主要落点与完成条件 |
| --- | --- | --- |
| 1 | 固定事实合同与反例 | 把 D1/D2/D3 转为目标行为的回归；修订观察结果/诊断及所有消费者，先消除无证据的 current 声称 |
| 2 | 统一投影来源 | `active-projection-refresh.ts`、window-runtime projection 的 inspection/maintenance；运行时当前配置与维护目标配置使用不同作用域，纯渲染继续共用 |
| 3 | 验证基础准入与 owner | Foundation/Kernel 的跨进程原语、统一锁序、取消与实例恢复；共享 writer 并行、维护排空、unknown owner 保守保护有真实进程证据 |
| 4 | 全入口采用作用域 | 配置 writer、维护事务、pod、endpoint 及全部运行时 apply/recover；加载上下文和决定在作用域内，既有领域锁不被替代；发布阶段不能存在遗漏 writer |
| 5 | 版本化启用与现场验收 | 明确协议迁移、构建固定及 host 目标；双制品、旧历史、原生多窗口及中断恢复一起验证 |

这是一个目标设计的分段落实，不是给每处缺陷发明不同规则。第 3/4 步完成前，不把前两步宣称为跨资源并发已经闭合。MCP/技能/Schema、Claude helper、两宿主 profile 和文档要随所属合同一起更新。

## 8. 模型和必须补齐的验收

有限模型枚举了两个运行 writer 与一个配置 writer：无准入时 30 条完整调度中 16 条出现提交依据已变；单独再检查一次时 140 条中仍有 58 条；共享运行时/独占维护模型的 526 条完整调度中未出现该问题，并实际到达两个 runtime reader 同时持许可的状态。这些数量来自不同模型的合法调度集，不能作为故障概率比较。

投影模型中，锁外捕获配置的 11 条完整调度有 1 条最终回退；把当前配置读取移入 publisher 锁后，6 条完整调度没有最终回退。该性质假定配置 writer 完成其后续刷新；崩溃留下过期缓存是单独的恢复场景。

以上是抽象设计实验，不证明磁盘协议、取消、进程死亡或混合版本已实现。正式验收还必须覆盖：

- 三个已复现反例，以及维护 source/target 配置激活顺序；零写观察与多次修复幂等。
- 每个 apply/recover 入口与维护的交错；不同 pod 同时工作，同 pod/绑定/claim 的原有围栏仍有效。
- 准入关闭前后、许可登记后、业务提交前后、维护 intent/journal 各阶段的 SIGKILL、取消与重启；不回收活跃或未知 writer。
- PID 复用、工作线程退出、EPERM、平台无法取得实例事实；明确降级而不以超时偷锁。
- 新 hook + 旧 MCP、新 MCP + 旧/缺失 hook、compact、子代理、绑定换代、重复/乱序记录、不可读 manifest、兄弟版本目录及两个宿主的不同构建。
- 旧 writer 与新协议并存的拒绝、升级中断恢复、v1 事件与归档字节保持；未验证的平台/宿主明确标注。

§13.145 设计评审时，运行代码仍是已通过 1198 项整门的基线；当时的反例断言通过表示缺陷复现。本次实施不改写那份历史证据，正向验收另记于 §13.146。


## 9. 已接受设计的首轮实现

- Foundation 新增共享/独占文件许可。短 latch 串行登记与关闭准入，等待中的 writer 保留独占请求，reader 可以独立释放；只回收已证明不活跃的实例，未知文件、未知 owner 与旧格式同 PID 残留保持阻塞。锁 v2 加入进程出生摘要和模块 registry 标识；macOS 使用 boot session 与进程启动时间，Linux 使用 boot ID 与 start ticks，事实不可得时保持 unknown。macOS 时间粒度相同不能证明旧实例已退出；工作线程及其他平台没有新增可靠的死亡证明。
- Kernel 在命令打开配置和领域上下文之前取得作用域，退出前完成主体、结果边界与上下文关闭；嵌套调用只能借用同一工作区的活跃作用域，不能从共享提升为独占。领域锁保留，不同 pod 的正常写入仍并行。内部回调必须等待其拥有的工作，未引入通用子任务排空器。
- 维护 gate 持有独占作用域，未完成 intent/journal 在进程退出后仍阻断普通 writer。pod 结构操作独占，普通运行时与派生刷新共享。单调的私有权限收紧仍使用原有精确节点证明，不改业务权威；hook 观察及宿主传输不变成业务 writer。
- 活动投影在 publisher 锁内打开当前配置与 Ledger；窗口刷新移除 `config` 输入，在绑定发布锁内读取当前配置。维护发布继续使用既有 intent 的目标配置。提交后刷新借用尚未结束的命令作用域，独立调用则新建共享作用域；每轮都重读当前来源。
- 当前配置为 v2，v1 Schema 冻结并保留读取/表示。公开 `reconfigure` 的 v1→v2 路径只允许两个协议身份字段变化，要求操作者明确确认旧 writer 已停止，并检查活动 Demand、claim 和事务残留。确认是外部事实声明，不是 Wakeflow 自行证明的停机。旧 v1 intent 和已退休 intent 的 v1 terminal journal 不由新构建完成；恢复前的 Foundation 精确暂存收敛仍可能处理协调残留，不应描述成整个 recover 零写。
- status/verify 结果升级为 v2。hook 摘要明确标为 `lastObservation.observerManifestDigest`；已绑定窗口的 MCP/指令版本缺乏可信宿主关联，统一为 `runtime.status=unverified`，完整 verify 因此可以是 unavailable。该结果不会自动产生重启、重绑或重建聊天的动作。自身 MCP 的清单缺失/变化则单独报告，并在变更分派前拒绝执行。
- 新增只读 `install:check`：校验候选制品与目标版本目录，拒绝同版本不同字节覆盖。它不是安装器、目录保留或原子发布；实际安装必须使用新版本目录和 create-only 发布，保留旧构建用于既有进程及恢复。本轮未修改 release version 或安装缓存。

**尚未完成的目标**：完整不可变加载证明、宿主选定兄弟版本的可信关联、窗口与服务实例的可信绑定、技能上下文加载证明、hook 调度/超时的宿主级诊断，以及所有平台、每个持久边界的强杀矩阵。启动清单摘要和写前 tripwire 只报告本路径事实，不是全树加载证明。此前两个原生聊天没有 SessionStart 的具体原因仍未知。v2 原生多窗口激活与旧工作区升级必须在新版本安装和真实停机确认后进行；不能拿生成子进程实验替代它们。


## 10. 新工作区基线裁决

用户随后要求新建测试环境，将当前实现作为首个支持版本，不再考虑旧本地文件和结构升级；见 [ADR-0018](../decisions/0018-current-workspace-baseline.md)。上文 v1 兼容和迁移实验保留为历史记录，已不属于当前运行合同。移除双版本配置读取、迁移 blocker/确认字段、旧 intent 特例与锁 v1 解析；保留当前协议标识、操作作用域、证据分离及同格式维护恢复。候选版本使用用户要求的小版本 1.1.0-rc.1。
