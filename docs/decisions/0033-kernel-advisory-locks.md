## 背景

- 今天的锁是"独占创建一个带属主记录的文件"。记录里有进程号、线程号、令牌与进程出生时刻的摘要；释放时按节点精确删除并同步父目录。持有者死了没有人知道，要靠下一个获取者读记录、查进程表判断"确实不在了"，再把锁文件连同它旁边的暂存清掉。
- 这套做法的代码：锁原语 937 行、读写作用域 329 行、维护门的残留处理 188 行；foundation 之外 12 处"在锁内执行"，多数前面有同样的两步——查看、属主已死就退役——共 14 处查看、12 处退役。名字里带 lock 的测试 20 个文件、2,909 行。
- 它留下的隐患登记在 L10：进程号被复用时判不清属主；两个进程同时清同一把死锁会出现两个持有者；按记录命名的锁没人再拿、死锁文件永久留下（账本在工作区仓库里时成为 Git 未跟踪文件）；读者租约只有攒到 64 个才清；释放时删除没落定就跳过同步；首次初始化被死锁文件挡住。ADR-0032 补记二为了掉电之后的残留范围，又给锁分了两档落盘。
- 这些全部来自同一件事：**持有者死了，锁还在。**

## 核实过的事实（Node 24.22、APFS 本地卷，2026-11-25）

打开文件时带独占锁或共享锁的标志（非阻塞），内核在这个打开的文件描述上记一把咨询锁：

- 别的进程持有独占时，独占与共享都被拒（`EAGAIN`）；共享与共享并存；有共享时独占被拒。同一个进程里第二次打开同样受这些规则约束。
- 关闭即释放；持有者被强杀之后立刻拿得到。
- 持锁期间启动的子进程不继承这把锁（父进程关闭之后，子进程还在跑，别人立刻拿得到）。
- 锁跟的是文件节点，不是路径：锁文件被删掉之后，新建的同名文件可以在旧节点仍被持有时拿到锁。拿到之后比较"手里的节点"与"路径现在指向的节点"能看出来。
- 路径上是符号链接时，带不跟随标志的打开被拒。
- 一次"拿、放"约 0.02 毫秒，不同步任何东西。
- Node 的常量表里没有这两个标志，要自己按 macOS 的数值定义。

公开做法：Python 的 `filelock` 与 Tor 的 `fslock-guard` 用同一做法；两者都在拿到锁之后比较节点、对不上就重来，后者明确规定只有持有者才可以删锁文件。网络卷上的行为随系统版本与服务器而变，公开的报告互相矛盾。来源见文末。

## 决定

1. **锁 = 在一个常驻文件上持有内核咨询锁。** 一个原语：给定锁文件、模式（共享或独占）与要执行的操作，非阻塞地打开，被拒就等一小会儿再试，到期报超时；拿到之后执行操作，结束时关闭。没有属主记录，没有"查看"与"退役"。
2. **锁文件只建不删，名字是一个封闭的集合。** 全部放在私有目录 `.wakeflow-local/runtime/locks/` 里，权限位 0600，内容只有一行供人看的进程号。十二个名字：

   | 锁 | 取代今天的 | 模式 |
   |---|---|---|
   | 维护的门 | 维护门锁 | 独占 |
   | 作用域的门、作用域 | 操作作用域的闩锁、写者锁、读者租约 | 见决定 4 |
   | 活动投影 | 投影锁 | 独占 |
   | 看板 | 看板索引锁与按需求包的认领状态锁 | 独占 |
   | pod 变更 | 按 pod 的变更锁 | 独占 |
   | Demand 发布 | 按 Demand 的发布锁 | 独占 |
   | 账本记录 | 按记录的发布锁 | 独占 |
   | 绑定登记 | 绑定登记锁 | 独占 |
   | 配置权威、`.gitignore` 重组、程序指令重组 | 工作区根的三把锁 | 独占 |

   工作区根、账本目录与 `.wakeflow-active` 里不再有任何锁文件。
3. **按名字分的锁合并成每类一把。** 看板、pod 变更、Demand 发布、账本记录四类今天按需求包、按 pod、按 Demand、按记录各有一个文件；合并之后同一类的两次操作先后进行。这个量级的并发下差别是几十毫秒，换来的是名字集合封闭——不删文件，就没有"删了之后两个人各拿一把"的那个竞态，也没有越积越多的锁文件。同一个进程重入同一把锁是程序错误，原语用进程内的登记当场报出来，不等超时。
4. **操作作用域用两个文件做出"写者优先"。** 普通命令：对"门"拿共享、执行准入前的检查、对"作用域"拿共享、放开"门"、执行、放开"作用域"。维护：对"门"拿独占并一直持有（新的命令进不来）、等"作用域"的独占拿到（在场的命令走完）、执行、全部放开。闩锁、写者锁、每个读者一个租约文件、数到 64 再清、准入目录的清点都不再存在。
5. **维护的门也换。** 维护"没做完"的记号是事务目录里的意图文件，不是门：进程死在"拿到门、还没写意图"之间，今天留下一把死门锁要专门退役，换了之后什么都不留下。门只表示"此刻有一次维护在跑"。
6. **持有者死掉不再留下锁，所以"清死锁"整套删掉。** 今天清死锁时顺带恢复受保护文件的暂存，只有四处这样做（配置、程序指令、`.gitignore`、活动投影的索引）；改成这四处每次拿到锁之后先恢复一次，不再取决于有没有死锁。别的锁今天只清锁文件自己的暂存，那种暂存不再存在。
7. **拿到之后核对一次。** 手里的节点必须是路径现在指向的那个普通文件、属主是当前用户；对不上（有人删了或换了锁文件）就关掉重来。打开时不跟随符号链接。
8. **不支持的卷拒绝，不退回文件锁。** 每个进程第一次用到锁时自测一次：拿着独占再开一次，第二次必须被拒。打开报"不支持"或第二次居然成功，都以点名的原因拒绝（`lock-unsupported`）。
9. **诊断。** 拿到锁之后把进程号写进锁文件，不同步，只在"忙"的拒绝里作为提示带出，不参与任何判断。"是否被持有"只有一种问法：试着拿一次。
10. **锁目录由维护的自举创建**（与今天创建 `runtime` 前缀在同一处）。别的命令发现它不在时照旧以 `operation-scope-missing` 指向维护。更新到这一版的维护把旧的锁目录与锁文件删掉。
11. **锁不再分落盘的档位。** ADR-0032 补记一、补记二里关于七类锁"取轻放重"的规定随之作废：锁在磁盘上没有任何需要落盘的状态。

## 不再保证什么

| 拿掉的 | 不再有的保证 | 现场记录 |
|---|---|---|
| 锁文件里的属主记录 | 看不出"谁在持有"到可以据此判断的程度；"忙"的拒绝里的进程号只是提示，可能是上一个持有者留下的 | 属主记录只被清死锁的判断用过 |
| 与旧版本进程之间的互斥 | 这一版之前的进程用文件锁，这一版用内核锁，两边互不相认。靠的是已有的门：每个变更入口先核对磁盘上的制品清单有没有被换，换了就拒绝。漏的是更新那一刻已经过了这道核对、还在跑的那一次调用 | 1.4.3 的桌面一轮里，进程还活着的老会话在更新后被这道门拦住（§13.288）；更新只在没有活动 Demand 时做（ADR-0026） |
| 任何卷上都能用的文件锁 | 工作区放在不支持咨询锁的卷（部分网络共享）上时不能用 | 没有出现过；ADR-0021 只支持本机 |
| 按名字分的锁 | 两个 pod 同时发布各自的 Demand、同时写两条账本记录、同时改两个需求包的认领状态时，先后排队 | 一次发布在 1 秒以内 |
| 更新时对旧锁文件的属主判断 | 更新的维护直接删掉旧的锁目录与锁文件，不判断旧持有者是否还活着 | 同第二行：更新时没有在途的调用 |
| `maintenance-owner-unknown`、`operation-scope-release-failure` 等拒绝原因 | 这些情形不再存在，原因码从目录里删掉 | — |

不变的：谁和谁互斥、锁的嵌套次序（合并的四类里没有同类嵌套——合并之前逐类核对，原语的重入检查在测试里兜底）、各类锁的等待预算、超时与中止的拒绝原因、维护"没做完就要恢复"的判断（它本来就看事务目录）。

## 随之消失的登记项

L10 里的 9 条：进程号复用判不清（锁的那一半）、两个进程同时清同一把死锁、首次初始化被死锁文件挡住、释放时删除没落定就跳过同步、按记录命名的锁永久留下（两处）与读者租约攒到 64 个才清、轻档获取输掉链接时暂存的删除不同步、全新初始化的端到端测试（准入目录里不再有锁文件）、卷的类型只在预览里看一眼（并进决定 8）。

## 后果

- **删掉的。** 锁原语与它的属主记录、查看、退役、释放失败的报告者；读写作用域里的租约与清点；维护门的残留处理里与门锁有关的一半；12 处"在锁内执行"前面的查看与退役；核心布局检查里对锁文件名与死锁的特判；锁的两档落盘及其登记表；`tests/support` 里造死锁残留的三个辅助进程。
- **新增的。** 一个原语（foundation）、一张锁名表与"在某把锁内执行"的入口（内核层）、macOS 的两个标志常量。
- **测试。** 原语用真实子进程测：持有时别人被拒、强杀后立刻可得、共享与独占的组合、节点被换后重来、重入报错、自测在不支持时拒绝。作用域测写者优先与"门"上的准入前检查。各类锁原有的"属主已死的残留"测试随残留一起删。
- **预期净减。** 源码约 1,200 到 1,500 行，测试约 2,000 行。按模块大小估的，以做完之后数的为准，每一批报告实数。
- **合同。** 公共请求与结果的形状不变；拒绝原因的目录减少几项，`refusals.md` 重新生成，技能里提到这些原因的地方一并删。
- **文档。** 本文接受之后，ADR-0032 补记里锁的档位、ADR-0014 决定 3 里"按 podId 隔离的运行锁"各加一行指向本文。

## 证明

崩溃扫点已在 1.4.2 删掉，不重建。这一项靠三样：

1. 原语的真实进程测试（上面列的）。
2. 场景链与各切片的测试照常通过——互斥的语义没有变，变的只是持有者死后的盘面。
3. tmux 一轮里的杀进程演练：在创建 Demand、规划、导入结果、记决定、完成、维护各自持锁的时候强杀服务进程，再发下一条命令，记录每一处是直接继续、还是由已有的 recover 接住。

## 没有核实的

- 机器睡眠唤醒、磁盘写满时内核锁的行为。
- 更新那一刻在途调用的窗口有多宽。
- 活动投影每次刷新都先恢复一次索引的暂存，开销多大——第二批量出来。
- 合并的四类里有没有同类嵌套：读过看板（文件头写明索引锁与状态锁互不嵌套）与账本记录的调用点，另两类在动手时逐处核对。

## 实现记录（2026-11-26）

做完之后与上面的决定对不上的地方，以及动手时才定下来的细节。以代码为准，这里只说差在哪里和为什么。

1. **决定 9 没有做：锁文件里不写进程号。** 写了之后发现没有任何读者——"忙"的拒绝没有把它带给调用方的字段——而每一次独占获取都会改动锁文件的字节，凡是"这次操作改了哪些文件"的观察（场景链里的重新配置一幕）都会看见它。删掉之后锁文件是空文件，建出来就不再有人写；"不再保证什么"表第一行里"进程号只是提示"那半句随之作废："忙"的拒绝不带进程号。
2. **决定 10 的后半句要靠一个真实的步骤才成立。** 从 1.4.3 更新上来的工作区，对账原本没有任何步骤，没有步骤的应用不进维护的门，锁目录于是永远建不出来，之后每一条要进操作作用域的命令都以 `operation-scope-missing` 被拒——一个出不去的状态。改成：锁目录是本地协议的一段，核心布局检查在"事务目录在、锁目录不在"时报 `bootstrap-prefix`（事务目录里有残留时仍然先报 `recovery-required`）；状态于是指向维护，对账计划里出现已有的 `core:local-protocol` 这一步，它的目标摘要改为整张维护资源目录（五条声明，含锁目录）。只有这一步（或再加重装自己发布的文件）的计划归 Controller 自己应用，与"插件更新之后的那次对账不用用户确认"是同一条规矩（用户裁决 2026-11-15、2026-11-25）。
3. **旧锁的清理**在 `wakeflow-file-lock-residue.ts`，只活一个版本。每一次做成的维护在门内、所有计划核对之后调用它：以准入目录 `.wakeflow-local/runtime/operation-admission` 为记号——在就清，最后才删它，中途被打断下一次接着做。删的是四个目录（准入、pod 变更、看板的 `locks/`、Demand 发布的 `locks/`）与只在持有者被强杀后才留下的文件（旧的维护门、投影器锁、工作区根上的四个、每个宿主登记表旁的登记锁）。尽力而为：删不掉就停，不让维护失败。
4. **两处读者为旧残留留了一个版本的余地。** 登记表的清点跳过 `.registration.lock`：它不跳过，一份强杀留下的旧登记锁就让登记表读不出来，而读不出登记表会挡住对账的预览——也就挡住了删它的那次维护。看板的列举照旧跳过 `locks` 这个名字。
5. **账本事务目录里按记录命名的旧锁文件没有清。** 账本根不一定在工作区根下；那种文件只在一次发布被强杀后才留下，没有读者被它挡住；这一版起不再有新的产生。用户的正式工作区里是 0 个（2026-11-26 只读查看）。
6. **托管的 `.gitignore` 块不重写。** 旧的块比今天多四条忽略根锁文件的规则，登记进托管正文的历史表之后照常被准入；它仍然满足今天的全部规则，所以对账不为它出步骤。多出的四条忽略的是已经不存在的文件。
7. **锁的等待超时在边界上是可重试的并发冲突。** `KernelFileLockError` 在 `timeout` 时带 `retryable`；没有被调用方说成自己的拒绝而逃到公共信封的那一种，由旧错误家族表翻成 `concurrency-conflict`。
8. **随锁一起删掉的**：释放失败的事故来源（`lock-release`）与事故记录里只有它用的 `resource` 字段；三处重组合同里从未被报出过的 `recovery-not-required`；资源目录里的七条锁声明与两处"锁的写法准入"。
9. **"没有核实的"里的第四条已经核实**：合并的四类里没有同类嵌套——1,505 个用例里重入检查没有被触发过；两个 pod 同时创建 Demand 改为先后进行，测试按排队改写。第三条（活动投影每次刷新先结算一次暂存的开销）还没有量。
10. **实数。** 源码净减 1,313 行，测试净减 2,332 行（`git diff --numstat`，含新文件）。`createFileAtomically` 的 `content-only` 一档——只同步内容、不同步父目录——在锁换掉之后没有调用方，接着的一个提交把它删了：逐次选项只剩 `fsync` 与 `none`，暂存内容与父目录要么都同步、要么都不同步。
11. **锁名是十三个，不是十二个。** 多出来的是 `evidence-publication`：证据的记录与它的 recover 此前没有任何互斥，真实进程里量出 recover 会把一次还在跑的记录接过去做完（gate-log §13.293）。它不是从旧的锁文件换来的，是这套办法便宜到可以补上的一把。
12. **"证明"第 3 条做了（gate-log §13.294）。** tmux 一轮里在认领、准备投递、导入结果、记决定、完成、维护六处持锁时强杀服务进程，六次都由 status 点名的 recover 或对账收场；同一轮里真实的 1.4.3 工作区更新上来，一次不用确认的对账。
