# ADR-0030 结果报告的事件形状升级一次：逐条锚点的结论与任务包之外收到的指示

> 状态：`accepted`
> 提出日期：2026-11-17
> 裁决日期：2026-11-17（用户 2026-11-16 同意"越级指挥留痕"作为 1.4 第二项并"可以全部按照你的建议先记录"；2026-11-17"其余按照你的建议记录和执行"）
> 基线提交：`44ac74f1`
> 相关：ADR-0012 D5（锚点引用验收标准）、ADR-0014（持久格式冻结与显式迁移）、ADR-0029（调用形状）、ADR-0031（防御的留存标准）、[1.4 开发计划](../reviews/2026-11-17-1.4-development-plan.md) 第 3、4 段、open-items H13、I22

## 背景

- 目标的结果报告存在 `result.target-result-recorded` 事件里（`data.result.report`），不是单独的文件。实现报告的字段是 `outcome`、`summary`、`repositoryChange`、`evidenceLocators`、`verification`、`risks`、`anchorEvidence`。
- 目标技能要求"任务包里的每条验收锚点都要回答：满足、不满足或受阻，并写出实际观察到的"。报告里没有承载它的结构化字段，只能写进自由文本。Controller 评审时因此要自己把每条锚点再记一遍：小样本里评审决定占 Controller 手写内容的 47%，其中对独立检查的记述又占一半以上。
- 使用者直接对目标窗口说话，系统里没有任何记录；目标技能也没有写这种情况该怎么办（open-items H13）。1.3.1 的现场里，Controller 只能从报告的自由文本里看出偏差，再回头向使用者核实。
- 事件的持久形状自 ADR-0014 起冻结在版本 1；15 个事件族至今没有登记过任何一步升级，上一次不兼容是用可选字段加兼容分支绕过去的。
- 改已持久化的事件形状要动：两份领域报告 Schema、导入请求（它的属性必须与领域报告一一对应）、导入结果与评审检查结果里内嵌的报告定义、解析器与摘要的基、隐私扫描读的文本集合、版本编解码与黄金重放。

## 问题

要加的两样东西都落在同一个事件上。分两次加就是两次迁移。并且"每条锚点必须回答"是一条新的强制要求，不只是多一个可以不填的字段。

## 决定

1. **只升级一次。** `result.target-result-recorded` 的报告升到版本 2，一次带上下面两项。1.4 里不再对这个事件做第二次形状改动。
2. **逐条锚点的结论。** 实现报告新增 `anchorResults`：任务包里的每条验收锚点恰好一项，`{anchorId, status, observed}`。`status` 四选一：`passed`（核对过，成立）、`failed`（核对过，不成立）、`blocked`（想核对但被挡住）、`not-run`（没有核对）。`observed` 是目标实际看到的事实。导入时核对锚点集合与任务包一致，缺项或多项被拒并点名。绝不把没有核对的写成 `passed`——这句话进目标技能。
3. **任务包之外收到的指示。** 两种报告都新增 `outsideInstructions`：零项或多项，`{source, summary, handling}`。`source` 是 `user`、`other-session` 或 `unknown`；`handling` 是 `followed`（不改合同，照做了）、`declined`（与任务包冲突，没有照做）、`escalated`（停下来上报）。没有收到就写空数组，不省略。
4. **版本与旧记录。** 旧事件（版本 1）经一个登记在案的升级步骤读入：`anchorResults` 与 `outsideInstructions` 记为"未记录"，不伪造结论。这是升级器机制的第一次真实使用；它连同黄金重放的补充一起，决定这套脚手架在 ADR-0031 的清单里是留还是删。
5. **评审因此变短。** 评审单元把目标的逐条结论与 Wakeflow 的观察（ADR-0028 的提交事实、第 4 段的越级观察）并排给出。Controller 的独立检查只需要记它重新核对过的、或与目标结论不一致的那几条；接受一个 `needs-review` 结果时锚点与证据的对应关系仍然必须齐全。
6. **测试报告。** 测试报告已有逐步的 `verdict`，不加 `anchorResults`；只加 `outsideInstructions`。四个取值与测试步骤判定词汇的对应关系写进合同说明，不改测试一侧的词汇。
7. **阅读面读这两项。** 每个 Demand 的页面上"验证了什么"一栏直接来自 `anchorResults`；"直接干预"一栏来自 `outsideInstructions` 与观察。

## 后果

- 合同与生成物：两份领域报告 Schema、导入请求、导入结果与评审检查结果内嵌的报告定义；工具目录预算重算（请求 Schema 计入）。
- 代码：解析器、摘要的基（新成员进摘要）、隐私扫描的文本集合、版本编解码登记第一步升级。
- 测试：黄金重放语料补版本 2 的提交与"版本 1 读入"的用例；导入的拒绝（锚点缺项、多项、未知锚点）；场景链两宿主各补一条。
- 文本：目标技能与测试技能各加一小段（逐条回答、任务包之外的指示怎么处理）；Controller 的评审参考相应删短。净行数不增加。
- 门：动了合同与持久形状，走完整门。

## 未决问题

- `observed` 的长度上限沿用现有的人读文本上限（8192 个码点）还是更短。
- 升级步骤对旧归档的只读核对范围：用测试工作区里现存的归档逐份读一遍。
- `outsideInstructions` 与 hook 观察到的条数不一致时，评审单元只并排显示，还是给出一个提示码——倾向只并排显示，判断留给 Controller。
